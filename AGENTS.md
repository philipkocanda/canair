## Running the CLI — ALWAYS use `uv run canair` from the repo root

**Every `canair` invocation in this repo MUST be run as `uv run canair …` from the project root (`/Users/philip/projects/canair`).** Do NOT call a bare `canair` (a globally installed `uv tool install .` copy). Running bare `canair`:

## Prefer canair's built-in tooling — do not hand-roll

For **all** querying, capturing, analysis, and reverse-engineering, use the dedicated `canair` subcommands documented below rather than raw sockets, ad-hoc scripts, or hand-editing YAML:

- **Query/read the device** with `canair query` / `monitor` / `scan` / `discover` / `io` / `routines` (use `raw` only as a last resort). `canair monitor` is the live, continuously-refreshing view (was `query --monitor`, now its own top-level command).
- **Analyze historical data** with `canair captures`, `canair decode`, `canair correlate`, `canair hunt`, `canair investigate`, `canair coverage`, `canair research`.
- **Edit definitions** with `canair pids` (surgical, validated) — not by hand-editing `ecus/` YAML.
- **Always pass `--save`** (with `--label`, `--state`, `--notes`) when reading from the device so every payload is recorded to `captures/`. See **Key Files → captures** below for the full flag set and examples. `--save` works with `query`/`monitor`/`scan`/`raw`/`discover`, positional query/raw steps. Saves are **journaled** (a write-ahead log under `captures/.journal/`) and reconciled into the dated capture file on exit, so a killed/crashed/disconnected session is never lost — recover leftovers with **`canair captures uds --recover`** (`--discard` to drop them). In `canair monitor` press **`s`** to set/edit the label/state/notes of the **current** session live (the save modal names which segment it labels), or **`n`** to **close the current segment and start a fresh one** (each segment reconciles to its own capture file, so one run yields several labelled sessions); an active `--save` recording shows a blinking **`● REC`** in the status line. Other monitor keys: **`?`** opens a keybinding help modal, **`=`/`-`** change the poll interval live, **`space`** pauses, **`f`** toggles follow-tail, **`r`** toggles byte-index rulers, **`l`** opens a scrollable **errors/diagnostics log** overlay (a live view of `canair logs` — the transport-fault event log, colour-coded by category), **`↑`/`↓`** select a parameter row for in-place editing and **`esc`** clears (deselects) that selection; when a payload byte changes, the parameter(s) whose expression decodes that byte are highlighted with the same coverage-coloured background the changed byte gets (verified→dark_green, unverified→dark_goldenrod), linking a byte flash to the value it produced. The status line shows a **`captured N/uniq M`** frame counter (total fresh payloads received vs distinct values kept — both differ from the on-screen row count) and a **`drops D`** transport-health indicator (cumulative dropped/stale ISO-TP frames, red when non-zero + a per-cycle `+N` spike; an `err E` count for other non-answers) — surfaced from the active client's `.diag` (`canlib/transport_stats.py`) to flag connection/latency trouble live. Each recorded `--save` session also stores its acquisition **`transport`** (`slcan-tcp`/`wican-ws`; `import` for `canair import uds`), the recording canair **`version`**, and a **`quality`** footprint (`exchanges` + any non-zero drop/stale/no_data/bus/decode counts) as capture provenance — shown in `canair captures uds --sessions` and inspectable in full via `canair logs`. The **vehicle state is auto-suggested** from decoded PID values via the profile's `vehicle_states.yaml` (see `canair validate states`) — the save modal's state field is **free text** (comma-separated), pre-filled with the auto-suggestion, and shows whether a state is set (`state auto-detected: …` / `no state set — will auto-detect from data on save`). When a `--save` segment is left without an explicit state, it is back-filled on reconcile with the **union of every state observed across the segment's whole span** (not just the state active at exit), so a segment that charged then went idle still reconciles as `charging`. Repeated non-`--save` on-demand saves only write payloads seen **since the last save** (no duplicates). **`canair monitor` keep-mode defaults to `--keep-unique`** (only distinct payloads per PID are stored/recorded, so a long `--save` session doesn't balloon its capture file with polled duplicates); pass **`--keep-all`** to record every polled cycle (full time-series, larger files — use it when you need real timing/rate) or **`--keep N`** for the last N per PID.

## Tools

> Reverse-engineering a new PID/DID end-to-end (discover → capture → analyze → define → verify) is documented in the **reverse-engineer-signal** skill; general project/device context is in the **ioniq-reverse-engineering** skill.

All functionality is exposed through a single installable CLI, **`canair`** — but in this repo you **always** invoke it as **`uv run canair …` from the repo root** (see "Running the CLI" above). `uv tool install .` exists for end users, not for agents working in the tree.

- **`canair wican`** — Build/sync the WiCAN device's AutoPID profile from the active bundle's `ecus/`. A bare `canair wican` prints help (writes nothing). Subcommands: `autopid write` (generate JSON to `out/` — **verified-only by default**; pass `--include-unverified` to also emit in-progress candidate params), `autopid upload`/`download`/`diff` (device sync, Pro-only — `upload`/`diff` share the same verified-only default + `--include-unverified` opt-out), `autopid stats`, and `mode show`/`mode set MODE` (device protocol switch, Pro-only — `mode set` also auto-aligns the config `transport.type` to the new mode: `slcan`→`slcan-tcp`, `elm327`→`wican-ws`, printing the `old -> new` change or "already"; `--no-transport` opts out, other modes leave it untouched)
- **`canair query`** — Custom CAN/UDS requests over the configured transport (raw `slcan-tcp` by default, or the `wican-ws` WebSocket ELM327 terminal). **Prefer positional query steps** like `canair query BMS:2101` (multi mini-language — handles sessions, wake, keepalives; a bare selector like `BMS:2101` is treated as a query step). **Bind each PID to its ECU with a colon (`IGPM:22BC07`), never a space** — in a query step a space separates *independent ECU selectors*, so `"query IGPM 22BC07"` means "all of IGPM plus a bogus ECU 22BC07" and is rejected. Use `canair query --param`/`canair query BMS` for simple single-ECU reads, `canair scan range` for discovery. Companions: `canair discover`, `canair io`, `canair routines`, `canair identity` (standard UDS identity DIDs — F100/F18x/F190/F19x), `canair scan routines` (probe requestRoutineResults across a range — auto-selects UDS 0x31 SF03 or KWP2000 0x33 RequestRoutineResultsByLocalIdentifier by `id_protocol`, so it never blind-sends 0x31 StartRoutine to a KWP2000 ECU; hits saved to `ecus/<ecu>.yaml` `routines:`), `canair scan iocontrol` (probe returnControlToECU across a DID/LID range — auto-selects UDS 0x2F or KWP2000 0x30 by `id_protocol`; hits saved to `iocontrol_discoveries:`), `canair raw` (**last resort** — hex dump only, no decoding), `canair repl` (interactive). `--verbose` is for debugging canair itself, not normal use. **TesterPresent keepalives are automatic and there is no `tester-present` command/flag** — opening a session (a `session <ECU>` query step or any command's `--session`) keeps it alive with idle-aware `3E00` (real traffic resets the S3 timer). `3E00` (SID `0x3E`) is shared by UDS and KWP2000, so it is sent identically for both protocols; send one by hand via a query step (`canair query BMS:3E00`), or use the `repl`'s `!tester` for a manual loop. **Use `--reboot` to restore AutoPID after session** (WebSocket terminal overrides AutoPID mode). Dependencies: `websockets`, `pyyaml`, `requests` (optional, for reboot).
- **`canair monitor`** — Live, continuously-refreshing view of ECU parameters (promoted from the former `canair query --monitor` flag into its own top-level command). Takes the same positional query steps as `canair query` (`canair monitor BMS:2101`, cross-ECU `"VCU:2101 BMS:2101"`), plus `--interval SECONDS` (poll period, default 5.0; change it live in the TUI with `=`/`-`). On a TTY it opens the scrollable Textual monitor; piped it polls silently until Ctrl+C. Recording (`--save`/`--label`/`--state`/`--notes`) and keep-modes (`--keep-unique` default, `--keep-all`, `--keep N`) live here, not on `canair query`. **`canair query` no longer has a `--monitor` flag** — use `canair monitor`.
- **`canair captures`** — Query captured data, split into two domain kinds (the `uds`/`can` naming spine). **`canair captures uds`** (domain A — diagnostic UDS payloads) takes a QUERY (mini-language, like the other tools): `BMS 2102` (ECU + PID, most useful), `"BMS:2102,2103"` (several PIDs), `BMS` (all PIDs for an ECU), or a quoted cross-ECU `"VCU:2101 BMS:2101"`. Add `--diff` for the byte-level diff view or `--step` to interactively step through captures (the step header shows the ECU's `alias` when it has one, e.g. `SKM (alias SMK)`). **The default list view is capped at the most recent `--limit N` captures (default 50; `--limit 0` = no cap) with a loud footer reporting any hidden history — so a bare `canair captures BMS 2102` can't blow the context window; widen with `--limit N`/`--limit 0` or a tighter scope (`--since`/`--last-session`/`--state`).** `--latest` (dedup-per-PID, most recent payload) reads its ECU/PID from the **QUERY** (`canair captures BMS --latest`, `BMS:2102 --latest`; a bare `--latest` = every PID's latest). Aggregate modes (no QUERY): `--summary` (stats per ECU/date), `--sessions`/`-n` (session **table of contents** — date/time-span/state/label/session-notes/ECUs + distinct capture-notes per session, plus each session's acquisition `transport`, the recording canair `version` (a `· vX.Y.Z ·` tag), and a `quality` line flagging any recorded drops/errors, no payloads; the fast "what's in the captures?" index, `--json` for machine output), `--recover` (reconcile orphaned journals from a killed/crashed `--save` session into capture files; `--discard` to delete them unsaved). **`--delete`** removes the captures matching QUERY (+ scope filters) via canair's own helpers — refuses a bare `--delete` (never nukes everything), previews with `--dry-run`, and confirms interactively unless `--yes` (scripting); never hand-edit `captures/` to remove data. Any mode can be scoped to a date/time range with `--since`/`--until` (inclusive; accepts a date `YYYY-MM-DD` **or** a timestamp `YYYY-MM-DD HH:MM[:SS[.ffffff]]` to narrow within a day) or `--date` (single day) or `--today`, the most recent sessions with `--last-session`/`--last-sessions N`, and/or by `--state SUBSTR`/`--label SUBSTR` (case-insensitive substring of the session state/label). **`canair captures can`** (domain B) lists imported raw broadcast-CAN frame logs from `captures/can/index.yaml` — file/format/frames/IDs per log (`--json` for machine output). **`canair captures migrate`** converts a profile's legacy per-day capture files (`captures/*.yaml`) to JSON (`captures/*.json`) — the one-time migration for a profile created before the JSON cutover; each file is round-trip verified before its YAML is replaced (`--dry-run` to preview, `--json` for machine output). **`canair captures migrate-rx`** renames the persisted capture field `ecu` → `rx` (the field holds the ECU CAN *response* address, RX = request TX + 8 — not an ECU name, so it was renamed to stop the confusion with the resolved short name; readers still accept the legacy `ecu` key via `capture_io.capture_rx`, so the migration is safe to defer). It renames at the capture level and inside `scan_results.responding[]`, is idempotent, and previews with `--dry-run` (`--json` for machine output). **`canair captures merge-driver`** is the git merge driver for the append-only capture files: invoked by git as `merge-driver %O %A %B %P` it **unions the session lists** so two machines' same-day appends merge cleanly instead of conflicting (git's line merge splits those conflicts mid-record); a genuine divergent edit or unreadable input falls back to normal conflict markers. It's wired via a `.gitattributes` rule (`profiles/*/captures/*.json merge=canair-captures`) but requires a **one-time per-clone registration** — run **`canair captures merge-driver --install`** once to write the `[merge "canair-captures"]` stanza into `.git/config` (git never loads a driver command from a tracked file, for safety; until a clone installs it, merges simply fall back to markers, so nothing breaks). Pure union in `canlib/captures_merge.py`. A bare `canair captures BMS 2102` (or any of the `--summary`/`--sessions`/… flags) is shorthand for `canair captures uds …` (via `_GROUP_DEFAULTS` in `cli.py`, like `scan`/`ecu`).
- **`canair import uds`** — Device-free UDS capture import (domain A; the `uds` kind of `canair import`): record an externally-provided UDS payload (pasted from a forum/issue, or read on another tool) into the active profile's `captures/` through the same machinery as a live `--save`, so it's indistinguishable from a device-recorded capture and immediately queryable by `decode`/`captures`/`coverage`. Each capture is `ECU:PID=PAYLOAD` (ECU short name or hex TX id; PID/DID; reassembled UDS payload, SID-first, PCI stripped); pass several to group them into one session. Metadata via `--label` (required), `--state` (repeatable, vehicle power state), `--notes`/`--capture-note`, `--time`, `--date` (default today; sets the target file). Resolves ECU→RX, rejects non-hex payloads, and **warns on SID/DID echo mismatch** (a payload filed under the wrong PID) without blocking. `--json` for machine output. This is how community-contributed readings (no device on hand) are onboarded — never hand-write `captures/`. (The domain-B ingest counterparts are `import can` / `import dbc` — see `canair import` below.)
- **`canair decode`** — Parameter/value-centric decoding: applies WiCAN expressions to all historical captures. **Takes a QUERY in the shared mini-language** (`canair decode BMS:2101`, the two-token `BMS 2101` still works, `BMS` = all its PIDs, `"MCU:2102 VCU:2101"` cross-ECU). **Default view shows each param's value range** across captures (payload/byte-diff views live in `canair captures`). **Multi-PID queries are supported for the default value-range, `--compact`, and `--json` views** (one section/JSON block per PID); the analysis modes below (`--corr`/`--plot`/`--stats`/`--discriminate`/`--find-mirrors`/`--try`/`--dump-bytes`) require the query to resolve to a **single** PID. Modes: `--param` (filter), `--compact` (one aligned row per capture — param names in a single header, `[state]` divider only when the session state changes, time-only rows, right-aligned value columns; add `--changes-only`/`-c` to drop rows unchanged from the previous one, collapsing stationary runs), `--stats` (n/distinct/mean/median/stdev per param; add `--group-by state` for per-drive-segment stats in one shot), `--corr PARAM` (Pearson correlation of every param vs a reference — **`PARAM` may be a local name OR a cross-signal `ECU:PID:PARAM`/`ECU:PID:EXPR`**, e.g. `--corr ESC:22C101:REAL_SPEED_KMH`, time-aligned by nearest timestamp; add `--corr-transform delta|abs|cumsum|normalize` to test level-vs-rate, `--method pearson|spearman` to pick the coefficient (spearman = rank, catches monotone-but-nonlinear/quantized/saturating links; **`cramers_v`/`mutual_info` treat each value as a nominal category — for enum/mode/flag references where numeric spacing is meaningless**; a **`--method` cheat sheet** — which coefficient when — is in `canair decode --help` / `correlate --help`), `--join-tol SECONDS` to widen the join), `--discriminate state` (rank params by how cleanly they separate across power states — an F = between/within variance ratio for numeric params, **Cramér's V for typed enum/bitmask params** — that surfaces thermal/mode/relay signals a driving correlation misses; add `--bytes` to also rank every varying raw byte and `--bits` every toggling bit, no `--try` needed), `--find-mirrors` (`--bits` for bit-level: report byte/bit positions exactly equal across all captures — redundant status mirrors / unit-variants), `--plot` (interactive signal explorer — a Textual TUI: sweep ImHex-style byte interpretations `u8/i16/f32/…`×endianness and params, plot across captures, apply transforms `delta/abs/normalize/…`, zoom/pan the x-axis, overlay a `--corr` signal, show the visible date/time range, list the backing captures in a modal (`i`), flag bytes already mapped by a defined param, read off the equivalent WiCAN expression, switch to another captured PID in place (`p`), annotate the current param/byte or rename the PID via `canair pids` (`a`/`R`), and `?` for a keybinding help modal), `--try "NAME[:unit]=EXPR"` (test a candidate expression against captures **without** editing YAML; works even for a not-yet-defined PID), `--verified`/`--unverified`, `--json`. **Scope which captures are considered** (shared with `canair captures`): `--since`/`--until`/`--date` (inclusive; a date `YYYY-MM-DD` or a timestamp `YYYY-MM-DD HH:MM[:SS[.ffffff]]` for `--since`/`--until`), `--today` (shorthand for today's date), `--last-session`/`--last-sessions N` (the most recent N recorded sessions in scope — applied *after* date/state/label, so `--state driving --last-session` = the last driving session), `--state SUBSTR`/`--label SUBSTR` (case-insensitive substring of the session state/label — the natural unit of drive analysis, e.g. `--state driving`), and `--first N`/`--last N` (chronological slice). Example drive analysis: `canair decode MCU 2102 --stats --group-by state --state driving`. **`--dump-bytes`** emits a `timestamp × byte-offset` matrix (one row per scoped capture) instead of decoding params — CSV by default, `--json` for JSON, PCI framing bytes skipped unless `--include-pci`, columns relabelled by `--notation`; the structured escape hatch for ad-hoc byte analysis (replaces regex-scraping `captures --diff`).
- **`canair correlate`** — Cross-signal correlation across a whole drive/session: time-aligns every decoded param (and, with `--bytes`, every varying raw byte; `--bits` for toggling bits) across all co-polled ECU/PIDs in scope and ranks the strongest cross-signal relationships — the "show me every strong relationship in this drive" entry point (how the AAF-speed / MCU-temp finds were made). Optional `ECU[:PID]` selector to restrict signals. Modes: default ranked pair list (cross-PID/ECU only unless `--include-intra`; near-perfectly-correlated |r|≥0.995 groups collapse to one summary line unless `--no-cluster`), `--against ECU:PID:PARAM` (rank every signal vs one reference — drops the trivial self-match unless `--include-self`; `--promote NAME` writes the top raw-byte hit into `ecus/` as an enabled unverified candidate; `--lag-scan N` reports the apparent lead/lag that maximises |r|; `--gate '[SIGNAL] OP VALUE'` restricts to a regime e.g. `'> 0'` = while-moving), `--overlap` (report which ECU:PID pairs actually share time-aligned samples in scope — pick a viable `--against` reference), **`--against-file FILE`** (rank every signal against an external `timestamp,value` CSV instead of an on-bus reference — a calibrated meter/GPS/grid-voltage log; mutually exclusive with `--against`; nearest-timestamp join on the captures' absolute clock), **`--control ECU:PID:PARAM`** (or `--control-file`; with `--against`, rank by the **partial** correlation with a nuisance signal regressed out — surfaces signals visible only once a dominant driver is removed), **`--find-mirrors` (report byte/bit positions that are time-aligned *equal* ACROSS co-polled ECU/PIDs — e.g. a door bit in IGPM mirrored in BCM; add `--bits` for bit-level; the cross-ECU companion to `decode --find-mirrors`, which is single-PID. Beware small `--min-n`: noisy low bits can match by chance)**, `--matrix`, `--json`; `--method pearson|spearman|cramers_v|mutual_info` (the last two rank by *categorical* association — for mode/flag/enum bytes; a **`--method` cheat sheet** explaining which coefficient to use when is in `canair correlate --help`); `--transform delta|abs|…` (transform the `--against` reference); thresholds `--min-r` (default 0.6) / `--min-n` (default 15) / `--top`; `--join-tol SECONDS`. Same scope flags as `decode`. **Warns when the scope includes `keep:unique` sessions** (rising-edge-only data) and caveats `--transform delta|cumsum` / `--lag-scan` on it. **Domain B — `canair correlate can FILE`** correlates a raw broadcast-CAN frame log's per-byte series instead of diagnostic captures — reads the native log (`--can-format auto` by extension), builds `0xID:rN` byte series (`--bits` for `0xID:rN.k`), and runs the *same* ranked/`--against`/cluster core (cross-arbitration-ID by default; `--include-intra` for same-ID; `--id 0x220,0x386` to restrict). **`--find-mirrors` works here too** — reports byte/bit positions time-aligned *equal* ACROSS arbitration IDs (a signal broadcast on two IDs, e.g. wheel speed on `0x386` and `0x331`); add `--bits` for bit-level. Frame labels render as-is (raw-CAN space, no WiCAN/PCI). Everything above is the default **`correlate uds`** kind — a bare `canair correlate …` is shorthand for it (via `_GROUP_DEFAULTS`); the diagnostic (WiCAN `Bn`) path is unchanged.
- **`canair hunt`** — "Which byte on ECU:PID *is* this known signal?" Sweeps every byte offset × interpretation (`u8/i16/f32/…` × endianness) on the target PID, time-aligns each against `--against ECU:PID:PARAM` (a known signal on another ECU/PID), and ranks by |Pearson r| — reporting the best **linear fit** (`y=m·x+c`) and a **physical-unit guess** (`raw−40 °C`, `×1.609 mph→km/h`, …) for each hit. Collapses to the best interpretation per byte offset by default (`--all-interps` to expand). `--transform delta|abs|…` hunts the byte that tracks the reference's *rate* (e.g. torque vs acceleration); `--method pearson|spearman`. `--promote NAME` writes the top hit's expression straight into `ecus/` as an enabled, unverified candidate param (via `canair pids upsert-param`) with the correlation evidence auto-filled into `notes`. **`--against-file FILE`** takes an external `timestamp,value` CSV (a calibrated meter, GPS track, grid-voltage export) as the reference instead of an on-bus `--against ECU:PID:PARAM` (mutually exclusive; joined by nearest timestamp; the file must be on the captures' absolute clock — a relative log joins to nothing). **`--control ECU:PID:PARAM`** (or `--control-file`) regresses out a nuisance signal and ranks by the **partial** correlation — surfacing a byte whose link to the reference only appears once a dominant driver is removed (the AC-voltage-behind-IR-drop case). **`--physical`** needs no reference at all: it flags bytes whose scaled value (`/1 /10 /100 ×2 ×√2`) lands in a named physical band (mains RMS/peak, line freq, 12V rail, HV pack) — the way to find an anchorless signal by plausibility. `--json`, `--top`, `--min-n`, `--join-tol`; same scope flags. **Domain B: `canair hunt can FILE --id 0xID --against 0xREFID:rN`** hunts on a raw broadcast-CAN frame log instead — sweeps every byte/interpretation of one arbitration ID's frames vs a reference frame byte in the same log (raw-CAN `rN` labels, no PCI; `--promote` not supported for frames — those are defined in `signals/`, Stage 4). Everything above is the default **`hunt uds`** kind (a bare `canair hunt AAF 2181 --against …` is shorthand for it); the diagnostic (WiCAN) path is unchanged.
- **`canair investigate`** — One-shot "tell me everything about this PID". For every varying data byte of `ECU PID`, reports in one ranked table: whether a param already **maps** it, its **state-discriminability** F, its strongest **co-polled cross-signal anchor** (r + linear fit + unit guess), and a **physical-band** flag (a scaling at which the byte lands in a named band — mains/HV/12V). Bundles the manual `coverage → discriminate → correlate → hunt` loop into a single call — the "point it at an unknown PID" entry point. Each byte also carries a **triage class** (constant/counter/checksum/enum — a live analog byte is unlabelled) from `canlib/triage.py`, and a **probable multi-byte words** section flags adjacent `[Bn:Bn+1]` pairs shaped like a scaled 16-bit value (near-constant hi byte + full-range lo byte — how a scaled voltage hides across a byte boundary). **`--independent-of ECU:PID:PARAM`** (or `--independent-of-file`) re-ranks bytes by state separation *weighted by independence from* that driver signal — the "active-but-independent" finder (a byte that varies by state yet doesn't track the named driver, e.g. AC voltage vs charge current), adding a `drv` (|r| vs driver) column. **`--bits`** also ranks individual toggling bits (`Bn:k`) — the body/comfort-ECU finder; a body PID with no co-polled anchor is ranked by state separation (no more misleading "no varying bytes"). **`--events`** switches to the bit/byte **edge timeline**: every rising/falling transition with its timestamp and value, aligned to the nearest capture note (the narrated event log) — the fastest way to decode event-driven captures (door/lock/hood). **`--events --field NAME`** collapses a single typed param (enum/bitmask/date/struct) into one logical signal — emitting one transition per change of its *decoded* value (e.g. `fanMAX (45) → fan1 (40)`) instead of scattered per-byte edges. `--all` (include mapped bytes), `--min-r`/`--min-n`/`--join-tol`, `--json`; same scope flags. **Warns on `keep:unique` scope** (rising-edge-only data).
- **`canair research`** — Report the open reverse-engineering backlog from the per-ECU `research:` sections in the profile's `ecus/`. Complements `canair coverage` (undecoded *bytes*) by surfacing *planned* work (scans/decodes/verifies). Modes: `canair research` (all open, priority-sorted), `--summary` (counts by status/type/priority/ECU), `--ecu`, `--type scan|decode|verify|iocontrol_scan`, `--status`, `--priority P1|P2|P3`, `--states acc|ready|…` (was `--prerequisite`), `--all` (include done), `--json`. Use as the "what should I RE next?" entry point.
- **`canair coverage`** — Audit PID definitions for decoding gaps. Cross-references each PID's parameter expressions against its longest captured payload and reports **UNMAPPED** data bytes, incomplete **BITS** (bytes read bit-by-bit with undecoded bits left), and **NO CAPTURE** PIDs (params defined but nothing captured). Modes: `canair coverage` (all), `canair coverage IGPM [22BC03]` (filter), `--bitfields`, `--unmapped`, `--no-capture`, `--all` (include fully-mapped), `--json`. Run after adding params/captures to spot what still needs decoding.
- **`--notation {wican,isotp,torque,bix}` (shared display flag)** — `correlate`, `hunt`, `investigate`, `coverage`, and `decode` (`--discriminate`/`--find-mirrors`) render raw-byte labels as WiCAN `Bnn` by default; `--notation` re-renders them as ISO-TP (`iN`), Torque letters, or bix for reading/cross-referencing. **Display only** — named params are untouched, and `--json`/`--promote` always emit the canonical WiCAN expression. Persist a default with `canair config set display.byte_notation NAME`. Internally a byte is modelled in ISO-TP space (`canlib/notation.py::ByteRef`); WiCAN/Torque/bix are derived views (the byte-notation de-conflation — `plans/2026-07-24-byte-notation-phase2-isotp-canonical.md`).
- **`canair pids`** — Safely add/update the profile's `ecus/` **parameters** and **research** entries from the CLI (surgical, comment-preserving; each edit is YAML-reparsed and schema-validated via `canair validate pids`, and auto-reverted on failure). Subcommands: `upsert-param ECU PID NAME EXPR [--unit --min --max --source --notes --verified/--unverified --type enum|bitmask|ascii|date|bcd --value RAW=LABEL --bit INDEX=LABEL …]` (**typed/multi-modal decoding**: `--type` + repeatable `--value`/`--bit` `KEY=LABEL` pairs define an enum/bitmask; passing only `--value`/`--bit` infers the type. The WiCAN `expression` stays the pure-float device value; the type is a *parallel* decoding rendered by `canlib/decode_value.py`. `ascii`/`date`/`struct` render text/date/record; `struct`'s ordered `fields:` are authored in YAML today. **After a successful write, `upsert-param` echoes the new expression's decoded value RANGE across existing captures** (e.g. `captures: 16h — 20h`, or a yellow `captures: constant 40 (check the offset if you expected variation)` / `captures: ERROR …`) — a passive sanity-check so a wrong byte offset (e.g. a WiCAN `Bnn` landing on an ISO-TP PCI framing byte, which reads a spurious constant) surfaces at write time instead of being silently persisted; `(no captures … yet)` when the PID has none. It never fails the write. **Remember WiCAN `Bnn` includes ISO-TP PCI bytes** (B00/B01 = FF PCI, B08/B16/… = CF PCI; SID at B02) — it is NOT the SID-first reassembled-payload index; confirm an offset with `canair bix -a HEX --ecu … --pid …` or `canair decode … --dump-bytes` (whose column headers are the correct WiCAN `Bnn`) before authoring), `rename-param ECU PID OLD NEW` (rename a param key; fields/formatting preserved), `rm-param ECU PID NAME` (remove a param — when it is the PID's LAST parameter the now-empty `parameters:` block is dropped entirely, leaving a valid identity-only PID rather than an empty `parameters:` that fails the schema), `add-pid ECU PID [--status active|draft|static|ignored (default draft) --prereq STATE … --period MS --notes …]` (create a new **parameter-less** PID — a discovery/identity placeholder like a not-yet-decoded `21F2` — so a bare-ECU capture (`canair query ECU`) polls it; a bare-ECU query polls only *defined* PIDs, so an undiscovered page must be added here first. Defaults to `draft` (swept/queryable but not shipped to the device); scaffolds the `pids:` section if the ECU has none; refuses an existing PID — use `upsert-param`/`set-pid-status` to edit one), `rename-pid ECU OLD NEW` (rename a PID key, e.g. `B002`→`22B002`; status/params/formatting preserved), `rm-pid ECU PID` (remove a whole PID — drops the `pids:` section entirely if it was the last PID, leaving an identity-only ECU), `add-research ECU --type --target --status [--priority --prereq …]`, `set-status ECU TARGET STATUS [--type]`, `set-pid-status ECU PID {active|draft|static|ignored}` (PID lifecycle), `set-pid-variable-length ECU PID {true|false}` (flag a PID as legitimately returning variable-length responses, so a shorter payload isn't mistaken for a truncated ISO-TP read; `false` clears it), `set-identity ECU FIELD VALUE` (set a curated identity field, e.g. `notes`), `set-can-bus ECU CODE [CODE …]` (set the ECU's physical CAN bus segment(s) — codes validated against the profile's own `can_buses.yaml` vocabulary, which is vendor-specific; Hyundai/Kia use `B-CAN`/`P-CAN`/`C-CAN`/`MM-CAN`/`H-CAN`/`D-CAN`/`ALL`; some ECUs span two, e.g. `H-CAN P-CAN`), `set-wake ECU --method rapid_read|session|relay [--prime-pid REQ --attempts N --interval-ms MS --sleep-timer-ms MS --session-mode XX --notes …]` (declare a per-ECU **wake ritual** for a fast-sleeping ECU — some modules, e.g. the SKM, power their CAN transceiver only briefly and sleep within ~1-2 s, so a single `1001` wake races the sleep timer; `rapid_read` fires a cheap full UDS `--prime-pid` request densely with a short per-prime timeout to hold the transceiver awake, then opens a session; honoured by `session <ECU> --wake` on **both** transports. Resolver `canlib/wake.py`; `method: relay` is the Ioniq SKM relay-wake, gated behind the `skm_wakeup` quirk), `set-addressing ECU [--mode --target-address --source-address --fc-id --rx-id]` (set an ECU's CAN addressing override — the make-specific knobs: the addressing `mode` (11-bit / the 29-bit modes / `normal_extended_11bit` for the BMW/PSA ISO-TP extended-11-bit target-byte scheme), the extended-mode ISO-TP extension bytes `target_address`/`source_address` (tester, default `0xF1`), a flow-control arbitration override `fc_id` (functional-TX / physical-RX ECUs, e.g. Renault/Mitsubishi), and/or the response-address `rx_id`; `canair ecu add` takes the same `--mode`/`--target-address`/`--source-address`/`--fc-id`/`--rx-id` to seed a 29-bit/extended ECU offline in one atomic write). Prefer this over hand-editing the rich per-ECU YAML. **Free-text `notes` (here and via `canair ecu add`/`discover --register`) auto-format**: a short note stays inline, a longer/multi-line one is written as a word-wrapped folded `>-` block (shared policy in `canlib/yaml_rt.py`, wrapping only the note — never reflowing the file). Pass plain strings; don't hand-format block scalars.
- **`canair signals`** — The domain-B analogue of `canair pids`: view/edit the broadcast signal-definition sidecar `signals/<bus>.yaml` (arbitration ID → named **linear** signals: `start_bit`/`length`/`byte_order`/`scale`/`offset`/`min`/`max`/`unit`/`verified`). `canair signals` / `signals list [BUS]` (list; `--json`), `signals upsert BUS 0xID NAME --start-bit --length [--byte-order --scale --offset --min --max --unit --verified/--unverified --notes --msg-name --tx-ecu]`, `signals rm BUS 0xID NAME`. Comment-preserving edits. Prefer this over hand-editing `config.yaml`.
- **`canair update`** — Update the CLI from its git-clone install. Locates the source clone (via uv's tool receipt `~/.local/share/uv/tools/canair/uv-receipt.toml`, falling back to the package repo root), reports current vs latest **released** version (GitHub Releases API) with a changelog link, then — after confirmation — **checks out that release tag** and reinstalls: `git fetch --tags` + `git checkout <tag>` + `uv tool install <clone-dir> --reinstall`. Checking out the advertised **release tag** (not fast-forwarding a branch to its HEAD) guarantees the installed code is exactly the released version — never whatever unreleased commits happen to sit on `main`; consequently it **refuses to update when the latest tag can't be determined** (GitHub unreachable), since there's no version to check out (`--check` still reports offline). **Also reports the install context** (`canlib/install_context.py`): *which* copy is running — the **repo working tree** (`uv run` / dev checkout) vs the **`uv tool install` snapshot** (bare `canair`) vs some other install — plus the clone's **current git HEAD** (branch name, e.g. `main`, or `detached at <tag>` after an update — surfaced as `clone_head` in `--json`), and warns when the installed tool copy's version (read from its `canair-*.dist-info` metadata in the uv-tool venv) differs from the source clone's `pyproject.toml` version (**out of sync**: a bare `canair` would run different code than `uv run canair`). **When there's no newer release to check out but the tool copy is out of sync, `canair update` offers a reinstall-only resync** — `uv tool install <clone-dir> --reinstall` with no `git fetch`/`checkout` (the clone is already where it should be), bringing the bare `canair` back in line with the clone. `--check` reports only (no changes), `--yes/-y` skips the prompt (automation), `--json` for machine output (includes the full `install` block — `running_origin`/`running_version`/`clone_version`/`tool_version`/`out_of_sync`). Refuses to touch a dirty clone (won't clobber contributor work) and degrades to printing manual commands when no clone/`uv` is found. Backed by `canlib/update_check.py`, which also drives the **automatic once-a-day background check**: interactive runs kick off a short-timeout, fully offline-safe daemon-thread fetch (any failure is silently ignored, never blocks or fails a command), cache it to `~/.config/canair/update_check.json`, and print a one-line "update available" notice on the next run (also surfaced in `canair status`). The out-of-sync warning is also surfaced in `canair status`. Disable the network check with `check_for_updates: false` in config or the `CANAIR_NO_UPDATE_CHECK` env var.

Logs each scan to the profile's `dtc_log.yaml` (tag the entry with `--label` and the vehicle power state with `--state`, e.g. `--state 'plugged, charging'`) and reports what **changed** since the last scan (DTC *meanings* live per-ECU in each `ecus/<name>.yaml` `dtcs:` section; profile-wide `failure_types:` in `profile.yaml`); clear fault memory with `--clear` (`0x14`). Read-only unless `--clear` is passed.

Live per-ID table (count/rate/last data/changed bytes) for discovering broadcast IDs the request/response path can't see; optional `.asc`/`.blf`/`.csv` frame logging via `--save`, plus `--filter`/`--listen-only`/`--duration`. Complements the active request/response tools which can't observe passive broadcasts.

- **`canair logs`** — View the **central diagnostics event log** (`~/.config/canair/logs/canair.log`), a single **size-rotated** file (small `maxBytes` + a few backups → self-cleaning, never grows unbounded) where transport faults are collated: dropped/stale ISO-TP frames, timeouts, bus errors, decode failures (classified via `canlib/uds_parse.py::classify_response` into `drop`/`stale`/`no_data`/`bus`/`decode`), plus unexpected internal exceptions (`log_exception`). Each line is `TS LEVEL category transport=… ecu=… pid=… :: detail`. `canair logs` tails the last N lines (`-n`, `-n 0` = all, reads across rotated backups), `--path` prints the file path, `--json` emits parsed fields (`parse_event_line`), `--clear` deletes the log + backups (`--yes` to skip the confirm). The event log is written by the per-exchange diagnostics recorder (`canlib/transport_stats.py::TransportStats`, attached as `.diag` on both terminals + the raw client) — the same tally that drives the monitor's live **drops** indicator and recorded-capture **quality** provenance.
- **`canair ecu`** — Inspect the profile's ECU registry (aggregated from the per-ECU `ecus/` files) and per-ECU stats (PID/param/verified counts, protocol, addresses, **CAN bus segment(s)**) via `canair ecu` / `canair ecu <ECU>` (the `show` kind). The list view has a **BUS** column (the ECU's `can_bus` codes) and takes **`--sort {bus,name,tx,proto,pids,verif,caps}`** — **defaults to `bus`** (group the table by segment, unbussed ECUs last); string/hex columns (`bus`/`name`/`tx`/`proto`) sort ascending, numeric columns (`pids`/`verif`/`caps`) descending, with `name` as the tie-breaker; the detail view resolves each code to its human name from `can_buses.yaml` (e.g. `H-CAN (Hybrid CAN)`). **`canair ecu <ECU> pids`** is a compact per-PID view listing every defined PID with its **latest decoded state** (the most recent capture's decoded param values — never raw hex; `--json` supported), pointing at `canair captures`/`canair decode` for full history/stats. **`canair ecu add TX [--name --description --id-protocol --rx-id --mode --target-address --source-address --fc-id --notes --overwrite --dir]`** registers a new ECU offline (no device) — the counterpart to `canair discover --register` for seeding a known ECU into a blank profile (`--rx-id` sets a non-standard CAN response address, e.g. XPeng `0x704`→`--rx-id 0x784`, for an ECU whose response addr isn't `tx_id` + the profile's `addressing.rx_offset`; `--mode`/`--target-address`/`--source-address`/`--fc-id` seed the addressing block so a 29-bit or extended-addressing ECU is created in one valid write); the write is validated + comment-preserving. Companion to `canair validate ecus`.
- **`canair bus`** — Read-only list of the active profile's physical CAN bus segments from `can_buses.yaml`: each declared code with its human name, description, optional **bus speed** (the `bitrate` field, in bit/s, rendered as e.g. `500 kbit/s`), and the **number of ECUs** on it (an ECU spanning two segments counts on each; an ECU tagged with the gateway code **`ALL`** bridges every segment, so it's counted on each declared bus — including the diagnostic bus — not just a lone `ALL` row, with a footnote noting how many gateway ECUs were fanned out). Flags any **undeclared** codes (used by an ECU but absent from the vocabulary) and counts **unbussed** ECUs, prints the source file path at the bottom, and colors output on a TTY only (`--json` for machine output). The read-only companion to `canair pids set-can-bus` (which edits an ECU's `can_bus`).
- **`canair states`** — List and edit the active profile's **vehicle operating-state vocabulary** (`vehicle_states.yaml`) — the state-axis analogue of `canair bus`. A bare `canair states` lists each declared state with its description, whether it's **auto-suggested** (has a `when:` predicate, shown ● + the predicate), and the **number of references** to it across `ecus/` (ECU/PID/DID/iocontrol/research/scan_log `vehicle_states:` fields); it also surfaces **undeclared tokens** (used in `ecus/` but absent from the vocabulary) and the source path (`--json` for machine output). State names are an **UPPERCASE** controlled vocabulary (like the CAN-bus codes) — base `SLEEP/PLUGGED/ACC/ACC2/READY/CHARGING` plus the **`ALL`** meta-token ("applicable/readable in every state"; documentary, no predicate — the state analogue of the `ALL` bus code). ### Profiles

Vehicle data lives in a **profile** bundle — a directory with `ecus/` (one file per ECU — the source of truth), `profile.yaml` (profile-wide settings), `captures/`, `references/`, `vehicle_states.yaml`, and generated `out/`. The repo bundles one or more profiles under `profiles/` (the mature `profiles/ioniq-2017/` is the reference example; `profiles/ioniq-5-2022/` is an early seed). Since more than one profile ships, none is auto-selected — set `default_profile` in config (the bundled `config.example.yaml` sets it to `ioniq-2017`) or pass `--profile`. Selection precedence: `--profile NAME|PATH` (global flag, before the subcommand) > `CANAIR_PROFILE` env var > `default_profile` in config > single discovered profile (auto). Profiles are discovered from `--profiles-dir`, `$CANAIR_PROFILES_DIR`, `profiles_dir` in config, `~/.config/canair/profiles/` (user, uncommitted), and the repo's bundled `profiles/`; user profiles shadow bundled ones by name. Inspect with `canair profile list` / `show [NAME]` (lists every bundle component — `ecus/`, `profile.yaml`, `captures/`, `can_buses.yaml`, `vehicle_states.yaml`, `signals/`, `captures/can/`, `references/`, `out/`) / `path [NAME]`; set the config default with `canair profile use NAME` (an alias for `canair config set default_profile NAME`, validated against discovered profiles). A **bare `canair profile` opens an interactive arrow-key picker on a TTY** (↑/↓ move, Enter sets it as `default_profile`, q/Esc cancels; built on `canlib.tui.select_from_list`); piped/non-interactive it prints the plain list (and hints `profile use` when no default is set). Scaffold a new vehicle with `canair profile create <name> --car-model "…"` (creates `profile.yaml`, empty `ecus/`, `captures/`, `out/` under `~/.config/canair/profiles/<name>` or `--path DIR`; `--set-default` to adopt it).

> **Pass `--profile NAME` explicitly on every *mutative/authoring* command** — anything that writes into a profile: `pids upsert-param`/`rename-*`/`rm-*`/`add-research`/`set-*`, `signals upsert`/`rm`, `import uds`/`import can`/`import dbc`, `discover --register`, `ecu add`, `wican autopid write`, and `--save` reads. Without `--profile` these write to the **active profile**, which is whatever `default_profile` (or `CANAIR_PROFILE`) resolves to — **not necessarily the car you mean**. This is exactly how Ioniq-28-derived `WHL_SPD11` signals once landed in `profiles/ioniq-5-2022/` instead of `ioniq-2017/` (a `signals upsert`/`import dbc` run with `default_profile: ioniq-5-2022` and no `--profile`; fixed in the git history). `canair signals`/`import` echo the target profile + full path on write — read it back to confirm. Read-only commands (`decode`/`correlate`/`hunt`/`captures`/`validate`/`ecu`…) are lower-stakes but still resolve the same way, so prefer explicit `--profile` there too when a specific car is intended.

## Key Files

- **`profiles/ioniq-2017/ecus/`** — SOURCE OF TRUTH, one file per ECU. Each `ecus/<name>.yaml` fully describes one ECU: `identity:` (name is the file's top key), `tx_id:` (request arbitration ID — 11-bit `0x000-0x7FF`, or a full 29-bit id like `0x18DA10F1` when the profile/ECU addressing mode is 29-bit), optional `rx_id:` (CAN response address override — defaults to `tx_id` + the profile's `addressing.rx_offset`, itself defaulting to `+0x08`, or the byte-swapped id for `normal_fixed_29bit`; set only for an ECU whose response address doesn't follow the profile rule), optional `addressing:` (per-ECU override of the profile addressing mode — `mode:` plus the make-specific knobs `target_address`/`source_address` (extended-11-bit BMW/PSA) and `fc_id` (functional-TX flow-control override); edit via `canair pids set-addressing`), `can_bus:` (physical CAN bus segment(s) — a flow list of codes like `[B-CAN, P-CAN]` drawn from `can_buses.yaml`; Hyundai/Kia use `B-CAN`/`P-CAN`/`C-CAN`/`MM-CAN`/`H-CAN`/`D-CAN`/`ALL`; edit via `canair pids set-can-bus`), optional `wake:` (a per-ECU **wake ritual** for a fast-sleeping ECU — `method` + `prime_pid`/`attempts`/`interval_ms`/`sleep_timer_ms`/`session_mode`; edit via `canair pids set-wake`; resolver `canlib/wake.py`), `scan_log:` (probe history), `dtcs:` (DTC meanings), `pids:`, `iocontrol:`, `routines:`, `research:`. Identity-only modules (AMP/SRS) have no `pids:`. Validate with `canair validate pids` (alias `ecus`); `--stats` for counts
- **`canair validate`** — Schema validation with a positional target: `canair validate pids|captures|ecus|states|can-buses|signals|can|all` (default `all`). Add `--stats` for a count summary (ECUs/PIDs/params/verified/research items). Schemas are tool-owned in `canlib/schema/` (`pids_schema.yaml` — covers the per-ECU files incl. identity/scan_log/dtcs, `captures_schema.json`, `states_schema.yaml`, `can_buses_schema.yaml` — per-profile CAN bus vocabulary, `signals_schema.yaml` — broadcast signal maps, `can_index_schema.json` — raw-CAN log index). `validate can-buses` (per-profile `can_buses.yaml`), `validate signals` (broadcast `signals/<bus>.yaml` domain-B maps) and `validate can` (`captures/can/index.yaml` raw-CAN log index) gracefully skip when absent (all optional). `validate ecus` is an alias for `validate pids`. **`validate pids` also errors on a duplicate *shipped* parameter name across PIDs** (a device signal-name collision — each `active`+`enabled` param becomes a distinct device signal, so names must be unique; caught here rather than only at `wican autopid write`). `validate captures` also emits **soft warnings** for (a) session `vehicle_states` outside the profile's `vehicle_states.yaml` vocabulary (free text still accepted), (b) **echo mismatches** — a stored capture whose payload's SID/PID/DID echo doesn't match its recorded `pid` (a stale/misfiled frame, e.g. a `6101…` payload filed under a `2102` request; the expected Hyundai/Kia `-1` identity-DID offset is tolerated only when the profile declares the `hk_f1xx_minus_one` quirk), (c) **non-hex payloads** — a capture payload that isn't a valid UDS byte string (an ELM327 status string like `NO DATA`, free text, or a mixed hex+ASCII transcription), and (d) **untimed payload captures** — a `payload` (time-series) capture with no usable `time`, which is excluded from time-aligned cross-signal analysis (`scan_results` captures are exempt; existing untimed rows are grandfathered), and (e) **degraded-transport sessions** — a session whose recorded `quality` shows dropped/stale ISO-TP frames (`drop`/`stale` > 0), flagging that its multi-frame payloads may be unreliable (non-answer categories no_data/bus/decode don't warn — nothing was stored). Pass `--strict` to promote the untimed-payload warning to an error (CI / new-data gate).
- **`profiles/ioniq-2017/captures/`** — Raw UDS response payloads, split by date (e.g. `2026-04-19.json`). Stored as **JSON** (`captures/YYYY-MM-DD.json`) — parses ~60x faster than YAML, the dominant cost of every history-consuming command). The read/write seam is `canlib/capture_io.py`; there is **no YAML fallback** — a profile created before the cutover fails fast with an actionable error and is converted once via **`canair captures migrate`** (`--dry-run` to preview). These files are **append-only session logs**, so same-day recordings from two machines merge via canair's git merge driver (`canair captures merge-driver`, `.gitattributes` rule `profiles/*/captures/*.json merge=canair-captures`) — run **`canair captures merge-driver --install`** once per clone to register it (until then git just falls back to conflict markers). Schema in `canlib/schema/captures_schema.json` (tool-owned, format-agnostic — validates the parsed structure; the human companion is `docs/concepts/captures-and-states.md`), with matching Python `TypedDict`s in `canlib/capture_types.py` (`CaptureFile`/`CaptureSession`/`CaptureRecord`/`ScanResults`/`RespondingEntry`/`Quality`) that the builders/IO are typed against (enforced by `ty`). Each capture's `rx` field is the ECU CAN **response** address (RX = request TX + 8, e.g. `0x7EC`; `broadcast` for multi-ECU scans) — it was renamed from `ecu` → `rx`; read it via `capture_io.capture_rx` (tolerates the legacy key) and rename old files with `canair captures migrate-rx`. Validate with `canair validate captures`. **NEVER hand-write or edit these files.** Record device reads via `canair query … --save` with `--label`/`--state`/`--notes` (non-interactive), e.g. `canair query "query MCU" "query VCU:2101" --wican vpn --save --label "…" --state "ready, parked" --notes "…"`. `--save` works with `canair monitor`/`scan`/`raw`/`discover`, positional query/raw steps. **When there's no device on hand** (e.g. a reading pasted from a forum/issue), onboard it with `canair import uds ECU:PID=PAYLOAD --label … --state …` — same machinery, no live bus. Saves are **journaled** to `captures/.journal/` (JSONL) as they stream and reconciled into the per-day JSON on exit; recover a killed session's leftovers with `canair captures uds --recover`. For edits/removals use `canair captures uds --delete <query>` (`--dry-run`/`--yes`) or the `canlib.captures` helpers (`set_capture_note`, `delete_capture`). **Truncated multi-frame reads are rejected at capture time** — `parse_uds_response` compares the reassembled length to the ISO-TP First-Frame declared length (exposed by the ELM327 terminal as a bare `NNN` line) and drops a short read (`truncated ISO-TP: got N, declared M`) so a misaligned payload is never saved; the check is generic (no per-PID length table). **After adding captures, run `canair captures uds --summary` to check for new patterns.**
- **`profiles/ioniq-2017/vehicle_states.yaml`** — Canonical, ordered vehicle operating states (**UPPERCASE** controlled vocabulary — `SLEEP/PLUGGED/ACC/ACC2/READY/CHARGING` + composites + the `ALL` meta-token), each with an optional `when:` predicate over decoded `ECU.PARAM` values used to **auto-suggest** a capture's `vehicle_states` (see `canlib/states.py`). Inspect/edit with **`canair states`** (never hand-edit; surgical editor in `canlib/states_edit.py`). References to states in `ecus/` are written as **inline flow lists** (`vehicle_states: [SLEEP, PLUGGED]`). Schema `canlib/schema/states_schema.yaml`; validate with `canair validate states`. `canair validate captures`/`validate pids` compare tokens **case-insensitively** and soft-warn / error on values outside the vocabulary. New profiles are scaffolded with a starter `vehicle_states.yaml`. Migrate a legacy lowercase/block-style profile with `scripts/migrate_states_uppercase.py`.
- **`profiles/ioniq-2017/can_buses.yaml`** — Per-profile physical CAN bus segment vocabulary: each bare code (`B-CAN`/`P-CAN`/`C-CAN`/`MM-CAN`/`H-CAN`/`D-CAN`/`ALL` for Hyundai/Kia) maps to a human `name` + `description` + an optional `bitrate` (segment bus speed in bit/s, e.g. `500000`), shown by `canair bus`/`canair ecu`. Bus naming is **vendor-specific** (Ford `HS`/`MS`; BMW `PT-CAN`/`K-CAN`), so it lives per profile, not in a global enum. ECU `can_bus:` lists are written in the readable flow form (`can_bus: [B-CAN, P-CAN]`) by `set-can-bus`. Schema `canlib/schema/can_buses_schema.yaml`; validate with `canair validate can-buses` (errors on a non-positive-integer `bitrate`); loader `canlib/can_buses.py` (`load_can_buses`/`allowed_can_buses`/`bus_names`; `BusDef.bitrate`). `canair pids set-can-bus` accepts only declared codes and `validate pids` errors on an out-of-vocabulary value. New profiles are scaffolded with a starter `can_buses.yaml` (`All` + commented placeholders). (A legacy bare-list form is still accepted.)
- **`profiles/<name>/signals/` and `profiles/<name>/captures/can/`** — the raw-CAN broadcast domain (in progress, `plans/2026-07-24-raw-can-analysis.md`), both optional/absent today. `signals/<bus>.yaml` holds DBC-compatible **linear** broadcast signal maps keyed by arbitration ID (schema `canlib/schema/signals_schema.yaml`; `canair validate signals`); `captures/can/` holds imported raw frame logs natively (`.blf`/`.asc`/`.csv`) indexed by `captures/can/index.yaml` (schema `canlib/schema/can_index_schema.json`; `canair validate can`). Distinct from domain-A diagnostic `captures/*.json` + freeform-WiCAN-`expression` PID params. Profile path accessors: `Profile.signals_dir` / `.can_dir` / `.can_index_file`. **Storage/licensing policy** (`.gitattributes` + docs/concepts/broadcast-frames.md → "Storing raw-CAN logs"): a profile's **own** `captures/can/` logs are committed **fully** — via **Git LFS** when large (`.gitattributes` tracks `*.blf`/`*.asc`/`*.trc` + `profiles/*/captures/can/**`; `tests/fixtures/**` is explicitly excluded so the tiny excerpts stay plain, diffable git). **Third-party** logs are committed only when their license permits redistribution (recorded alongside); **unlicensed** corpora (the uhi22 Ioniq-28 data) stay **fetch-on-demand** in gitignored `references/can/` (`scripts/fetch_can_corpus.py`) + a minimal fair-use excerpt in `tests/fixtures/can/`. LFS is storage only — it grants no redistribution right, so it never changes the license question. Contributors need `git lfs install`.
- **`profiles/ioniq-2017/references/`** — External reference material (other-vehicle logs, spreadsheets, SavvyCAN exports, charge-curve data) used to cross-reference RE work. Distinct from the per-ECU `research:` backlog sections inside `ecus/` (surfaced by `canair research`).
- **`profiles/ioniq-2017/profile.yaml`** — Profile-wide settings: `car_model`, `init` (ELM327 AT string, `wican-ws` transport only), `response_timeout_ms`, `multi_did_batching`, `multi_did_max` (cap on DIDs combined per multi-DID request, default 3; per-ECU `multi_did_max` overrides), optional `can_bitrate` (vehicle bus speed in bit/s; precedence config `transport.bitrate` > profile `can_bitrate` > device config > 500000), optional `addressing:` block (CAN diagnostic addressing rule — `mode:` selects `normal_11bit` (default) / `normal_29bit` / `normal_fixed_29bit` (the ISO `0x18DA{target}{tester}` convention, Ford/VAG/etc.; RX derived by byte-swap, no offset) / `normal_extended_11bit` (ISO-TP extended/mixed 11-bit — an 11-bit header plus a per-ECU `target_address` byte in the payload, BMW `0x6F1` / PSA) / `extended_29bit`; `rx_offset:` sets 11-bit response = `tx_id + rx_offset`, default `0x08`, e.g. `0x80` for XPeng `0x704`→`0x784` (may be negative — PSA/Stellantis `-0x20`); the extended-mode ISO-TP extension bytes `target_address`/`source_address` (tester, default `0xF1`); a per-ECU flow-control arbitration override `addressing.fc_id` (functional-TX / physical-RX ECUs, e.g. Renault/Mitsubishi — FC goes to the physical id, not the functional TX); a single ECU overrides with its own `rx_id` and/or a per-ECU `addressing.mode`; resolver in `canlib/addressing.py` — `resolve_mode`/`resolve_rx`/`resolve_ecu_address`/`build_isotp_address` (the `EcuAddress` bundle), with the FC-address override in `canlib/transport/isotp_stack.py`), optional `isotp:` block (client-side ISO-TP tuning for `slcan-tcp` — `tx_padding`/`blocksize`/`stmin`/`rx_flowcontrol_timeout`/`rx_consecutive_frame_timeout`/`can_fd`/`tx_data_length`, defaults in `canlib/transport/isotp_params.py`; the padding byte drives multi-DID split/strip via `resolve_tx_padding`), optional `quirks:` list (make-specific behavior toggles the profile opts into — known: `hk_f1xx_minus_one`, the Hyundai/Kia identity-DID `-1` offset `22F188`→`62F187`; `skm_wakeup`, which enables the Ioniq SKM relay-wake command (`skm-wake`); resolver `canlib/quirks.py`), and DTC `failure_types:`. Only `car_model`+`init` are required; `canair validate` type-checks the rest.
- **`templates/`** (repo root) — Scaffold templates used by `canair profile create`: `profile.yaml.tmpl`, `vehicle_states.yaml.tmpl`, `can_buses.yaml.tmpl`. Placeholders use `string.Template` (`$car_model`, `$init`) so literal braces in YAML/comments never need escaping. Resolved via `TEMPLATES_DIR = SCRIPT_DIR / "templates"` (`canlib/constants.py`) and rendered by `_render_template()` in `canlib/commands/profile.py`. **Shipped in the wheel** via `pyproject.toml`'s `[tool.hatch.build.targets.wheel.force-include]` (`"templates" = "templates"`, alongside `profiles`) so `uv tool install` copies can still scaffold. Edit the scaffold output by editing these files, not Python strings.
- **`canair pids`** edits the `ecus/` files (parameters + research); ECU identity/scan_log are written by `canair discover --register` / `canair identity`.
- (There is no longer a top-level `ecus.yaml` or `dtc.yaml` — both were folded into the per-ECU `ecus/` files.)
- **`canair bix`** — Byte index converter: WiCAN ↔ ISO-TP ↔ Torque ↔ bix. A bare `canair bix` (no args) prints a **guided overview** — a plain-language legend for each notation and the `PCI`/`FF`/`CF`/`SID`/`PID`/`DID` Role labels, plus a compact 2-frame table (B00–B15) and next-step hints. Use `canair bix w9` or `canair bix E` for quick lookups, `--table` for the full table (**grouped by CAN frame** — `── Frame N ──` dividers between 8-byte blocks + a `Role` column marking the `FF PCI`/`CF PCI` framing and `SID`/`PID`/`DID` header bytes, so the raw CAN frame boundaries are visible; the legend is printed above it too; frame dividers/PCI rows are color-highlighted on a TTY, plain when piped). **By default `--table` and `--annotate` show only WiCAN + ISO-TP + Role** (the notations expressions use); the **Torque letter (`--torque`)** and **OBDb bix (`--obdb`)** columns are now **separate opt-in flags** (no longer aliases — they're different notations) for cross-referencing third-party PID sheets. Torque notation is used by the Torque app, **Car Scanner**, and similar OBD apps. **A single-index lookup (`canair bix w9`/`b32`/`E`) also reports the CAN frame the byte lands in** (e.g. `CAN frame: 1 (B08–B15)`). **`--annotate HEX` (`-a`)** maps a raw UDS response payload to a table with WiCAN Bnn, ISO-TP index, Torque letter, bix, and role per byte (multi-frame payloads get the same `── Frame N ──` boundary markers). It is **length-aware** — single-frame (≤7-byte) responses have one PCI byte at B00 (SID at B01), multi-frame responses two FF PCI bytes at B00/B01, and the ISO-TP/Torque/bix columns follow the *actual* frame layout (they no longer assume multi-frame, which was off-by-one for single-frame payloads). The **Torque column is Torque 1 (`-1`, 21xx PIDs) or Torque 2 (`-2`, 22xxxx DIDs)** — with `--torque`, annotate names the active variant so it's clear the Torque/OBDb mapping isn't fixed (it counts from the first UDS data byte, after SID + subfunction). The hex may be a no-space blob (`62B004…`), a quoted space-separated string (`"62 B0 04 …"`), or **unquoted space-separated bytes** (`-a 62 B0 04 …`) — all equivalent. Put the mode flag `-1` (21xx, default) / `-2` (22xxxx) **before** the bytes. **`--annotate` expects the reassembled UDS payload (SID-first, ISO-TP PCI stripped — what the transport/captures return); pass `--raw`/`--frame` to annotate an already-framed CAN payload (PCI present, e.g. straight off the bus) as-is.** It reliably warns when the input's first byte contradicts the mode — UDS response SIDs (`0x40`–`0x7F`) and PCI first-bytes (`0x00`–`0x3F`) are disjoint — so a raw frame fed without `--raw` (or a PCI-stripped payload with `--raw`) is caught, not silently mislabelled; a Flow-Control/invalid frame under `--raw` errors. Add **`--ecu ECU --pid PID`** to overlay which defined parameter (and bit `[NAME:k]`) maps each byte and flag `unmapped` data bytes — the fastest way to spot a wrong byte offset in an expression (how the BC05 `B09`→`B10` bug was caught).

## WiCAN Access

Device addresses are configured in `~/.config/canair/config.yaml` (a legacy repo-root `config.yaml` is still read for back-compat; both gitignored). Copy from `config.example.yaml`:

```yaml
wican_addresses:
  home: "10.0.2.86"       # Device on local LAN
  vpn: "192.168.3.2"      # Device via VPN
default_wican: home
```

All CLI tools use `--wican home|vpn|<ip>` to select the target. Without `config.yaml`, falls back to `192.168.80.1` (WiCAN AP mode).

- WebSocket terminal: `ws://<ip>/ws` (send `{"ws_mode": "terminal", "terminal_type": "elm327"}`)
