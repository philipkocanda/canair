# Hyundai Ioniq 2017 — CAN Reverse Engineering

For reference, the WiCAN firmware is checked out in the `wican-fw/` directory (gitignored; pull if you need to reference the latest version).

## Running the CLI — ALWAYS use `uv run canair` from the repo root

**Every `canair` invocation in this repo MUST be run as `uv run canair …` from the project root (`/Users/philip/projects/canair`).** Do NOT call a bare `canair` (a globally installed `uv tool install .` copy). Running bare `canair`:

- may execute **stale code** from a previous install instead of the current working tree, and
- may resolve a **different vehicle profile** (wrong `--profiles-dir` / `default_profile`) than the repo-bundled `profiles/ioniq-2017/`.

Running `uv run canair …` from the repo root guarantees the latest repo code and the expected in-repo profile. Throughout this file and the skills, wherever an example is written as `canair …`, execute it as `uv run canair …` (use the `workdir` of the repo root; never `cd`-hop away from it).

## Prefer canair's built-in tooling — do not hand-roll

For **all** querying, capturing, analysis, and reverse-engineering, use the dedicated `canair` subcommands documented below rather than raw sockets, ad-hoc scripts, or hand-editing YAML:

- **Query/read the device** with `canair query` / `scan` / `discover` / `io` / `routines` (use `raw` only as a last resort).
- **Analyze historical data** with `canair captures`, `canair decode`, `canair correlate`, `canair hunt`, `canair investigate`, `canair coverage`, `canair research`.
- **Edit definitions** with `canair pids` (surgical, validated) — not by hand-editing `ecus/` YAML.
- **Always pass `--save`** (with `--label`, `--state`, `--notes`) when reading from the device so every payload is recorded to `captures/`. See **Key Files → captures** below for the full flag set and examples. `--save` works with `query`/`scan`/`raw`/`discover`, positional query/raw steps, and `--monitor`. Saves are **journaled** (a write-ahead log under `captures/.journal/`) and reconciled into the dated capture file on exit, so a killed/crashed/disconnected session is never lost — recover leftovers with **`canair captures uds --recover`** (`--discard` to drop them). In `--monitor` press **`s`** to set/edit the label/state/notes of the **current** session live (the save modal names which segment it labels), or **`n`** to **close the current segment and start a fresh one** (each segment reconciles to its own capture file, so one run yields several labelled sessions); an active `--save` recording shows a blinking **`● REC`** in the status line. The **vehicle state is auto-suggested** from decoded PID values via the profile's `states.yaml` (see `canair validate states`). Repeated non-`--save` on-demand saves only write payloads seen **since the last save** (no duplicates).

## Tools

> Reverse-engineering a new PID/DID end-to-end (discover → capture → analyze → define → verify) is documented in the **reverse-engineer-signal** skill; general project/device context is in the **ioniq-reverse-engineering** skill.

All functionality is exposed through a single installable CLI, **`canair`** — but in this repo you **always** invoke it as **`uv run canair …` from the repo root** (see "Running the CLI" above). `uv tool install .` exists for end users, not for agents working in the tree.

- **`canair wican`** — Build/sync the WiCAN device's AutoPID profile from the active bundle's `ecus/`. A bare `canair wican` prints help (writes nothing). Subcommands: `autopid write` (generate JSON to `out/`), `autopid upload`/`download`/`diff` (device sync, Pro-only), `autopid stats`, and `mode show`/`mode set MODE` (device protocol switch, Pro-only)
- **`canair query`** — Custom CAN/UDS requests over the configured transport (raw `slcan-tcp` by default, or the `wican-ws` WebSocket ELM327 terminal). **Prefer positional query steps** like `canair query BMS:2101` (multi mini-language — handles sessions, wake, keepalives; a bare selector like `BMS:2101` is treated as a query step). **Bind each PID to its ECU with a colon (`IGPM:22BC07`), never a space** — in a query step a space separates *independent ECU selectors*, so `"query IGPM 22BC07"` means "all of IGPM plus a bogus ECU 22BC07" and is rejected. Use `canair query --param`/`canair query BMS` for simple single-ECU reads, `canair scan range` for discovery. Companions: `canair discover`, `canair io`, `canair routines`, `canair identity` (standard UDS identity DIDs — F100/F18x/F190/F19x), `canair scan routines` (probe requestRoutineResults across a range — auto-selects UDS 0x31 SF03 or KWP2000 0x33 RequestRoutineResultsByLocalIdentifier by `id_protocol`, so it never blind-sends 0x31 StartRoutine to a KWP2000 ECU; hits saved to `ecus/<ecu>.yaml` `routines:`), `canair scan iocontrol` (probe returnControlToECU across a DID/LID range — auto-selects UDS 0x2F or KWP2000 0x30 by `id_protocol`; hits saved to `iocontrol_discoveries:`), `canair raw` (**last resort** — hex dump only, no decoding), `canair repl` (interactive). `--verbose` is for debugging canair itself, not normal use. **TesterPresent keepalives are automatic and there is no `tester-present` command/flag** — opening a session (a `session <ECU>` query step or any command's `--session`) keeps it alive with idle-aware `3E00` (real traffic resets the S3 timer). `3E00` (SID `0x3E`) is shared by UDS and KWP2000, so it is sent identically for both protocols; send one by hand via a query step (`canair query BMS:3E00`), or use the `repl`'s `!tester` for a manual loop. **Use `--reboot` to restore AutoPID after session** (WebSocket terminal overrides AutoPID mode). Dependencies: `websockets`, `pyyaml`, `requests` (optional, for reboot).
- **`canair captures`** — Query captured data, split into two domain kinds (the `uds`/`can` naming spine). **`canair captures uds`** (domain A — diagnostic UDS payloads) takes a QUERY (mini-language, like the other tools): `BMS 2102` (ECU + PID, most useful), `"BMS:2102,2103"` (several PIDs), `BMS` (all PIDs for an ECU), or a quoted cross-ECU `"VCU:2101 BMS:2101"`. Add `--diff` for the byte-level diff view or `--step` to interactively step through captures. Standalone modes (no QUERY): `--summary` (stats per ECU/date), `--sessions`/`-n` (session **table of contents** — date/time-span/state/label/session-notes/ECUs + distinct capture-notes per session, no payloads; the fast "what's in the captures?" index, `--json` for machine output), `--latest [ECU]` (most recent payload per PID), `--recover` (reconcile orphaned journals from a killed/crashed `--save` session into capture files; `--discard` to delete them unsaved). Any mode can be scoped to a date range with `--since`/`--until` (inclusive, `YYYY-MM-DD`) or `--date` (single day), and/or by `--state SUBSTR`/`--label SUBSTR` (case-insensitive substring of the session state/label). **`canair captures can`** (domain B) lists imported raw broadcast-CAN frame logs from `captures/can/index.yaml` — file/format/frames/IDs per log (`--json` for machine output). A bare `canair captures BMS 2102` (or any of the `--summary`/`--sessions`/… flags) is shorthand for `canair captures uds …` (via `_GROUP_DEFAULTS` in `cli.py`, like `scan`/`ecu`).
- **`canair import uds`** — Device-free UDS capture import (domain A; the `uds` kind of `canair import`): record an externally-provided UDS payload (pasted from a forum/issue, or read on another tool) into the active profile's `captures/` through the same machinery as a live `--save`, so it's indistinguishable from a device-recorded capture and immediately queryable by `decode`/`captures`/`coverage`. Each capture is `ECU:PID=PAYLOAD` (ECU short name or hex TX id; PID/DID; reassembled UDS payload, SID-first, PCI stripped); pass several to group them into one session. Metadata via `--label` (required), `--state` (repeatable, vehicle power state), `--notes`/`--capture-note`, `--time`, `--date` (default today; sets the target file). Resolves ECU→RX, rejects non-hex payloads, and **warns on SID/DID echo mismatch** (a payload filed under the wrong PID) without blocking. `--json` for machine output. This is how community-contributed readings (no device on hand) are onboarded — never hand-write `captures/`. (The domain-B ingest counterparts are `import can` / `import dbc` — see `canair import` below.)
- **`canair decode`** — Parameter/value-centric decoding: applies WiCAN expressions to all historical captures. **Default `canair decode BMS 2101` shows each param's value range** across captures (payload/byte-diff views live in `canair captures`). Modes: `--param` (filter), `--compact` (one aligned row per capture — param names in a single header, `[state]` divider only when the session state changes, time-only rows, right-aligned value columns; add `--changes-only`/`-c` to drop rows unchanged from the previous one, collapsing stationary runs), `--stats` (n/distinct/mean/median/stdev per param; add `--group-by state` for per-drive-segment stats in one shot), `--corr PARAM` (Pearson correlation of every param vs a reference — **`PARAM` may be a local name OR a cross-signal `ECU:PID:PARAM`/`ECU:PID:EXPR`**, e.g. `--corr ESC:22C101:REAL_SPEED_KMH`, time-aligned by nearest timestamp; add `--corr-transform delta|abs|cumsum|normalize` to test level-vs-rate, `--method pearson|spearman` to pick the coefficient (spearman = rank, catches monotone-but-nonlinear/quantized/saturating links; **`cramers_v`/`mutual_info` treat each value as a nominal category — for enum/mode/flag references where numeric spacing is meaningless**), `--join-tol SECONDS` to widen the join), `--discriminate state` (rank params by how cleanly they separate across power states — an F = between/within variance ratio for numeric params, **Cramér's V for typed enum/bitmask params** — that surfaces thermal/mode/relay signals a driving correlation misses; add `--bytes` to also rank every varying raw byte and `--bits` every toggling bit, no `--try` needed), `--find-mirrors` (`--bits` for bit-level: report byte/bit positions exactly equal across all captures — redundant status mirrors / unit-variants), `--plot` (interactive signal explorer: sweep ImHex-style byte interpretations `u8/i16/f32/…`×endianness and params, plot across captures, apply transforms `delta/abs/normalize/…`, zoom/pan the x-axis, overlay a `--corr` signal, show the visible date/time range, list the backing captures in a modal (`i`), flag bytes already mapped by a defined param, and read off the equivalent WiCAN expression), `--try "NAME[:unit]=EXPR"` (test a candidate expression against captures **without** editing YAML; works even for a not-yet-defined PID), `--verified`/`--unverified`, `--json`. **Scope which captures are considered** (shared with `canair captures`): `--since`/`--until`/`--date` (inclusive `YYYY-MM-DD`), `--state SUBSTR`/`--label SUBSTR` (case-insensitive substring of the session state/label — the natural unit of drive analysis, e.g. `--state driving`), and `--first N`/`--last N` (chronological slice). Example drive analysis: `canair decode MCU 2102 --stats --group-by state --state driving`.
- **`canair correlate`** — Cross-signal correlation across a whole drive/session: time-aligns every decoded param (and, with `--bytes`, every varying raw byte; `--bits` for toggling bits) across all co-polled ECU/PIDs in scope and ranks the strongest cross-signal relationships — the "show me every strong relationship in this drive" entry point (how the AAF-speed / MCU-temp finds were made). Optional `ECU[:PID]` selector to restrict signals. Modes: default ranked pair list (cross-PID/ECU only unless `--include-intra`; near-perfectly-correlated |r|≥0.995 groups collapse to one summary line unless `--no-cluster`), `--against ECU:PID:PARAM` (rank every signal vs one reference — drops the trivial self-match unless `--include-self`; `--promote NAME` writes the top raw-byte hit into `ecus/` as an enabled unverified candidate; `--lag-scan N` reports the apparent lead/lag that maximises |r|; `--gate '[SIGNAL] OP VALUE'` restricts to a regime e.g. `'> 0'` = while-moving), `--overlap` (report which ECU:PID pairs actually share time-aligned samples in scope — pick a viable `--against` reference), **`--find-mirrors` (report byte/bit positions that are time-aligned *equal* ACROSS co-polled ECU/PIDs — e.g. a door bit in IGPM mirrored in BCM; add `--bits` for bit-level; the cross-ECU companion to `decode --find-mirrors`, which is single-PID. Beware small `--min-n`: noisy low bits can match by chance)**, `--matrix`, `--json`; `--method pearson|spearman|cramers_v|mutual_info` (the last two rank by *categorical* association — for mode/flag/enum bytes); `--transform delta|abs|…` (transform the `--against` reference); thresholds `--min-r` (default 0.6) / `--min-n` (default 15) / `--top`; `--join-tol SECONDS`. Same scope flags as `decode`. **Warns when the scope includes `keep:unique` sessions** (rising-edge-only data) and caveats `--transform delta|cumsum` / `--lag-scan` on it. **Domain B — `canair correlate can FILE`** correlates a raw broadcast-CAN frame log's per-byte series instead of diagnostic captures — reads the native log (`--can-format auto` by extension), builds `0xID:rN` byte series (`--bits` for `0xID:rN.k`), and runs the *same* ranked/`--against`/cluster core (cross-arbitration-ID by default; `--include-intra` for same-ID; `--id 0x220,0x386` to restrict). **`--find-mirrors` works here too** — reports byte/bit positions time-aligned *equal* ACROSS arbitration IDs (a signal broadcast on two IDs, e.g. wheel speed on `0x386` and `0x331`); add `--bits` for bit-level. Frame labels render as-is (raw-CAN space, no WiCAN/PCI). Everything above is the default **`correlate uds`** kind — a bare `canair correlate …` is shorthand for it (via `_GROUP_DEFAULTS`); the diagnostic (WiCAN `Bn`) path is unchanged.
- **`canair hunt`** — "Which byte on ECU:PID *is* this known signal?" Sweeps every byte offset × interpretation (`u8/i16/f32/…` × endianness) on the target PID, time-aligns each against `--against ECU:PID:PARAM` (a known signal on another ECU/PID), and ranks by |Pearson r| — reporting the best **linear fit** (`y=m·x+c`) and a **physical-unit guess** (`raw−40 °C`, `×1.609 mph→km/h`, …) for each hit. Collapses to the best interpretation per byte offset by default (`--all-interps` to expand). `--transform delta|abs|…` hunts the byte that tracks the reference's *rate* (e.g. torque vs acceleration); `--method pearson|spearman`. `--promote NAME` writes the top hit's expression straight into `ecus/` as an enabled, unverified candidate param (via `canair pids upsert-param`) with the correlation evidence auto-filled into `notes`. `--json`, `--top`, `--min-n`, `--join-tol`; same scope flags. **Domain B: `canair hunt can FILE --id 0xID --against 0xREFID:rN`** hunts on a raw broadcast-CAN frame log instead — sweeps every byte/interpretation of one arbitration ID's frames vs a reference frame byte in the same log (raw-CAN `rN` labels, no PCI; `--promote` not supported for frames — those are defined in `signals/`, Stage 4). Everything above is the default **`hunt uds`** kind (a bare `canair hunt AAF 2181 --against …` is shorthand for it); the diagnostic (WiCAN) path is unchanged.
- **`canair investigate`** — One-shot "tell me everything about this PID". For every varying data byte of `ECU PID`, reports in one ranked table: whether a param already **maps** it, its **state-discriminability** F, and its strongest **co-polled cross-signal anchor** (r + linear fit + unit guess). Bundles the manual `coverage → discriminate → correlate → hunt` loop into a single call — the "point it at an unknown PID" entry point. **`--bits`** also ranks individual toggling bits (`Bn:k`) — the body/comfort-ECU finder; a body PID with no co-polled anchor is ranked by state separation (no more misleading "no varying bytes"). **`--events`** switches to the bit/byte **edge timeline**: every rising/falling transition with its timestamp and value, aligned to the nearest capture note (the narrated event log) — the fastest way to decode event-driven captures (door/lock/hood). **`--events --field NAME`** collapses a single typed param (enum/bitmask/date/struct) into one logical signal — emitting one transition per change of its *decoded* value (e.g. `fanMAX (45) → fan1 (40)`) instead of scattered per-byte edges. `--all` (include mapped bytes), `--min-r`/`--min-n`/`--join-tol`, `--json`; same scope flags. **Warns on `keep:unique` scope** (rising-edge-only data).
- **`canair research`** — Report the open reverse-engineering backlog from the per-ECU `research:` sections in the profile's `ecus/`. Complements `canair coverage` (undecoded *bytes*) by surfacing *planned* work (scans/decodes/verifies). Modes: `canair research` (all open, priority-sorted), `--summary` (counts by status/type/priority/ECU), `--ecu`, `--type scan|decode|verify|iocontrol_scan`, `--status`, `--priority P1|P2|P3`, `--states acc|ready|…` (was `--prerequisite`), `--all` (include done), `--json`. Use as the "what should I RE next?" entry point.
- **`canair coverage`** — Audit PID definitions for decoding gaps. Cross-references each PID's parameter expressions against its longest captured payload and reports **UNMAPPED** data bytes, incomplete **BITS** (bytes read bit-by-bit with undecoded bits left), and **NO CAPTURE** PIDs (params defined but nothing captured). Modes: `canair coverage` (all), `canair coverage IGPM [22BC03]` (filter), `--bitfields`, `--unmapped`, `--no-capture`, `--all` (include fully-mapped), `--json`. Run after adding params/captures to spot what still needs decoding.
- **`--notation {wican,isotp,torque,bix}` (shared display flag)** — `correlate`, `hunt`, `investigate`, `coverage`, and `decode` (`--discriminate`/`--find-mirrors`) render raw-byte labels as WiCAN `Bnn` by default; `--notation` re-renders them as ISO-TP (`iN`), Torque letters, or bix for reading/cross-referencing. **Display only** — named params are untouched, and `--json`/`--promote` always emit the canonical WiCAN expression. Persist a default with `canair config set display.byte_notation NAME`. Internally a byte is modelled in ISO-TP space (`canlib/notation.py::ByteRef`); WiCAN/Torque/bix are derived views (the byte-notation de-conflation — `plans/2026-07-24-byte-notation-phase2-isotp-canonical.md`).
- **`canair pids`** — Safely add/update the profile's `ecus/` **parameters** and **research** entries from the CLI (surgical, comment-preserving; each edit is YAML-reparsed and schema-validated via `canair validate pids`, and auto-reverted on failure). Subcommands: `upsert-param ECU PID NAME EXPR [--unit --min --max --source --notes --verified/--unverified --type enum|bitmask|ascii|date|bcd --value RAW=LABEL --bit INDEX=LABEL …]` (**typed/multi-modal decoding**: `--type` + repeatable `--value`/`--bit` `KEY=LABEL` pairs define an enum/bitmask; passing only `--value`/`--bit` infers the type. The WiCAN `expression` stays the pure-float device value; the type is a *parallel* decoding rendered by `canlib/decode_value.py`. `ascii`/`date`/`struct` render text/date/record; `struct`'s ordered `fields:` are authored in YAML today), `rename-param ECU PID OLD NEW` (rename a param key; fields/formatting preserved), `rm-param ECU PID NAME` (remove a param), `rename-pid ECU OLD NEW` (rename a PID key, e.g. `B002`→`22B002`; status/params/formatting preserved), `rm-pid ECU PID` (remove a whole PID — drops the `pids:` section entirely if it was the last PID, leaving an identity-only ECU), `add-research ECU --type --target --status [--priority --prereq …]`, `set-status ECU TARGET STATUS [--type]`, `set-pid-status ECU PID {active|draft|static|ignored}` (PID lifecycle), `set-identity ECU FIELD VALUE` (set a curated identity field, e.g. `notes`). Prefer this over hand-editing the rich per-ECU YAML.
- **`canair signals`** — The domain-B analogue of `canair pids`: view/edit the broadcast signal-definition sidecar `signals/<bus>.yaml` (arbitration ID → named **linear** signals: `start_bit`/`length`/`byte_order`/`scale`/`offset`/`min`/`max`/`unit`/`verified`). `canair signals` / `signals list [BUS]` (list; `--json`), `signals upsert BUS 0xID NAME --start-bit --length [--byte-order --scale --offset --min --max --unit --verified/--unverified --notes --msg-name --tx-ecu]`, `signals rm BUS 0xID NAME`. Surgical, comment-preserving, validated (`canair validate signals`) + auto-reverted (via `canlib/signals_edit.py`). Never hand-edit `signals/`. Distinct from `pids` (freeform WiCAN `expression` over `Bnn`); this is the DBC-compatible linear model for passively-broadcast frames. (The `signals/` **schema** also accepts the same typed-decode fields as PID params — `type`/`values`/`bits`, decoded by `canlib/decode_value.py` — for enum/bitmask broadcast signals; the `signals upsert` CLI flags to author them are a follow-up, so typed broadcast signals are authored in YAML for now.)
- **`canair config`** — View and manage user config (`~/.config/canair/config.yaml`): transport block, `wican_addresses`, `default_wican`, `default_profile`, `profiles_dir`. Subcommands: `show` (default — config file locations + effective settings + resolved transport + WiCAN address book; `--json`), `path` (print user config file path), `get KEY`, `set KEY VALUE` (dotted keys create nested mappings, e.g. `transport.type`, `wican_addresses.home`; int/bool coerced unless `--string`), `unset KEY`, `edit` (`$EDITOR`). Comment-preserving edits. Prefer this over hand-editing `config.yaml`.
- **`canair update`** — Update the CLI from its git-clone install. Locates the source clone (via uv's tool receipt `~/.local/share/uv/tools/canair/uv-receipt.toml`, falling back to the package repo root), reports current vs latest **released** version (GitHub Releases API) with a changelog link, then — after confirmation — runs `git pull --ff-only` + `uv tool install <clone> --reinstall`. `--check` reports only (no changes), `--yes/-y` skips the prompt (automation), `--json` for machine output. Refuses to touch a dirty clone (won't clobber contributor work) and degrades to printing manual commands when no clone/`uv` is found. Backed by `canlib/update_check.py`, which also drives the **automatic once-a-day background check**: interactive runs kick off a short-timeout, fully offline-safe daemon-thread fetch (any failure is silently ignored, never blocks or fails a command), cache it to `~/.config/canair/update_check.json`, and print a one-line "update available" notice on the next run (also surfaced in `canair status`). Disable with `check_for_updates: false` in config or the `CANAIR_NO_UPDATE_CHECK` env var.
- **`canair dtc`** — Read stored Diagnostic Trouble Codes (DTCs) for one ECU or `--all` (UDS `0x19` / KWP2000 `0x18`, auto-selected by `id_protocol`). Logs each scan to the profile's `dtc_log.yaml` (tag the entry with `--label` and the vehicle power state with `--state`, e.g. `--state 'plugged, charging'`) and reports what **changed** since the last scan (DTC *meanings* live per-ECU in each `ecus/<name>.yaml` `dtcs:` section; profile-wide `failure_types:` in `profile.yaml`); clear fault memory with `--clear` (`0x14`). Read-only unless `--clear` is passed.
- **`canair sniff`** — Passive CAN-bus sniffer (raw `slcan-tcp` backend **only** — asks to switch the device to `slcan` if needed). Live per-ID table (count/rate/last data/changed bytes) for discovering broadcast IDs the request/response path can't see; optional `.asc`/`.blf`/`.csv` frame logging via `--save`, plus `--filter`/`--listen-only`/`--duration`. Complements the active request/response tools which can't observe passive broadcasts.
- **`canair status`** — Read-only snapshot of the configured transport, device mode, and reachability: "what am I talking to, in what mode, is it usable?". Use before a session to confirm the device is in the expected protocol (`slcan` vs `auto_pid`).
- **`canair ecu`** — Inspect the profile's ECU registry (aggregated from the per-ECU `ecus/` files) and per-ECU stats (PID/param/verified counts, protocol, addresses) via `canair ecu` / `canair ecu <ECU>` (the `show` kind). **`canair ecu add TX [--name --description --id-protocol --notes --overwrite --dir]`** registers a new ECU offline (no device) — the counterpart to `canair discover --register` for seeding a known ECU into a blank profile; the write is validated + comment-preserving. Companion to `canair validate ecus`.
- **`canair import`** — Bring external CAN data into the active profile, split by the `uds`/`can`/`dbc` kind. **`import uds ECU:PID=PAYLOAD …`** is the domain-A device-free UDS capture import (documented above as its own entry). The domain-B (raw-CAN broadcast, `plans/2026-07-24-raw-can-analysis.md`) kinds: **`import can <FILE>`** reads a raw broadcast-CAN frame log (`.asc`/`.blf`/python-can `.csv`/candump `.log`/`.trc`/**SavvyCAN GVRET `.csv`**; `--format auto` by extension, `.csv` header-sniffed to tell GVRET from python-can CSV) via python-can's readers (GVRET via a built-in adapter), stores it **verbatim** in `captures/can/`, and appends a metadata entry (`frame_count`, `id_set`, `bitrate`, `date`, `label`, …) to `captures/can/index.yaml` — flags `--label`/`--state`/`--notes`/`--source`/`--bitrate`/`--date`/`--force`/`--json`. High-volume logs stay native (not exploded into `captures/*.yaml`). **`import dbc <FILE> [--bus --tx-ecu --ids --dry-run --json]`** imports a DBC's broadcast signal definitions into the profile's `signals/<bus>.yaml` (cantools, `strict=False` to tolerate real-world overlapping-signal DBCs; `--dry-run` previews). List imported logs with **`canair captures can`**. Module is `commands/import_.py` (`import` is a keyword); `NAME="import"`; the `uds` kind lives in `commands/import_uds.py`. Fetch the reference corpus with `scripts/fetch_can_corpus.py` (into gitignored `references/can/`).
- **`canair export`** — Export canair data to interchange formats. **`export dbc [--bus --verified-only -o FILE]`** writes the profile's `signals/` broadcast definitions to a DBC (cantools) for SavvyCAN/cabana/Wireshark; round-trips with `import dbc`. (Domain-A decoded-value CSV/JSON export is future work.)

### Profiles

Vehicle data lives in a **profile** bundle — a directory with `ecus/` (one file per ECU — the source of truth), `profile.yaml` (profile-wide settings), `captures/`, `references/`, `states.yaml`, and generated `out/`. The repo bundles one or more profiles under `profiles/` (the mature `profiles/ioniq-2017/` is the default/example; `profiles/ioniq-5-2022/` is an early seed). Selection precedence: `--profile NAME|PATH` (global flag, before the subcommand) > `CANAIR_PROFILE` env var > `default_profile` in config > single discovered profile (auto). Profiles are discovered from `--profiles-dir`, `$CANAIR_PROFILES_DIR`, `profiles_dir` in config, `~/.config/canair/profiles/` (user, uncommitted), and the repo's bundled `profiles/`; user profiles shadow bundled ones by name. Inspect with `canair profile list` / `show [NAME]` / `path [NAME]`; set the config default with `canair profile use NAME` (an alias for `canair config set default_profile NAME`, validated against discovered profiles — a bare `canair profile` list also hints this when no default is set). Scaffold a new vehicle with `canair profile create <name> --car-model "…"` (creates `profile.yaml`, empty `ecus/`, `captures/`, `out/` under `~/.config/canair/profiles/<name>` or `--path DIR`; `--set-default` to adopt it).

> **Pass `--profile NAME` explicitly on every *mutative/authoring* command** — anything that writes into a profile: `pids upsert-param`/`rename-*`/`rm-*`/`add-research`/`set-*`, `signals upsert`/`rm`, `import uds`/`import can`/`import dbc`, `discover --register`, `ecu add`, `wican autopid write`, and `--save` reads. Without `--profile` these write to the **active profile**, which is whatever `default_profile` (or `CANAIR_PROFILE`) resolves to — **not necessarily the car you mean**. This is exactly how Ioniq-28-derived `WHL_SPD11` signals once landed in `profiles/ioniq-5-2022/` instead of `ioniq-2017/` (a `signals upsert`/`import dbc` run with `default_profile: ioniq-5-2022` and no `--profile`; fixed in the git history). `canair signals`/`import` echo the target profile + full path on write — read it back to confirm. Read-only commands (`decode`/`correlate`/`hunt`/`captures`/`validate`/`ecu`…) are lower-stakes but still resolve the same way, so prefer explicit `--profile` there too when a specific car is intended.

## Key Files

- **`profiles/ioniq-2017/ecus/`** — SOURCE OF TRUTH, one file per ECU. Each `ecus/<name>.yaml` fully describes one ECU: `identity:` (name is the file's top key), `scan_log:` (probe history), `dtcs:` (DTC meanings), `pids:`, `iocontrol:`, `routines:`, `research:`. Identity-only modules (AMP/SRS) have no `pids:`. Validate with `canair validate pids` (alias `ecus`); `--stats` for counts
- **`canair validate`** — Schema validation with a positional target: `canair validate pids|captures|ecus|states|signals|can|all` (default `all`). Add `--stats` for a count summary (ECUs/PIDs/params/verified/research items). Schemas are tool-owned in `canlib/schema/` (`pids_schema.yaml` — covers the per-ECU files incl. identity/scan_log/dtcs, `captures_schema.json`, `states_schema.yaml`, `signals_schema.yaml` — broadcast signal maps, `can_index_schema.json` — raw-CAN log index). `validate signals` (broadcast `signals/<bus>.yaml` domain-B maps) and `validate can` (`captures/can/index.yaml` raw-CAN log index) gracefully skip when absent (both are optional, populated by the in-progress raw-CAN work — `plans/2026-07-24-raw-can-analysis.md`). `validate ecus` is an alias for `validate pids`. **`validate pids` also errors on a duplicate *shipped* parameter name across PIDs** (a device signal-name collision — each `active`+`enabled` param becomes a distinct device signal, so names must be unique; caught here rather than only at `wican autopid write`). `validate captures` also emits **soft warnings** for (a) session `vehicle_states` outside the profile's `states.yaml` vocabulary (free text still accepted), (b) **echo mismatches** — a stored capture whose payload's SID/PID/DID echo doesn't match its recorded `pid` (a stale/misfiled frame, e.g. a `6101…` payload filed under a `2102` request; the expected Hyundai/Kia `-1` identity-DID offset is tolerated), (c) **non-hex payloads** — a capture payload that isn't a valid UDS byte string (an ELM327 status string like `NO DATA`, free text, or a mixed hex+ASCII transcription), and (d) **untimed payload captures** — a `payload` (time-series) capture with no usable `time`, which is excluded from time-aligned cross-signal analysis (`scan_results` captures are exempt; existing untimed rows are grandfathered). Pass `--strict` to promote the untimed-payload warning to an error (CI / new-data gate).
- **`profiles/ioniq-2017/captures/`** — Raw UDS response payloads, split by date (e.g. `2026-04-19.yaml`). Schema in `captures/SCHEMA.yaml` (tool-owned: `canlib/schema/captures_schema.json`). Validate with `canair validate captures`. **NEVER hand-write or edit these YAML files.** Record device reads via `canair query … --save` with `--label`/`--state`/`--notes` (non-interactive), e.g. `canair query "query MCU" "query VCU:2101" --wican vpn --save --label "…" --state "ready, parked" --notes "…"`. `--save` works with `canair scan`/`raw`/`discover`, positional query/raw steps, and `--monitor`. **When there's no device on hand** (e.g. a reading pasted from a forum/issue), onboard it with `canair import uds ECU:PID=PAYLOAD --label … --state …` — same machinery, no live bus. Saves are **journaled** to `captures/.journal/` as they stream and reconciled on exit; recover a killed session's leftovers with `canair captures uds --recover`. For edits/removals use `canlib.captures` helpers (`set_capture_note`, `delete_capture`). **After adding captures, run `canair captures uds --summary` to check for new patterns.**
- **`profiles/ioniq-2017/states.yaml`** — Canonical, ordered vehicle operating states (`sleep/plugged/acc/acc2/ready/charging` + composites), each with an optional `when:` predicate over decoded `ECU.PARAM` values used to **auto-suggest** a capture's `vehicle_states` (see `canlib/states.py`). Schema `canlib/schema/states_schema.yaml`; validate with `canair validate states`. `canair validate captures` soft-warns on session vehicle_states with no token in this vocabulary. New profiles are scaffolded with a starter `states.yaml`.
- **`profiles/<name>/signals/` and `profiles/<name>/captures/can/`** — the raw-CAN broadcast domain (in progress, `plans/2026-07-24-raw-can-analysis.md`), both optional/absent today. `signals/<bus>.yaml` holds DBC-compatible **linear** broadcast signal maps keyed by arbitration ID (schema `canlib/schema/signals_schema.yaml`; `canair validate signals`); `captures/can/` holds imported raw frame logs natively (`.blf`/`.asc`/`.csv`) indexed by `captures/can/index.yaml` (schema `canlib/schema/can_index_schema.json`; `canair validate can`). Distinct from domain-A diagnostic `captures/*.yaml` + freeform-WiCAN-`expression` PID params. Profile path accessors: `Profile.signals_dir` / `.can_dir` / `.can_index_file`. **Storage/licensing policy** (`.gitattributes` + docs/concepts/broadcast-frames.md → "Storing raw-CAN logs"): a profile's **own** `captures/can/` logs are committed **fully** — via **Git LFS** when large (`.gitattributes` tracks `*.blf`/`*.asc`/`*.trc` + `profiles/*/captures/can/**`; `tests/fixtures/**` is explicitly excluded so the tiny excerpts stay plain, diffable git). **Third-party** logs are committed only when their license permits redistribution (recorded alongside); **unlicensed** corpora (the uhi22 Ioniq-28 data) stay **fetch-on-demand** in gitignored `references/can/` (`scripts/fetch_can_corpus.py`) + a minimal fair-use excerpt in `tests/fixtures/can/`. LFS is storage only — it grants no redistribution right, so it never changes the license question. Contributors need `git lfs install`.
- **`profiles/ioniq-2017/references/`** — External reference material (other-vehicle logs, spreadsheets, SavvyCAN exports, charge-curve data) used to cross-reference RE work. Distinct from the per-ECU `research:` backlog sections inside `ecus/` (surfaced by `canair research`).
- **`profiles/ioniq-2017/profile.yaml`** — Profile-wide settings: `car_model`, `init`, `response_timeout_ms`, `multi_did_batching`, and DTC `failure_types:`.
- **`canair pids`** edits the `ecus/` files (parameters + research); ECU identity/scan_log are written by `canair discover --register` / `canair identity`.
- (There is no longer a top-level `ecus.yaml` or `dtc.yaml` — both were folded into the per-ECU `ecus/` files.)
- **`canair bix`** — Byte index converter: WiCAN ↔ ISO-TP ↔ Torque ↔ bix. A bare `canair bix` (no args) prints a **guided overview** — a plain-language legend for each notation and the `PCI`/`FF`/`CF`/`SID`/`PID`/`DID` Role labels, plus a compact 2-frame table (B00–B15) and next-step hints. Use `canair bix w9` or `canair bix E` for quick lookups, `--table` for the full table (**grouped by CAN frame** — `── Frame N ──` dividers between 8-byte blocks + a `Role` column marking the `FF PCI`/`CF PCI` framing and `SID`/`PID`/`DID` header bytes, so the raw CAN frame boundaries are visible; the legend is printed above it too; frame dividers/PCI rows are color-highlighted on a TTY, plain when piped). **By default `--table` and `--annotate` show only WiCAN + ISO-TP + Role** (the notations expressions use); the **Torque letter (`--torque`)** and **OBDb bix (`--obdb`)** columns are now **separate opt-in flags** (no longer aliases — they're different notations) for cross-referencing third-party PID sheets. Torque notation is used by the Torque app, **Car Scanner**, and similar OBD apps. **A single-index lookup (`canair bix w9`/`b32`/`E`) also reports the CAN frame the byte lands in** (e.g. `CAN frame: 1 (B08–B15)`). **`--annotate HEX` (`-a`)** maps a raw UDS response payload to a table with WiCAN Bnn, ISO-TP index, Torque letter, bix, and role per byte (multi-frame payloads get the same `── Frame N ──` boundary markers). It is **length-aware** — single-frame (≤7-byte) responses have one PCI byte at B00 (SID at B01), multi-frame responses two FF PCI bytes at B00/B01, and the ISO-TP/Torque/bix columns follow the *actual* frame layout (they no longer assume multi-frame, which was off-by-one for single-frame payloads). The **Torque column is Torque 1 (`-1`, 21xx PIDs) or Torque 2 (`-2`, 22xxxx DIDs)** — with `--torque`, annotate names the active variant so it's clear the Torque/OBDb mapping isn't fixed (it counts from the first UDS data byte, after SID + subfunction). The hex may be a no-space blob (`62B004…`), a quoted space-separated string (`"62 B0 04 …"`), or **unquoted space-separated bytes** (`-a 62 B0 04 …`) — all equivalent. Put the mode flag `-1` (21xx, default) / `-2` (22xxxx) **before** the bytes. **`--annotate` expects the reassembled UDS payload (SID-first, ISO-TP PCI stripped — what the transport/captures return); pass `--raw`/`--frame` to annotate an already-framed CAN payload (PCI present, e.g. straight off the bus) as-is.** It reliably warns when the input's first byte contradicts the mode — UDS response SIDs (`0x40`–`0x7F`) and PCI first-bytes (`0x00`–`0x3F`) are disjoint — so a raw frame fed without `--raw` (or a PCI-stripped payload with `--raw`) is caught, not silently mislabelled; a Flow-Control/invalid frame under `--raw` errors. Add **`--ecu ECU --pid PID`** to overlay which defined parameter (and bit `[NAME:k]`) maps each byte and flag `unmapped` data bytes — the fastest way to spot a wrong byte offset in an expression (how the BC05 `B09`→`B10` bug was caught).

## WiCAN Access

Device addresses are configured in `~/.config/canair/config.yaml` (a legacy repo-root `config.yaml` is still read for back-compat; both gitignored). Copy from `config.example.yaml`:

```yaml
wican_addresses:
  home: "10.0.2.86"       # Device on local LAN
  vpn: "192.168.3.2"      # Device via VPN
default_wican: home
```

All CLI tools use `--wican home|vpn|<ip>` to select the target. Without `config.yaml`, falls back to `192.168.80.1` (WiCAN AP mode).

- WebSocket terminal: `ws://<ip>/ws` (send `{"ws_mode": "terminal", "terminal_type": "elm327"}`)
