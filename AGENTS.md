## Prefer canair's built-in tooling — do not hand-roll

For **all** querying, capturing, analysis, and reverse-engineering, use the dedicated `canair` subcommands documented below rather than raw sockets, ad-hoc scripts, or hand-editing YAML:

- **Query/read the device** with `canair read` (formerly `canair query`; `query` kept as an alias) / `monitor` / `scan` / `discover` / `io` / `routines` (use `raw` only as a last resort). `canair monitor` is the live, continuously-refreshing view (was `query --monitor`, now its own top-level command).
- **Analyze historical data** with `canair captures`, `canair decode`, `canair align`, `canair correlate`, `canair hunt`, `canair investigate`, `canair coverage`, `canair research`.
- **Edit definitions** with `canair pids` (surgical, validated) — not by hand-editing `ecus/` YAML.
- **Always pass `--save`** (with `--label`, `--state`, `--notes`) when reading from the device so every payload is recorded to `captures/`. See **Key Files → captures** below for the full flag set and examples. `--save` works with `read`/`monitor`/`scan`/`raw`/`discover`, positional query/raw steps. Saves are **journaled** (a write-ahead log under `captures/.journal/`) and reconciled into the dated capture file on exit, so a killed/crashed/disconnected session is never lost — recover leftovers with **`canair captures uds --recover`** (`--discard` to drop them). **Every write prints the full path of the capture file it landed in** (`→ Saved N capture(s) to /…/profiles/<car>/captures/YYYY-MM-DD.json`, formatted by `canlib/captures.py::saved_banner`) — read it back to confirm which profile got the data; a save made *inside* the `canair monitor` TUI (`s` without `--save`, or an `n` rotate) has its banner deferred and printed when the monitor exits, since Textual owns stdout while the app is up. In `canair monitor` press **`s`** to **label the current recording** (set/edit its label/state/notes — with `--save` active every payload is already journaled and written on exit, so `s` only labels; without `--save`, `s` does a one-off write of the payloads captured so far to a new capture file), or **`n`** to **finish the current `--save` session and start a fresh one** (writes the current session to its own capture file *now*, then begins a new labelled recording, so one run yields several labelled sessions; `n` requires `--save`); an active `--save` recording shows a blinking **`● REC`** in the status line. Other monitor keys: **`?`** opens a keybinding help modal, **`=`/`-`** change the poll interval live, **`space`** pauses, **`r`** toggles the **byte ruler** (one row above the hex, numbering each byte column in the user's `display.byte_notation` / `--notation` — WiCAN `Bnn` by default — plus each signal's byte-reference column beside its value, rendered from the *same* notation so the two can never disagree; a run that is non-adjacent as rendered shows as `B15,B17-B19`, since WiCAN interleaves PCI bytes, and `bix` — a *bit* index — falls back to WiCAN because it cannot fit a 2-char column), **`V`** cycles the **view mode** (`ecus` → `ranges` → `signals` → `full`: a bare responding-ECU list, each signal's captured value *span* (numeric min–max or distinct labels, like `investigate`/`decode` report a range), the decoded signals only, or signals + raw byte payloads — the default; view mode is display-only and never changes what's recorded), **`i`** opens a read-only **session-info** overlay (the current segment's label/state/notes + start time, the run-level counters — frames captured/unique, cycles, retain mode, poll interval, transport, run start/elapsed — the paths of the `captures/` dir and the active **write-ahead journal** (`.journal/*.jsonl` — exactly what `canair captures uds --recover` would read), and the history of the `--save` segments already finished this run, each with its label/states/time-span/frame-count/written file), **`l`** opens a scrollable **errors/diagnostics log** overlay (a live view of `canair logs` — the transport-fault event log, colour-coded by category), **`↑`/`↓`** select a signal row for in-place editing and **`esc`** clears (deselects) that selection. **There is no follow/tail mode** (the `f` key was removed): a repaint never moves the scroll position, so a byte can be read while data keeps arriving — `G`/`End` jumps to the newest output on demand. **Signals are listed in payload order** — sorted by the byte each one reads first (`canlib/decoding.py::signal_order_key`/`order_signals`), applied in `decode_param_rows` so *every* decoded view (monitor, `read`, `captures --diff`/`--step`, `decode`) lists them in the same order the hex bytes print in, instead of the ECU file's definition order. When a payload byte changes, the byte is highlighted in the hex line, and the signal(s) whose expression decodes that byte are highlighted with the same coverage-coloured background (verified→dark_green, unverified→dark_goldenrod) **only when their decoded (interpreted) value actually changed** — a byte flip that leaves the signal's value unchanged (a bit it doesn't map, or a sub-resolution change that rounds to the same value) highlights the byte but not the signal — linking a byte flash to the value it produced. The status line shows a **`captured N/uniq M`** frame counter (total fresh payloads received vs distinct values kept — both differ from the on-screen row count) and a **`drops D`** transport-health indicator (cumulative dropped/stale ISO-TP frames, red when non-zero + a per-cycle `+N` spike; an `err E` count for other non-answers) — surfaced from the active client's `.diag` (`canlib/transport_stats.py`) to flag connection/latency trouble live. The whole bottom bar is a **width-aware status bar** (`canlib/tui_status.py`: `StatusItem` + `compose_status` + the `StatusBar` widget, shared by `monitor`/`sniff`/`captures --step`/`decode --plot`) — each segment is priority-ranked and the bar renders only what fits the terminal's *current* width, shedding the least essential segments (and re-composing on resize) instead of soft-wrapping its tail out of a fixed-height widget; `? help` / `q quit` and any alert are the last to go, and `?` remains the complete key list. Each recorded `--save` session also stores its acquisition **`transport`** (`slcan-tcp`/`wican-ws`; `import` for `canair import uds`), the recording canair **`version`** (provenance-bearing — from a git checkout it carries the branch + short commit, e.g. `1.15.0+main.343b244`, `+…dirty` with uncommitted tracked edits, so a reading traces to the exact code that produced it), and a **`quality`** footprint (`exchanges` + any non-zero drop/stale/no_data/bus/decode counts) as capture provenance — shown in `canair captures uds --sessions` and inspectable in full via `canair logs`. The **vehicle state is auto-suggested** from decoded PID values via the profile's `vehicle_states.yaml` (see `canair validate states`) — the save modal's state field is **free text** (comma-separated), pre-filled with the auto-suggestion, and shows whether a state is set (`state auto-detected: …` / `no state set — will auto-detect from data on save`). When a `--save` segment is left without an explicit state, it is back-filled on reconcile with the **union of every state observed across the segment's whole span** (not just the state active at exit), so a segment that charged then went idle still reconciles as `charging`. Repeated non-`--save` on-demand saves only write payloads seen **since the last save** (no duplicates). **`canair monitor` keep-mode defaults to `--keep-changes`** (run-length: only payloads that differ from the *immediately preceding* one per PID are stored/recorded, so a long `--save` session stays compact on a stationary signal yet still records genuine oscillation `A→B→A` and keeps dwell durations recoverable from the timestamps); pass **`--keep-unique`** for the legacy **global** dedup (only globally-distinct values per PID — smallest file, but return-to-previous transitions and durations are lost, tagged `keep_mode: unique`), **`--keep-all`** to record every polled cycle (full time-series, larger files — use it when you need real timing/rate) or **`--keep N`** for the last N per PID.

## Vocabulary — say **signal**, not parameter/param

**A decoded quantity read off the bus is a SIGNAL.** That is the settled
user-facing term, in both data domains: a field decoded from a diagnostic PID/DID
response (domain A) and a field decoded from a broadcast CAN frame (domain B) are
both *signals*. Prefer it in every new/edited string a user reads — `--help`,
TUI labels and status hints, prompts, error messages, docs, release notes, commit
messages, plan docs, and skills.

- **Do not introduce new "parameter"/"param" wording.** When you touch a
  user-visible string that still says parameter, change it to signal (Boy Scout).
- **The existing `parameters:` key in `ecus/` and the `canair pids upsert-param`
  /`rm-param`/`rename-param` CLI are the compatibility surface** — they keep their
  names for now (a schema/CLI rename is a separate, migration-bearing change).
  Their *help text* still says signal.
- **`canair signals` remains domain-B-specific** (the broadcast `signals/<bus>.yaml`
  editor). "Signal" as a *word* is domain-neutral; the *command* is not.
- **Python identifiers still say `param`** in many places (`ParamRow`,
  `decode_param_rows`, `render_param_table`, `ParamStats`, …). That rename is
  tracked as one atomic follow-up in
  `plans/2026-08-06-signal-naming-convention.md` — read it before renaming
  piecemeal, so the tree does not sit half-renamed.

## Tools

> Reverse-engineering a new PID/DID end-to-end (discover → capture → analyze → define → verify) is documented in the **reverse-engineer-signal** skill; decoding the unknown bits of a partially-decoded bitflag byte is in the **decode-bitfields** skill; general project/device context is in the **ioniq-reverse-engineering** skill.

All functionality is exposed through a single installable CLI, **`canair`** — but in this repo you **always** invoke it as **`uv run canair …` from the repo root** (see "Running the CLI" above). `uv tool install .` exists for end users, not for agents working in the tree.

- **`canair wican`** — Build/sync the WiCAN device's AutoPID profile from the active bundle's `ecus/`. A bare `canair wican` prints help (writes nothing). Subcommands: `autopid write` (generate JSON to `out/` — **verified-only by default**; pass `--include-unverified` to also emit in-progress candidate params), `autopid upload`/`download`/`diff` (device sync, Pro-only — `upload`/`diff` share the same verified-only default + `--include-unverified` opt-out), `autopid stats`, and `mode show`/`mode set MODE` (device protocol switch, Pro-only — `mode set` also auto-aligns the config `transport.type` to the new mode: `slcan`→`slcan-tcp`, `elm327`→`wican-ws`, printing the `old -> new` change or "already"; `--no-transport` opts out, other modes leave it untouched)
- **`canair read`** (formerly `canair query`; `query` kept as an alias — named for UDS ReadDataByIdentifier 0x22) — Custom CAN/UDS requests over the configured transport (raw `slcan-tcp` by default, or the `wican-ws` WebSocket ELM327 terminal). **Prefer positional query steps** like `canair read BMS:2101` (multi mini-language — handles sessions, wake, keepalives; a bare selector like `BMS:2101` is treated as a query step — the mini-language *step verb* is still `query`). **Bind each PID to its ECU with a colon (`IGPM:22BC07`), never a space** — in a query step a space separates *independent ECU selectors*, so `"query IGPM 22BC07"` means "all of IGPM plus a bogus ECU 22BC07" and is rejected. Use `canair read --param`/`canair read BMS` for simple single-ECU reads, `canair scan range` for discovery. A **`@group`** token in a step expands to a saved set of selectors (`canair groups`; e.g. `canair read @charging`) and composes with ad-hoc selectors. Companions: `canair discover` (alias `disc`), `canair io`, `canair routines`, `canair identity` (alias `id`; standard UDS identity DIDs — F100/F18x/F190/F19x), `canair scan routines` (probe requestRoutineResults across a range — auto-selects UDS 0x31 SF03 or KWP2000 0x33 RequestRoutineResultsByLocalIdentifier by `id_protocol`, so it never blind-sends 0x31 StartRoutine to a KWP2000 ECU; hits saved to `ecus/<ecu>.yaml` `routines:`), `canair scan iocontrol` (probe returnControlToECU across a DID/LID range — auto-selects UDS 0x2F or KWP2000 0x30 by `id_protocol`; hits saved to `iocontrol_discoveries:`), `canair raw` (**last resort** — hex dump only, no decoding), `canair repl` (interactive). `--verbose` is for debugging canair itself, not normal use. **TesterPresent keepalives are automatic and there is no `tester-present` command/flag** — opening a session (a `session <ECU>` query step or any command's `--session`) keeps it alive with idle-aware `3E00` (real traffic resets the S3 timer). `3E00` (SID `0x3E`) is shared by UDS and KWP2000, so it is sent identically for both protocols; send one by hand via a query step (`canair read BMS:3E00`), or use the `repl`'s `!tester` for a manual loop. **Use `--reboot` to restore AutoPID after session** (WebSocket terminal overrides AutoPID mode). Dependencies: `websockets`, `pyyaml`, `requests` (optional, for reboot).
- **`canair monitor`** (alias **`mon`**) — Live, continuously-refreshing view of ECU parameters (promoted from the former `canair query --monitor` flag into its own top-level command). Takes the same positional query steps as `canair read` (`canair monitor BMS:2101`, cross-ECU `"VCU:2101 BMS:2101"`, saved groups `canair monitor @charging`), plus `--interval SECONDS` (poll period, default 5.0; change it live in the TUI with `=`/`-`). On a TTY it opens the scrollable Textual monitor; piped it polls silently until Ctrl+C. Recording (`--save`/`--label`/`--state`/`--notes`) and keep-modes (`--keep-changes` default, `--keep-unique`, `--keep-all`, `--keep N`) live here, not on `canair read`. **`--wait`** blocks until the device comes online then starts (shared by all live commands), and for `monitor` also makes a mid-session drop reconnect forever instead of the bounded default (auto-failover to a reachable same-transport device — see the **Mid-session reconnect** paragraph under WiCAN Access below). **`canair read` never had a `--monitor` flag** — use `canair monitor`.
- **`canair captures`** (alias **`cap`**) — Query captured data, split into two domain kinds (the `uds`/`can` naming spine). **`canair captures uds`** (domain A — diagnostic UDS payloads) takes a QUERY (mini-language, like the other tools): `BMS 2102` (ECU + PID, most useful), `"BMS:2102,2103"` (several PIDs), `BMS` (all PIDs for an ECU), or a quoted cross-ECU `"VCU:2101 BMS:2101"`. Add `--diff` for the byte-level diff view or `--step` for the interactive stepper/comparator (the step header shows the ECU's `alias` when it has one, e.g. `SKM (alias SMK)`). **`--step` with a QUERY selecting several PIDs stacks them underneath each other in one time-joined frame** — one block per `(ECU, PID)`, anchored on the *union* of every capture timestamp with the other PIDs nearest-joined within **`--join-tol`** (default 10s — wider than the shared `DEFAULT_JOIN_TOL_S` used by `align`/`correlate`/`hunt`, since a full round-robin monitor cycle over several ECUs spans ~8-10s and the stepper is a viewer that shows each block's `Δt`; a slot with no capture in range renders `— no ECU:PID capture within Ns —`, so nothing is hidden), which is how you cross-compare signals at the same instant (e.g. `canair cap "HVAC:220100,2201A0,2201A2" --step` reads duct temperatures against compressor duty as the AC cycles). It is a **Textual app** (scrollable — a stacked frame is routinely taller than the terminal; `?` opens the keybinding help): `←`/`→` (`h`/`l`, `n`/`p`, `space`) move frames, `[`/`]` jump ±100, `g`/`G` first/last, `:` goto, `↑`/`↓`/`j`/`k`/PgUp/PgDn/wheel scroll *within* a frame and `home`/`end` jump to the frame's top/bottom. **A frame move never moves the scroll position** — the same rule as `canair monitor`: a stacked frame is taller than the screen and stepping is how one byte is watched *across* frames, so the viewport stays where the reader parked it and only the content underneath changes (the frame's timestamp is mirrored into the status bar, since the body's frame header scrolls out of view). The one exception is an explicit *reveal*: `tab`/`shift+tab` move a **block cursor** (`▶`) that `e` (edit note), `d` (delete, confirmed) and `x` (drop this PID from the comparison) act on — moving it, or jumping to a note, scrolls that block on screen **only if it is off-screen** (shared policy in `canlib/tui_scroll.py::reveal_marker`, also used by the monitor's selection cursor). **`a` opens a filterable checklist to add/remove PIDs live**, **`t` sets the join tolerance** (`<`/`>` step a ladder), **`s` opens a jump list of the sessions in scope (newest first) with each session's noted captures nested under it** — select a session to land on its first frame, or a note to land on that capture (a note on a PID that isn't in the comparison adds it, and unique-payload dedup is lifted when it hid the target, both reported in the status line; `/` filters, `n` shows only noted sessions; a session is listed only when it has a frame for the current selection **or** carries notes — one offering neither is omitted and counted in the footer rather than padding the list — and a note the current view can't place (an untimed legacy capture) is omitted too, counted in the footer with a pointer to `captures --sessions`, while a note no view can render (non-payload) is listed disabled with the reason), `V` cycles the view, `r` rulers, `u` unique/all payloads. **`--view {auto,stacked,signals,changed,interleaved}`** selects the rendering non-interactively: `stacked` (params + byte-diff hex), `signals` (params only — fits more PIDs on one screen), `changed` (only params whose *decoded* value moved since that PID's previous capture), `interleaved` (one capture per frame, chronologically across the PIDs — the right choice for browsing a whole ECU), default `auto` = stacked up to 6 PIDs, else interleaved. `--step` is fully non-interactive too: **`--json` emits the joined frames** (one block per PID with its `dt_s` offset from the anchor + decoded params) and piped output renders the most recent frames statically, both capped by `--limit`. (The old `--step --pair` two-PID flag is **removed** — a multi-PID QUERY does it, N-way and editable.) **The default list view is capped at the most recent `--limit N` captures (default 50; `--limit 0` = no cap) with a loud footer reporting any hidden history — so a bare `canair captures BMS 2102` can't blow the context window; widen with `--limit N`/`--limit 0` or a tighter scope (`--since`/`--last-session`/`--state`).** `--latest` (dedup-per-PID, most recent payload) reads its ECU/PID from the **QUERY** (`canair captures BMS --latest`, `BMS:2102 --latest`; a bare `--latest` = every PID's latest). Aggregate modes (no QUERY): `--summary` (stats per ECU/date), `--sessions`/`-n` (session **table of contents** — date/time-span/state/label/session-notes/ECUs + distinct capture-notes per session, plus each session's acquisition `transport`, the recording canair `version` (a `· vX.Y.Z ·` tag — with the branch + commit appended for a checkout-recorded session), and a `quality` line flagging any recorded drops/errors, no payloads; the fast "what's in the captures?" index, `--json` for machine output), `--recover` (reconcile orphaned journals from a killed/crashed `--save` session into capture files; `--discard` to delete them unsaved). **`--delete`** removes the captures matching QUERY (+ scope filters) via canair's own helpers — refuses a bare `--delete` (never nukes everything), previews with `--dry-run`, and confirms interactively unless `--yes` (scripting); never hand-edit `captures/` to remove data. **`--backfill-states`** infers and back-fills a session's `vehicle_states` offline by re-decoding its captures and evaluating the profile's `vehicle_states.yaml` predicates (via `canlib/state_infer.py`, the offline analogue of the monitor's span-aware back-fill) — it **fills** sessions with no recorded state and **reports** (but by default never rewrites) sessions whose recorded state is provably contradicted by the evidence (`--overwrite` to correct them); cross-ECU predicates group co-polled captures into pseudo-cycles within `--cycle-tol` seconds (default 10s), previews with `--dry-run`, emits `--json`, honors the scope filters, and confirms unless `--yes` (writes via `canlib/captures.py::set_session_states`). **`--set-state STATES`** manually sets a session's `vehicle_states` (comma-separated) on the scope-selected sessions — the manual counterpart to `--backfill-states` for a state known from the label/context but not inferable from the data (e.g. a body/low-power ECU read: `--set-state ACC --label 'ACC only'`); it **requires** a scope filter (`--label`/`--date`/`--since`/…) so it can't blanket-relabel the whole history, soft-warns on out-of-vocabulary tokens, previews with `--dry-run`, emits `--json`, and confirms unless `--yes` (same `set_session_states` writer). Any mode can be scoped to a date/time range with `--since`/`--until` (inclusive; accepts a date `YYYY-MM-DD` **or** a timestamp `YYYY-MM-DD HH:MM[:SS[.ffffff]]` to narrow within a day) or `--date` (single day) or `--today`, the most recent sessions with `--last-session`/`--last-sessions N`, and/or by `--state SUBSTR`/`--label SUBSTR` (case-insensitive substring of the session state/label). **`canair captures can`** (domain B) lists imported raw broadcast-CAN frame logs from `captures/can/index.yaml` — file/format/frames/IDs per log (`--json` for machine output). **`canair captures migrate`** converts a profile's legacy per-day capture files (`captures/*.yaml`) to JSON (`captures/*.json`) — the one-time migration for a profile created before the JSON cutover; each file is round-trip verified before its YAML is replaced (`--dry-run` to preview, `--json` for machine output). **`canair captures migrate-rx`** renames the persisted capture field `ecu` → `rx` (the field holds the ECU CAN *response* address, RX = request TX + 8 — not an ECU name, so it was renamed to stop the confusion with the resolved short name; readers still accept the legacy `ecu` key via `capture_io.capture_rx`, so the migration is safe to defer). It renames at the capture level and inside `scan_results.responding[]`, is idempotent, and previews with `--dry-run` (`--json` for machine output). **`canair captures merge-driver`** is the git merge driver for the append-only capture files: invoked by git as `merge-driver %O %A %B %P` it **unions the session lists** so two machines' same-day appends merge cleanly instead of conflicting (git's line merge splits those conflicts mid-record); a genuine divergent edit or unreadable input falls back to normal conflict markers. It's wired via a `.gitattributes` rule (`profiles/*/captures/*.json merge=canair-captures`) but requires a **one-time per-clone registration** — run **`canair captures merge-driver --install`** once to write the `[merge "canair-captures"]` stanza into `.git/config` (git never loads a driver command from a tracked file, for safety; until a clone installs it, merges simply fall back to markers, so nothing breaks). Pure union in `canlib/captures_merge.py`. A bare `canair captures BMS 2102` (or any of the `--summary`/`--sessions`/… flags) is shorthand for `canair captures uds …` (via `_GROUP_DEFAULTS` in `cli.py`, like `scan`/`ecu`).
- **`canair import uds`** — Device-free UDS capture import (domain A; the `uds` kind of `canair import`): record an externally-provided UDS payload (pasted from a forum/issue, or read on another tool) into the active profile's `captures/` through the same machinery as a live `--save`, so it's indistinguishable from a device-recorded capture and immediately queryable by `decode`/`captures`/`coverage`. Each capture is `ECU:PID=PAYLOAD` (ECU short name or hex TX id; PID/DID; reassembled UDS payload, SID-first, PCI stripped); pass several to group them into one session. Metadata via `--label` (required), `--state` (repeatable, vehicle power state), `--notes`/`--capture-note`, `--time` (default: the import instant — a payload capture is **always** timestamped, since an untimed one is silently dropped by every time-aligned analysis), `--date` (default today; sets the target file). Resolves ECU→RX, rejects non-hex payloads, and **warns on SID/DID echo mismatch** (a payload filed under the wrong PID) without blocking. `--json` for machine output. This is how community-contributed readings (no device on hand) are onboarded — never hand-write `captures/`. (The domain-B ingest counterparts are `import can` / `import dbc` — see `canair import` below.)
- **`canair decode`** (alias **`dec`**) — Parameter/value-centric decoding: applies WiCAN expressions to all historical captures. **Takes a QUERY in the shared mini-language** (`canair decode BMS:2101`, the two-token `BMS 2101` still works, `BMS` = all its PIDs, `"MCU:2102 VCU:2101"` cross-ECU). **Default view shows each param's value range** across captures (payload/byte-diff views live in `canair captures`). **Multi-PID queries are supported for the default value-range, `--compact`, and `--json` views** (one section/JSON block per PID); the analysis modes below (`--corr`/`--plot`/`--stats`/`--discriminate`/`--find-mirrors`/`--try`/`--dump-bytes`) require the query to resolve to a **single** PID. Modes: `--param` (filter), `--compact` (one aligned row per capture — param names in a single header, `[state]` divider only when the session state changes, time-only rows, right-aligned value columns; add `--changes-only`/`-c` to drop rows unchanged from the previous one, collapsing stationary runs), `--stats` (n/distinct/mean/median/stdev per param; add `--group-by state` for per-drive-segment stats in one shot), `--corr PARAM` (Pearson correlation of every param vs a reference — **`PARAM` may be a local name OR a cross-signal `ECU:PID:PARAM`/`ECU:PID:EXPR`**, e.g. `--corr ESC:22C101:REAL_SPEED_KMH`, time-aligned by nearest timestamp; add `--corr-transform delta|abs|cumsum|normalize` to test level-vs-rate, `--method pearson|spearman` to pick the coefficient (spearman = rank, catches monotone-but-nonlinear/quantized/saturating links; **`cramers_v`/`mutual_info` treat each value as a nominal category — for enum/mode/flag references where numeric spacing is meaningless**; a **`--method` cheat sheet** — which coefficient when — is in `canair decode --help` / `correlate --help`), `--join-tol SECONDS` to widen the join), `--discriminate AXIS` (rank params by how cleanly they separate across groups of AXIS — an F = between/within variance ratio for numeric params, **Cramér's V for typed enum/bitmask params** — that surfaces thermal/mode/relay signals a driving correlation misses; add `--bytes` to also rank every varying raw byte and `--bits` every toggling bit, no `--try` needed. **AXIS is `state`** (the vehicle power state) **or a cross-signal `ECU:PID:PARAM`** — e.g. `--discriminate HVAC:220102:HVAC_COMPRESSOR_ON --bytes` ranks which byte separates compressor-on from off; the axis signal is nearest-joined onto each capture and discretized into low-cardinality enum/flag/mode groups, a too-continuous axis is rejected), `--find-mirrors` (`--bits` for bit-level: report byte/bit positions on this PID that mirror each other — redundant status mirrors / unit-variants; `--allow-offset`/`--mirror-match` per the shared mirror entry below), `--plot` (interactive signal explorer — a Textual TUI: sweep ImHex-style byte interpretations `u8/i16/f32/…`×endianness and params, plot across captures, apply transforms `delta/abs/normalize/…`, zoom/pan the x-axis, overlay a `--corr` signal, show the visible date/time range, list the backing captures in a modal (`i`), flag bytes already mapped by a defined param, read off the equivalent WiCAN expression, switch to another captured PID in place (`p`), annotate the current param/byte or rename the PID via `canair pids` (`a`/`R`), and `?` for a keybinding help modal), `--try "NAME[:unit]=EXPR"` (test a candidate expression against captures **without** editing YAML; works even for a not-yet-defined PID), `--verified`/`--unverified`, `--json`. **Scope which captures are considered** (shared with `canair captures`): `--since`/`--until`/`--date` (inclusive; a date `YYYY-MM-DD` or a timestamp `YYYY-MM-DD HH:MM[:SS[.ffffff]]` for `--since`/`--until`), `--today` (shorthand for today's date), `--last-session`/`--last-sessions N` (the most recent N recorded sessions in scope — applied *after* date/state/label, so `--state driving --last-session` = the last driving session), `--state SUBSTR`/`--label SUBSTR` (case-insensitive substring of the session state/label — the natural unit of drive analysis, e.g. `--state driving`), and `--first N`/`--last N` (chronological slice). Example drive analysis: `canair decode MCU 2102 --stats --group-by state --state driving`. **`--dump-bytes`** emits a `timestamp × byte-offset` matrix (one row per scoped capture) instead of decoding params — CSV by default, `--json` for JSON, PCI framing bytes skipped unless `--include-pci`, columns relabelled by `--notation`, and **`--signed`** renders each data byte as a two's-complement value (-128..127) under an `Snn` header instead of the unsigned `Bnn` (0..255) — for a byte that is the high half of a signed value (a `0xFF` near-zero baseline correlates cleanly signed, not as unsigned 255); the structured escape hatch for ad-hoc byte analysis (replaces regex-scraping `captures --diff`). Timestamps are harmonized with `align`/`decode --json`: CSV `time` = absolute `YYYY-MM-DD HH:MM:SS.ffffff`, JSON `time` = time-only + a separate `date` (no ISO `T`), so a `dump-bytes` CSV and an `align --csv` join without reformatting.
- **`canair align`** — Emit a **time-aligned, wide table of several cross-ECU signals**: one row per reference sample, one column per `ECU:PID:PARAM` (or `ECU:PID:EXPR`) selector, nearest-joined within `--join-tol` (default 5.0s — the shared `DEFAULT_JOIN_TOL_S`, sized for the round-robin inter-ECU skew of a multi-ECU monitor session; a "far" ECU on an 8-ECU cycle lands ~3.4s from the reference, which the old 2.5s silently dropped). The **first** selector sets the row cadence; the rest join onto it (via the shared `canlib/align.py` `align_many`/`load_ref` join used by correlate/hunt). Output: `--csv` (absolute `YYYY-MM-DD HH:MM:SS.ffffff` `time` column, joinable with `--against-file` / a `decode --dump-bytes` CSV), `--json` (row objects: `date` + time-only `time` + `values`), or a compact TTY table (short `c1/c2/…` handles + a full-label legend, `c1` = reference). Shares the standard scope flags (`--since`/`--until`/`--date`/`--state`/`--label`/`--today`/`--last-session`) and warns on `keep:changes` scope. Fills the "show me A, B, C side by side over this window" gap (eyeball a regime, export a drive slice, feed an external plot/meter) that previously forced a hand-written nearest-join script. `uds` (diagnostic) domain; a `can` (raw broadcast frame) counterpart is future work. See `docs/concepts/analysis-commands.md` for when to reach for `align` vs `decode`/`correlate`/`hunt`. Plan: `plans/2026-08-01-align-and-discriminate-axis.md`.
- **`canair correlate`** — Cross-signal correlation across a whole drive/session: time-aligns every decoded param (and, with `--bytes`, every varying raw byte; `--bits` for toggling bits) across all co-polled ECU/PIDs in scope and ranks the strongest cross-signal relationships — the "show me every strong relationship in this drive" entry point (how the AAF-speed / MCU-temp finds were made). Optional `ECU[:PID]` selector to restrict signals. Modes: default ranked pair list (cross-PID/ECU only unless `--include-intra`; near-perfectly-correlated |r|≥0.995 groups collapse to one summary line unless `--no-cluster`), `--against ECU:PID:PARAM` (rank every signal vs one reference — drops the trivial self-match unless `--include-self`; `--promote NAME` writes the top raw-byte hit into `ecus/` as an enabled unverified candidate; `--lag-scan N` reports the apparent lead/lag that maximises |r|; `--gate '[SIGNAL] OP VALUE'` restricts to a regime e.g. `'> 0'` = while-moving), `--overlap` (report which ECU:PID pairs actually share time-aligned samples in scope — pick a viable `--against` reference), **`--against-file FILE`** (rank every signal against an external `timestamp,value` CSV instead of an on-bus reference — a calibrated meter/GPS/grid-voltage log; mutually exclusive with `--against`; nearest-timestamp join on the captures' absolute clock), **`--control ECU:PID:PARAM`** (or `--control-file`; with `--against`, rank by the **partial** correlation with a nuisance signal regressed out — surfaces signals visible only once a dominant driver is removed), **`--find-mirrors` (report byte/bit positions mirrored ACROSS co-polled ECU/PIDs, time-aligned — e.g. a door bit in IGPM also present in BCM, or a temperature another ECU reports at a different offset; add `--bits` for bit-level and `--allow-offset` for offset/scale mirrors; the cross-ECU companion to `decode --find-mirrors`, which is single-PID. See the `--find-mirrors`/`--mirror-match`/`--allow-offset` entry below for the matcher)**, `--matrix`, `--json`; `--method pearson|spearman|cramers_v|mutual_info` (the last two rank by *categorical* association — for mode/flag/enum bytes; a **`--method` cheat sheet** explaining which coefficient to use when is in `canair correlate --help`); `--transform delta|abs|…` (transform the `--against` reference); thresholds `--min-r` (default 0.6) / `--min-n` (default 15) / `--top`; `--join-tol SECONDS`. Same scope flags as `decode`. **Warns when the scope includes `keep:changes` sessions** (stored rows are value-transitions, not fixed-rate samples) and caveats `--transform delta|cumsum` / `--lag-scan` on `keep:unique`/`keep:changes` data; there is deliberately **no blanket `keep:unique` scope banner** (it fired on nearly every report over historical captures). **Domain B — `canair correlate can FILE`** correlates a raw broadcast-CAN frame log's per-byte series instead of diagnostic captures — reads the native log (`--can-format auto` by extension), builds `0xID:rN` byte series (`--bits` for `0xID:rN.k`), and runs the *same* ranked/`--against`/cluster core (cross-arbitration-ID by default; `--include-intra` for same-ID; `--id 0x220,0x386` to restrict). **`--find-mirrors` works here too** — reports byte/bit positions mirrored ACROSS arbitration IDs, time-aligned (a signal broadcast on two IDs, e.g. wheel speed on `0x386` and `0x331`); add `--bits` for bit-level and `--allow-offset` for offset/scale mirrors. Frame labels render as-is (raw-CAN space, no WiCAN/PCI). Everything above is the default **`correlate uds`** kind — a bare `canair correlate …` is shorthand for it (via `_GROUP_DEFAULTS`); the diagnostic (WiCAN `Bn`) path is unchanged.
- **`canair hunt`** — "Which byte on ECU:PID *is* this known signal?" Sweeps every byte offset × interpretation (`u8/i16/f32/…` × endianness) on the target PID, time-aligns each against `--against ECU:PID:PARAM` (a known signal on another ECU/PID), and ranks by |Pearson r| — reporting the best **linear fit** (`y=m·x+c`) and a **physical-unit guess** (`raw−40 °C`, `×1.609 mph→km/h`, …) for each hit. Collapses to the best interpretation per byte offset by default (`--all-interps` to expand). `--transform delta|abs|…` hunts the byte that tracks the reference's *rate* (e.g. torque vs acceleration); `--method pearson|spearman`. `--promote NAME` writes the top hit's expression straight into `ecus/` as an enabled, unverified candidate param (via `canair pids upsert-param`) with the correlation evidence auto-filled into `notes`. **`--against-file FILE`** takes an external `timestamp,value` CSV (a calibrated meter, GPS track, grid-voltage export) as the reference instead of an on-bus `--against ECU:PID:PARAM` (mutually exclusive; joined by nearest timestamp; the file must be on the captures' absolute clock — a relative log joins to nothing). **`--control ECU:PID:PARAM`** (or `--control-file`) regresses out a nuisance signal and ranks by the **partial** correlation — surfacing a byte whose link to the reference only appears once a dominant driver is removed (the AC-voltage-behind-IR-drop case). **`--physical`** needs no reference at all: it flags bytes whose scaled value (`/1 /10 /100 ×2 ×√2`) lands in a named physical band (mains RMS/peak, line freq, 12V rail, HV pack) — the way to find an anchorless signal by plausibility. The bands are configurable across two axes (else an 800 V pack / non-EU grid silently gets no hit): a profile's `physical_bands:` (vehicle axis — `hv_pack`/`rail_12v`) and the user-config `grid_region` (grid axis — mains/line-freq); resolved by `canlib/physical_bands.py::resolve_physical_bands`, defaults reproduce the Ioniq's five bands. `--json`, `--top`, `--min-n`, `--join-tol`; same scope flags. **Domain B: `canair hunt can FILE --id 0xID --against 0xREFID:rN`** hunts on a raw broadcast-CAN frame log instead — sweeps every byte/interpretation of one arbitration ID's frames vs a reference frame byte in the same log (raw-CAN `rN` labels, no PCI; `--promote` not supported for frames — those are defined in `signals/`, Stage 4). Everything above is the default **`hunt uds`** kind (a bare `canair hunt AAF 2181 --against …` is shorthand for it); the diagnostic (WiCAN) path is unchanged.
- **`canair investigate`** — One-shot "tell me everything about this PID". For every varying data byte of `ECU PID`, reports in one ranked table: whether a param already **maps** it, its **state-discriminability** F, its strongest **co-polled cross-signal anchor** (r + linear fit + unit guess), and a **physical-band** flag (a scaling at which the byte lands in a named band — mains/HV/12V). Bundles the manual `coverage → discriminate → correlate → hunt` loop into a single call — the "point it at an unknown PID" entry point. Each byte also carries a **triage class** (constant/counter/checksum/enum — a live analog byte is unlabelled) from `canlib/triage.py`, and a **probable multi-byte words** section flags adjacent `[Bn:Bn+1]` pairs shaped like a scaled 16-bit value (near-constant hi byte + full-range lo byte — how a scaled voltage hides across a byte boundary). **`--independent-of ECU:PID:PARAM`** (or `--independent-of-file`) re-ranks bytes by state separation *weighted by independence from* that driver signal — the "active-but-independent" finder (a byte that varies by state yet doesn't track the named driver, e.g. AC voltage vs charge current), adding a `drv` (|r| vs driver) column. **`--bits`** also ranks individual toggling bits (`Bn:k`) — the body/comfort-ECU finder; a body PID with no co-polled anchor is ranked by state separation (no more misleading "no varying bytes"). **`--events`** switches to the bit/byte **edge timeline**: every rising/falling transition with its timestamp and value, aligned to the nearest capture note (the narrated event log) — the fastest way to decode event-driven captures (door/lock/hood). **`--events --field NAME`** collapses a single typed param (enum/bitmask/date/struct) into one logical signal — emitting one transition per change of its *decoded* value (e.g. `fanMAX (45) → fan1 (40)`) instead of scattered per-byte edges. **`--dwell`** summarises each event bit/byte by how long it stays ON (median on-duration + a `momentary`/`sustained` class), separating a briefly-pulsed bit from one held for minutes — needs `--keep-all`/`--keep-changes` data. **`--counters`** switches to **monotonic counter detection**: it sweeps every 1-4-byte window x endianness for a value that only ever RISES across the whole capture corpus, and sorts hits into `accumulator` (rises within sessions too — odometer, operating-seconds, cumulative Ah/Wh), `cycle` (flat inside every session, stepping only between them — ignition/power-cycle/trip count) and `timer` (ramps and resets per session, slope snapped to a wall-clock tick — uptime). This is the one question correlation cannot answer: a slow counter does not move within a session, so it reads as a CONSTANT byte to every other tool (`triage`'s `counter` class is direction-blind and single-byte — it finds a fast rolling counter's low byte, never an odometer). Evidence is scored in **bits** (one-sided binomial tail: each clean up-step with no down-step is 1 bit), which is what lets a 4000-sample accumulator and a 6-sample odometer rank on one scale instead of behind a step-count threshold. Windows are formed in **ISO-TP** space (contiguous by construction) and rendered via `ByteRef`, so a PCI-straddling counter emits a shift composition rather than a wrong `[Bn:Bm]`. Nested prefix windows of one physical counter collapse to the widest **canonical** window (end bytes not padding), because the width recovers the readable magnitude (`[B12:B14] = 72982` reads as an odometer; `B14 = 88` says nothing). Rejection rules that matter: `msb_jump` (a window straddling a neighbouring counter leaps its high byte), `step_ratio` (a running counter's value is much larger than one increment — kills a block of flags flipping 0→1), reset-to-~0 + tick snapping for timers, and suppression of a wide accumulator's wrapping low bytes masquerading as a timer. Flags: `--min-bits BITS` (default 4), `--counter-width N` (default 4), `--unmapped-only` (hides a window only when **every** covering param is `verified`; a window mapped by an *unverified* guess is kept and tagged `[NAME?]`, since monotonicity is frequently what **refutes** the guess — the bundled profile's `VCU:21F2 CHARGE_TIMER_WKND_END_HOUR` was inferred from one before/after coincidence yet the byte only ever rises), `--json` (each window carries `mapped_by` + `mapped_verified`). **Do NOT scope it** — it wants the whole history, since the horizon IS the evidence; an empty report names the best sub-threshold window and the `--min-bits` that would surface it. `uds` only (no `can` counterpart yet). Detection lives in the leaf `canlib/counters.py`; the capture-model bridge (row-aligned **prefix** payload matrix — aligning on the *modal* length instead silently discards every capture of a minority length, i.e. months of horizon when a padded response changes length) is `canlib/commands/investigate/counters.py`. `--all` (include mapped bytes), `--min-r`/`--min-n`/`--join-tol`, `--json`; same scope flags. **Warns on `keep:changes` scope** (stored rows are value-transitions, not fixed-rate samples); `keep:unique` gets no blanket banner — it is flagged only in the `--events` dwell classes, where dropped falling edges actually change the reading.
- **`canair research`** — Report the open reverse-engineering backlog from the per-ECU `research:` sections in the profile's `ecus/`. Complements `canair coverage` (undecoded *bytes*) by surfacing *planned* work (scans/decodes/verifies). Modes: `canair research` (all open, priority-sorted), `--summary` (counts by status/type/priority/ECU), `--ecu`, `--type scan|decode|verify|iocontrol_scan`, `--status`, `--priority P1|P2|P3`, `--states acc|ready|…` (was `--prerequisite`), `--all` (include done), `--json`. Use as the "what should I RE next?" entry point.
- **`canair coverage`** (alias **`cov`**) — Audit PID definitions for decoding gaps. Cross-references each PID's signal expressions against its longest captured payload and reports **UNMAPPED** data bytes, incomplete **BITS** (bytes read bit-wise with undecoded bits left), and **NO CAPTURE** PIDs (signals defined but nothing captured). Modes: `canair coverage` (all), `canair coverage IGPM [22BC03]` (filter), `--bitfields`, `--unmapped`, `--no-capture`, `--all` (include fully-mapped), `--json`. Run after adding signals/captures to spot what still needs decoding. **Bit coverage counts both models**: the `Bn:k`/`Sn:k` accessor (via the shared `canlib/byteindex.extract_bit_indices`) *and* a `type: bitmask` param's `bits:` map keys — so labelling 3 of 8 bits as a bitmask no longer hides the other 5. **A whole-byte read (`Bn`) does NOT suppress the bit-gap report**; the line is flagged `(also read whole)` and `--json` carries `also_whole: bool`. This matters because the profile's own `DEBUG_*_FLAGS` convention (raw byte + individual bits below) used to make `analyze_pid` treat the byte as fully mapped, which hid the two most-captured bitfields in the bundled profile (VCU 2101 B10, the PRND byte, and BMS 2101 B14) — see `plans/2026-08-06-bitfield-audit-and-gear-state.md`. Remaining known blind spot: an `&`-mask expression (`(B09 & 0x04)`) contributes no bit references, so author bits as `Bn:k`, never a mask.
- **`--join-tol` / `--fill` / `--max-hold` (shared join flags)** — declared once in `canlib/commands/_join.py::add_join_args` (the `add_scope_args`/`add_notation_arg` precedent) for `align`/`correlate`/`hunt`/`investigate`/`decode`, so the default cannot drift between them; `captures uds --step` deliberately keeps its own wider viewer tolerance. **`--fill` turns on forward fill (last-observation-carried-forward) for run-length data** — a `keep:changes` row means "this value holds until the next row", but the joins used to treat it as a point sample and silently dropped every reference row it had no sample at (measured: aligning IGPM `CHARGE_PORT_LOCK`, known for a whole 3h charge, against BMS `SOC_BMS` joined 5 of 2016 rows). **Default `auto`** fills only rows whose session recorded `keep_mode: changes` (per *row*, so a mixed scope fills only the part it may); `hold` forces it over unrecorded provenance (legacy/`keep:all`) and warns loudly on `keep:unique` (`fill.FORCED_HOLD_WARNING`); `none` restores strict point semantics. `--max-hold SECONDS` caps the carry. **Policy lives in `canlib/fill.py`** (`FillPolicy`, `hold_until_vector`, `session_end_times`) and is resolved at *series-build* time, where the capture rows still carry `keep_mode` and `(file, _session_idx)`; it becomes a per-sample `TimePoint.hold_until` → `PreparedSeries.hold_ts` that `align.join_indices(..., cand_hold_ts=)` consults **as a fallback** (a real sample within `--join-tol` always wins), so the join primitives never learn what a keep mode is and passing no hold vector is bit-identical to the pre-fill join. A value is **never carried across a session boundary**, and a session's final run closes at that *session's* last capture (across all PIDs — `session_end_times`), not the PID's own. Fills are always reported: `align` shows `[N joined + M held, up to 2h58m]` per column (`align.join_fill_stats` → `JoinStats`) and a per-row `filled` key in `--json`; `correlate`/`hunt`/`investigate` print `_join.fill_summary_line` and a `--json` `fill` block. A summary counts only holds **longer than `--join-tol`** (a shorter hold covers only instants the strict join already reached, so reporting it was pure noise). Caveat: scope filters run *before* validity windows, so a narrow `--since/--until` excludes the earlier row that established the held value — prefer `--date`/`--state`/`--last-session`. Plan: `plans/2026-08-05-run-length-forward-fill-joins.md`.
- **`--find-mirrors` / `--mirror-match` / `--allow-offset` (mirror detection)** — a *mirror* is one physical quantity reachable two ways (a status bit an ECU repeats, a temperature another module reports at a different offset, a raw byte and the param derived from it) — the fastest identification of an unknown byte, since it needs no correlation reasoning. Three sweeps share one matcher in **`canlib/mirrors.py`**: `decode --find-mirrors` (intra-PID, rows aligned by capture index — `frame_columns` + `find_column_mirrors`), `correlate --find-mirrors` (cross-ECU/PID, time-aligned — `find_series_mirrors`), `correlate can --find-mirrors` (cross-arbitration-ID). It replaced an all-rows *exact* equality test that missed most real mirrors: **`--mirror-match FRACTION`** (default `DEFAULT_MIRROR_MATCH` = 0.9) sets the agreement required, because round-robin polling reads a drifting signal on two ECUs seconds apart and they disagree by ±1 on a minority of rows; **`--allow-offset`** accepts `a == scale·b + offset`, since real mirrors are frequently the same quantity at a different zero/scale (recovered on the bundled profile: `OBC:2101:B19 == AAF:2181:AAF_LDC_TEMP + 100`, `AAF:2180:B21 == COMPRESSOR_TEMP + 40`, a raw 12V byte at `× 12.8`). Candidates are **proposed from a sample** (modal `a−b` / `a/b` over the first 32 aligned rows) and then **verified on every row** with an early bail once the disagreement budget is spent, so the sweep stays O(1) joins per *clock* pair (bucketed like `corrmatrix`) rather than per signal pair — the whole-corpus sweep went 24s → 4s while searching more. Agreement must also beat coincidence (**`MIN_KAPPA`**, Cohen's κ, reported whenever not unanimous): without it two flags that are both zero in 99% of rows "agree" 99% of the time by construction, which inflated 3 real mirrors to 73 reported pairs. A pair whose sides are *constant* in scope is never a mirror. Defined params are swept alongside raw bytes, so an unknown byte can mirror a named signal.
- **`--notation {wican,isotp,torque,bix}` (shared display flag)** — `correlate`, `hunt`, `investigate`, `coverage`, and `decode` (`--discriminate`/`--find-mirrors`) render raw-byte labels as WiCAN `Bnn` by default; `--notation` re-renders them as ISO-TP (`iN`), Torque letters, or bix for reading/cross-referencing. **`monitor` and `captures` take it too** — there it selects the notation of the `--rulers` byte ruler *and* the per-signal byte-reference column beside each value (one `ByteDisplay` renders both, so they always agree; `bix` falls back to WiCAN for the ruler, which needs ≤2-char columns). **Display only** — named signals are untouched, and `--json`/`--promote` always emit the canonical WiCAN expression. Persist a default with `canair config set display.byte_notation NAME`. Internally a byte is modelled in ISO-TP space (`canlib/notation.py::ByteRef`, rendered for display via `ByteDisplay`); WiCAN/Torque/bix are derived views (the byte-notation de-conflation — `plans/2026-07-24-byte-notation-phase2-isotp-canonical.md`).
- **`canair pids`** — Safely add/update the profile's `ecus/` **parameters** and **research** entries from the CLI (surgical, comment-preserving; each edit is YAML-reparsed and schema-validated via `canair validate pids`, and auto-reverted on failure). Subcommands: `upsert-param ECU PID NAME EXPR [--unit --min --max --source --notes --verified/--unverified --type enum|bitmask|ascii|date|bcd --value RAW=LABEL --bit INDEX=LABEL …]` (**typed/multi-modal decoding**: `--type` + repeatable `--value`/`--bit` `KEY=LABEL` pairs define an enum/bitmask; passing only `--value`/`--bit` infers the type. The WiCAN `expression` stays the pure-float device value; the type is a *parallel* decoding rendered by `canlib/decode_value.py`. `ascii`/`date`/`struct` render text/date/record; `struct`'s ordered `fields:` are authored in YAML today. **After a successful write, `upsert-param` echoes the new expression's decoded value RANGE across existing captures** (e.g. `captures: 16h — 20h`, or a yellow `captures: constant 40 (check the offset if you expected variation)` / `captures: ERROR …`) — a passive sanity-check so a wrong byte offset (e.g. a WiCAN `Bnn` landing on an ISO-TP PCI framing byte, which reads a spurious constant) surfaces at write time instead of being silently persisted; `(no captures … yet)` when the PID has none. It never fails the write. **Remember WiCAN `Bnn` includes ISO-TP PCI bytes** (B00/B01 = FF PCI, B08/B16/… = CF PCI; SID at B02) — it is NOT the SID-first reassembled-payload index; confirm an offset with `canair bix -a HEX --ecu … --pid …` or `canair decode … --dump-bytes` (whose column headers are the correct WiCAN `Bnn`) before authoring), `rename-param ECU PID OLD NEW` (rename a param key; fields/formatting preserved — **warns when a `vehicle_states.yaml` `when:` predicate reads the old name**, since the rename would silently disable that state; same warning on `rm-param`), `rm-param ECU PID NAME` (remove a param — when it is the PID's LAST parameter the now-empty `parameters:` block is dropped entirely, leaving a valid identity-only PID rather than an empty `parameters:` that fails the schema), `add-pid ECU PID [--status active|draft|static|ignored (default draft) --prereq STATE … --period MS --notes …]` (create a new **parameter-less** PID — a discovery/identity placeholder like a not-yet-decoded `21F2` — so a bare-ECU capture (`canair read ECU`) polls it; a bare-ECU query polls only *defined* PIDs, so an undiscovered page must be added here first. Defaults to `draft` (swept/queryable but not shipped to the device); scaffolds the `pids:` section if the ECU has none; refuses an existing PID — use `upsert-param`/`set-pid-status` to edit one), `rename-pid ECU OLD NEW` (rename a PID key, e.g. `B002`→`22B002`; status/params/formatting preserved), `rm-pid ECU PID` (remove a whole PID — drops the `pids:` section entirely if it was the last PID, leaving an identity-only ECU), `add-research ECU --type --target --status [--priority --prereq …]`, `set-status ECU TARGET STATUS [--type]`, `set-pid-status ECU PID {active|draft|static|ignored}` (PID lifecycle), `set-pid-variable-length ECU PID {true|false}` (flag a PID as legitimately returning variable-length responses, so a shorter payload isn't mistaken for a truncated ISO-TP read; `false` clears it), `set-pid-notes ECU PID [TEXT]` (set — or, with TEXT omitted, clear — a PID's free-text `notes:`, the record of what the page *is*; it goes stale as decoding progresses, so correcting it is a routine edit that previously had no surgical editor. An existing note is replaced in place; a new one is inserted above `parameters:`), `set-identity ECU FIELD VALUE` (set a curated identity field, e.g. `notes`; FIELD must be one the schema declares — a typo is now a validation *error*, so the edit is reverted rather than silently persisted), `rm-identity ECU FIELD` (remove an identity field — the inverse of `set-identity`, for dropping a value filed under the wrong field or mirrored into a second synonymous one; handles block-scalar `notes`, drops the whole `identity:` block if it was the last field, and errors on an absent field rather than silently no-op'ing), `set-can-bus ECU CODE [CODE …]` (set the ECU's physical CAN bus segment(s) — codes validated against the profile's own `can_buses.yaml` vocabulary, which is vendor-specific; Hyundai/Kia use `B-CAN`/`P-CAN`/`C-CAN`/`MM-CAN`/`H-CAN`/`D-CAN`/`ALL`; some ECUs span two, e.g. `H-CAN P-CAN`), `set-iocontrol-ranges ECU RANGE [RANGE …]` (set the ECU's `iocontrol_scan_ranges:` — the `"START-END"` hex DID ranges the `canair scan iocontrol` sweep covers; when unset, ranges are PID-derived from the ECU's `2F`/`22` keys, else the full DID space — the make-neutral replacement for the old hardcoded HK body-controller zones), `set-wake ECU --method rapid_read|session|relay [--prime-pid REQ --attempts N --interval-ms MS --sleep-timer-ms MS --session-mode XX --notes …]` (declare a per-ECU **wake ritual** for a fast-sleeping ECU — some modules, e.g. the SKM, power their CAN transceiver only briefly and sleep within ~1-2 s, so a single `1001` wake races the sleep timer; `rapid_read` fires a cheap full UDS `--prime-pid` request densely with a short per-prime timeout to hold the transceiver awake, then opens a session; honoured by `session <ECU> --wake` on **both** transports. Resolver `canlib/wake.py`; `method: relay` is the Ioniq SKM relay-wake, gated behind the `skm_wakeup` quirk), `set-addressing ECU [--mode --target-address --source-address --fc-id --rx-id]` (set an ECU's CAN addressing override — the make-specific knobs: the addressing `mode` (11-bit / the 29-bit modes / `normal_extended_11bit` for the BMW/PSA ISO-TP extended-11-bit target-byte scheme), the extended-mode ISO-TP extension bytes `target_address`/`source_address` (tester, default `0xF1`), a flow-control arbitration override `fc_id` (functional-TX / physical-RX ECUs, e.g. Renault/Mitsubishi), and/or the response-address `rx_id`; `canair ecu add` takes the same `--mode`/`--target-address`/`--source-address`/`--fc-id`/`--rx-id` to seed a 29-bit/extended ECU offline in one atomic write). Prefer this over hand-editing the rich per-ECU YAML. **Free-text `notes` (here and via `canair ecu add`/`discover --register`) auto-format**: a short note stays inline, a longer/multi-line one is written as a word-wrapped folded `>-` block (shared policy in `canlib/yaml_rt.py`, wrapping only the note — never reflowing the file). Pass plain strings; don't hand-format block scalars.
- **`canair signals`** — The domain-B analogue of `canair pids`: view/edit the broadcast signal-definition sidecar `signals/<bus>.yaml` (arbitration ID → named **linear** signals: `start_bit`/`length`/`byte_order`/`scale`/`offset`/`min`/`max`/`unit`/`verified`). `canair signals` / `signals list [BUS]` (list; `--json`), `signals upsert BUS 0xID NAME --start-bit --length [--byte-order --scale --offset --min --max --unit --verified/--unverified --notes --msg-name --tx-ecu]`, `signals rm BUS 0xID NAME`. Surgical, comment-preserving, validated (`canair validate signals`) + auto-reverted (via `canlib/signals_edit.py`). Never hand-edit `signals/`. Distinct from `pids` (freeform WiCAN `expression` over `Bnn`); this is the DBC-compatible linear model for passively-broadcast frames. (The `signals/` **schema** also accepts the same typed-decode fields as PID params — `type`/`values`/`bits`, decoded by `canlib/decode_value.py` — for enum/bitmask broadcast signals; the `signals upsert` CLI flags to author them are a follow-up, so typed broadcast signals are authored in YAML for now.)
- **`canair config`** — View and manage user config (`~/.config/canair/config.yaml`): transport block, `devices` (per-device `host`/`transport`/`port`/`bitrate`), `default_wican`, `default_profile`, `profiles_dir`, `grid_region`. Subcommands: `show` (default — config file locations + effective settings + resolved transport + devices + fallback status; `--json` keeps `wican.addresses` as `{alias: host}` for back-compat and adds a `devices` block + `fallback` block), `example` (print `config.example.yaml` — the authoritative, fully-commented reference for every key; force-included into the wheel so it's present in an installed copy too), `path` (print user config file path), `get KEY`, `set KEY VALUE` (dotted keys create nested mappings, e.g. `transport.type`, `devices.home.host`; int/**float**/bool coerced unless `--string` — non-finite floats stay strings; list-valued keys like `transport.fallback_order` accept a comma-separated value; reports the change as `key: old -> new` or "already … (unchanged)", validates enum keys `transport.type`/`devices.<alias>.transport`/`wican_model`/`grid_region` up front, warns on an unrecognized key, and warns that `wican_addresses.*` is deprecated in favor of `devices.<alias>.host` — noting it's ignored when a `devices:` block exists), `unset KEY`, `edit` (`$EDITOR`). Comment-preserving edits. Prefer this over hand-editing `config.yaml`. **`grid_region`** (`EU`/`UK`/`US`/`JP`/`CN`/`AU`, case-insensitive; presets in `canlib/grid_regions.py`) selects the mains-voltage/line-frequency **grid-axis** bands for the physical-value scan (`canair hunt --physical` / `investigate`) — a property of *where the car charges*, so it lives in user config (once per location, applies to every profile), not the profile; unset assumes EU (230 V/50 Hz) and the first physical scan offers to set it (one-shot TTY prompt / piped stderr note, via `canlib/grid_prompt.py`, sentinel `grid_region_prompted`).
- **`canair contribute`** (alias **`canair share`**) — Open a GitHub pull request contributing the **active** profile upstream (`philipkocanda/canair`), without the manual fork/clone/branch/push. Backed by the **GitHub CLI (`gh`)** — which also gives non-git-savvy users a browser/device-flow sign-in (`gh auth login`); when `gh` is missing/unauthenticated it prints platform-specific install instructions + `gh auth login` + the equivalent manual steps and exits without changing anything. **Storage-location-agnostic by design:** the profile is *copied* into `profiles/<name>/` inside a managed fork checkout (`~/.config/canair/contribute/canair/`, forked+cloned on first run via `gh repo fork --clone`, then fetch/reset to `upstream/main` on later runs), so it works identically whether the source profile is bundled in the repo, in `~/.config/canair/profiles/`, or at a `--path` bundle — a new profile shows as an added dir, edits to an existing one as a diff (append-only captures still union-merge upstream). Flow: `canair validate all` (refuses a broken profile) → **installed-snapshot guard** (warns + confirms when the active profile was read from a frozen `site-packages`/`uv tool`/`pipx` copy — a bare `canair` instead of `uv run canair` from a checkout — since that copy can be behind the checkout and ahead on captures from bare `--save`; `canlib/contribute.py::installed_snapshot_kind`) → **PII pre-flight** (`canlib/pii.py` — flags VIN/ECU-serial identity DIDs, VIN-shaped payloads, and emails/phone-ish/VIN text in labels/notes/`car_model`; requires confirmation) → **workspace self-collision guard** (`canlib/contribute.py::workspace_collision` — **hard-refuses** (not `--yes`-overridable) when the active profile IS the workspace's own copy of it, i.e. canair is running from *inside* the managed contribution clone, so source == copy destination; warns + confirms when the profile merely lives somewhere under the workspace, since preparing the branch resets that checkout mid-run) → **rollback guard** (warns + confirms when the contribution would *remove* committed upstream lines from curated definitions `ecus/`/`profile.yaml`/buses/states/signals — which normally only grow, so a rollback signals a stale source; `canlib/contribute.py::definition_rollback`, heuristic via `git diff --numstat`) → branch → copy → commit → push to fork → `gh pr create`. Captures are **overlaid** onto the upstream copy at copy time (append-only, via `canlib/captures_merge.py::overlay_documents`), so a source that's behind upstream on captures never proposes deleting upstream sessions — and, unlike the symmetric merge-driver union, the overlay **preserves the upstream file's existing session order and leaves a capture log it adds nothing to byte-identical** (the canonical re-sort otherwise rewrote every dated file end-to-end, since sessions with no first-capture `time` sort by label; see `plans/2026-08-05-contribute-workspace-self-collision.md`). A capture file that can't be parsed on either side is skipped with a warning rather than overwritten. Captures included by default with a size guard; **`--no-captures`** ships definitions-only, **`--diff`** validates + prepares the workspace and prints the unified `git diff` of `profiles/<name>/` vs upstream (new files included) then stops (no commit/push/PR; `--json` emits it under `diff`, plus a `rollback` array), **`--dry-run`** prepares the branch+commit without pushing/PR, **`--yes`** skips prompts (agents/CI), **`--json`** emits `{branch, pr_url, findings, rollback, warnings, installed_snapshot, workspace_collision, …}`, **`--repo-dir PATH`** uses an existing checkout (fork as `origin`) instead of the managed clone, **`--branch`/`--title`/`--body`** override the generated defaults. The run prints **where it reads the profile from** (source profile path) and **where it stages/pushes** (the workspace checkout), and **prompts for confirmation before pushing** and opening the PR (declining leaves the branch prepared locally; `--yes` bypasses). Every `--json` payload carries the same identity base (`profile`/`source`/`branch`/`workspace`/`mode`/`include_captures`) plus a `warnings` array. Layering: `canlib/contribute.py` = git/gh orchestration (module-level `_run` wrapper — device-free-testable); `canlib/commands/contribute.py` = CLI surface + the pipeline and its actions (stage → review → submit); `canlib/commands/_contribute_gates.py` = the pre-flight policy (snapshot/validate/environment/capture-size/workspace/privacy gates); `canlib/commands/_contribute_report.py` = the human/`--json` reporting duality (`Reporter`, and `Stop` — raised by any gate to end the run). The shared upstream-repo constant lives in `canlib/constants.py::GITHUB_REPO` (also used by `canair update`).
- **`canair update`** — Update the CLI from its git-clone install. Locates the source clone (via uv's tool receipt `~/.local/share/uv/tools/canair/uv-receipt.toml`, falling back to the package repo root), reports current vs latest **released** version (GitHub Releases API) with a changelog link, then — after confirmation — **checks out that release tag** and reinstalls: `git fetch --tags` + `git checkout <tag>` + `uv tool install <clone-dir> --reinstall`. Checking out the advertised **release tag** (not fast-forwarding a branch to its HEAD) guarantees the installed code is exactly the released version — never whatever unreleased commits happen to sit on `main`; consequently it **refuses to update when the latest tag can't be determined** (GitHub unreachable), since there's no version to check out (`--check` still reports offline). The reported **current** version is the provenance-bearing `build_info.full_version()` (branch + short commit from a checkout) while the release comparison runs on the pure `canlib.__version__`. **Also reports the install context** (`canlib/install_context.py`): *which* copy is running — the **repo working tree** (`uv run` / dev checkout) vs the **`uv tool install` snapshot** (bare `canair`) vs some other install — plus the clone's **current git HEAD** (branch name, e.g. `main`, or `detached at <tag>` after an update — surfaced as `clone_head` in `--json`), and warns when the installed tool copy's version (read from its `canair-*.dist-info` metadata in the uv-tool venv) differs from the source clone's `pyproject.toml` version (**out of sync**: a bare `canair` would run different code than `uv run canair`). **When there's no newer release to check out but the tool copy is out of sync, `canair update` offers a reinstall-only resync** — `uv tool install <clone-dir> --reinstall` with no `git fetch`/`checkout` (the clone is already where it should be), bringing the bare `canair` back in line with the clone. `--check` reports only (no changes), `--yes/-y` skips the prompt (automation), `--json` for machine output (includes the full `install` block — `running_origin`/`running_version`/`running_build`/`clone_version`/`tool_version`/`out_of_sync`). Refuses to touch a dirty clone (won't clobber contributor work) and degrades to printing manual commands when no clone/`uv` is found. Backed by `canlib/update_check.py`, which also drives the **automatic once-a-day background check**: interactive runs kick off a short-timeout, fully offline-safe daemon-thread fetch (any failure is silently ignored, never blocks or fails a command), cache it to `~/.config/canair/update_check.json`, and print a one-line "update available" notice on the next run (also surfaced in `canair status`). The out-of-sync warning is also surfaced in `canair status`. Disable the network check with `check_for_updates: false` in config or the `CANAIR_NO_UPDATE_CHECK` env var.
- **`canair dtc`** — Read stored Diagnostic Trouble Codes (DTCs) for one ECU or `--all` (UDS `0x19` / KWP2000 `0x18`, auto-selected by `id_protocol`). Logs each scan to the profile's `dtc_log.yaml` (tag the entry with `--label` and the vehicle power state with `--state`, e.g. `--state 'plugged, charging'`) and reports what **changed** since the last scan (DTC *meanings* live per-ECU in each `ecus/<name>.yaml` `dtcs:` section; profile-wide `failure_types:` in `profile.yaml`); clear fault memory with `--clear` (`0x14`). Read-only unless `--clear` is passed.
- **`canair sniff`** — Passive CAN-bus sniffer (raw `slcan-tcp` backend **only** — asks to switch the device to `slcan` if needed). Live per-ID table (count/rate/last data/changed bytes) for discovering broadcast IDs the request/response path can't see; optional `.asc`/`.blf`/`.csv` frame logging via `--save`, plus `--filter`/`--listen-only`/`--duration`. Complements the active request/response tools which can't observe passive broadcasts.
- **`canair status`** (alias **`st`**) — Read-only snapshot of the configured transport, device mode, and reachability: "what am I talking to, in what mode, is it usable?". Also prints the running **canair version** (the provenance-bearing one from `canlib/build_info.py::full_version` — from a git checkout it carries the branch + short commit, e.g. `1.15.0+main.343b244`) and, when the WiCAN HTTP API answers, the device's **firmware/hardware version** (`fw_version`/`hw_version`/`git_version` from `/check_status`). Use before a session to confirm the device is in the expected protocol (`slcan` vs `auto_pid`). Also reports the **connection mutex** (a `Lock` line + a `lock` block in `--json`: `held`/`pid`/`cmdline`/`age_s`/`ours`/`steal_pending`) — read-only, probed without taking it (`canlib/lock.py::lock_state`).
- **`canair lock`** — Inspect/clear the **device connection mutex** (only one canair session may talk to the device at a time; `flock(2)` on `/tmp/wican-connection.lock`, released by the kernel when the holder exits — so a *dead* session never leaves a stale lock). A bare `canair lock` shows the holder (PID, command line, age, pending release request; `--json`), **`canair lock steal`** runs the **cooperative steal** (records a release request in `/tmp/wican-connection.steal`, waits, leaves the lock free — `--wait N`, `--yes`, `--json`), and **`canair lock kill`** signals a holder that won't release (`SIGTERM`, or `SIGKILL` with `--hard`; confirms unless `--yes`, and **refuses a PID whose command line shows it is not canair** — recycled-PID safety). Exit 0 = free/freed, 1 = still held. **canair never kills another process on its own**: `--force` on any live command asks the holder to leave (steal request) and polls for up to `FORCE_WAIT_S` (10s), then gives up naming the PID and the exact `kill` to run — it never blocks indefinitely (the old `--force` called blocking `flock(LOCK_EX)` and hung forever against a live holder). The holder side is the **watchdog** (`canlib/lock_watchdog.py::LockWatchdog`, started by `run_live`/`sniff`): a daemon thread polling `WiCANLock.still_ours()` (release request aimed at us / a foreign holder PID / the lock file removed-or-replaced) that self-`SIGTERM`s into the normal graceful shutdown — so an **orphaned session** (terminal gone, no `SIGHUP` ever delivered) stands down instead of holding the device hostage. Steal requests are **target-scoped** (`target=<holder pid> by=<pid> at=<epoch>`) and TTL'd (`STEAL_TTL_S`), so a leftover request can never abort an unrelated later session. Stop signals are unified in `canlib/stop_signals.py` (`graceful_stop`/`graceful_stop_async`): **`SIGTERM` *and* `SIGHUP`** (plus Ctrl-C) all reconcile the `--save` journal and release the connection — the monitor TUI routes them through its own quit action, so Textual tears down cleanly. A `kill -9`'d session's data is still recoverable with `canair captures uds --recover`.
- **`canair logs`** — View the **central diagnostics event log** (`~/.config/canair/logs/canair.log`), a single **size-rotated** file (small `maxBytes` + a few backups → self-cleaning, never grows unbounded) where transport faults are collated: dropped/stale ISO-TP frames, timeouts, bus errors, decode failures (classified via `canlib/uds_parse.py::classify_response` into `drop`/`stale`/`no_data`/`bus`/`decode`), plus unexpected internal exceptions (`log_exception`). Each line is `TS LEVEL category transport=… ecu=… pid=… :: detail`. `canair logs` tails the last N lines (`-n`, `-n 0` = all, reads across rotated backups), `--path` prints the file path, `--json` emits parsed fields (`parse_event_line`), `--clear` deletes the log + backups (`--yes` to skip the confirm). The event log is written by the per-exchange diagnostics recorder (`canlib/transport_stats.py::TransportStats`, attached as `.diag` on both terminals + the raw client) — the same tally that drives the monitor's live **drops** indicator and recorded-capture **quality** provenance.
- **`canair ecu`** — Inspect the profile's ECU registry (aggregated from the per-ECU `ecus/` files) and per-ECU stats (PID/param/verified counts, protocol, addresses, **CAN bus segment(s)**) via `canair ecu` / `canair ecu <ECU>` (the `show` kind). The list view has a **BUS** column (the ECU's `can_bus` codes) and takes **`--sort {bus,name,tx,proto,pids,verif,caps,states}`** — **defaults to `bus`** (group the table by segment, unbussed ECUs last); string/hex columns (`bus`/`name`/`tx`/`proto`/`states`) sort ascending, numeric columns (`pids`/`verif`/`caps`) descending, with `name` as the tie-breaker; the detail view resolves each code to its human name from `can_buses.yaml` (e.g. `H-CAN (Hybrid CAN)`). Pass **`--states`** to add a **STATES** column — the vehicle states each ECU is readable/awake in, resolved from its ECU-level `vehicle_states` or (when unset) the union of its PIDs' (via `canlib/states.py::ecu_states`); `--sort states` auto-enables the column. The reverse view is **`canair states <STATE>`** (below). **`canair ecu <ECU> pids`** is a compact per-PID view listing every defined PID with its **latest decoded state** (the most recent capture's decoded param values — never raw hex; `--json` supported), pointing at `canair captures`/`canair decode` for full history/stats. **`canair ecu add TX [--name --description --id-protocol --rx-id --mode --target-address --source-address --fc-id --notes --overwrite --dir]`** registers a new ECU offline (no device) — the counterpart to `canair discover --register` for seeding a known ECU into a blank profile (`--rx-id` sets a non-standard CAN response address, e.g. XPeng `0x704`→`--rx-id 0x784`, for an ECU whose response addr isn't `tx_id` + the profile's `addressing.rx_offset`; `--mode`/`--target-address`/`--source-address`/`--fc-id` seed the addressing block so a 29-bit or extended-addressing ECU is created in one valid write); the write is validated + comment-preserving. Companion to `canair validate ecus`. **`canair ecu <ECU> edit`** opens the ECU's `ecus/<name>.yaml` in `$EDITOR` — a **TTY-only** human escape hatch for bulk/awkward edits the surgical `canair pids` subcommands don't reach; it refuses to run when stdin/stdout isn't a terminal (so agents can't drive it — use `canair pids …`/`canair ecu add` instead) and re-validates the edited file on exit (not auto-reverted — the user owns the edit).
- **`canair bus`** — Read-only list of the active profile's physical CAN bus segments from `can_buses.yaml`: each declared code with its human name, description, optional **bus speed** (the `bitrate` field, in bit/s, rendered as e.g. `500 kbit/s`), and the **number of ECUs** on it (an ECU spanning two segments counts on each; an ECU tagged with the gateway code **`ALL`** bridges every segment, so it's counted on each declared bus — including the diagnostic bus — not just a lone `ALL` row, with a footnote noting how many gateway ECUs were fanned out). Flags any **undeclared** codes (used by an ECU but absent from the vocabulary) and counts **unbussed** ECUs, prints the source file path at the bottom, and colors output on a TTY only (`--json` for machine output). The read-only companion to `canair pids set-can-bus` (which edits an ECU's `can_bus`).
- **`canair states`** — List and edit the active profile's **vehicle operating-state vocabulary** (`vehicle_states.yaml`) — the state-axis analogue of `canair bus`. A bare `canair states` lists each declared state with its description, whether it's **auto-suggested** (has a `when:` predicate, shown ● + the predicate — or **`✗` + the reason** when that predicate references a signal the registry doesn't define, so a permanently-dead predicate can't hide behind a healthy ●; `--json` carries a per-state `broken` array), and the **number of references** to it across `ecus/` (ECU/PID/DID/iocontrol/research/scan_log `vehicle_states:` fields); it also surfaces **undeclared tokens** (used in `ecus/` but absent from the vocabulary) and the source path (`--json` for machine output). A bare token — **`canair states <STATE>`** (e.g. `canair states READY`) — is the reverse lookup: it lists which **ECUs are readable/awake in that state** (matched on the ECU-level `vehicle_states`, else the union of its PIDs'; an ECU tagged `ALL` matches every state), each with its TX/CAN-bus and the match `source` (`ECU-level`/`via PIDs`/`ALL`); `--json` supported, an unknown state errors with the known vocabulary. Backed by `canlib/states.py::ecu_states`/`ecus_in_state` (the same resolver `canair ecu --states` uses). State names are an **UPPERCASE** controlled vocabulary (like the CAN-bus codes) — the make-neutral base is the **ignition-switch ladder `SLEEP/ACC/RUN/CRANK`** (the universal OFF/ACC/ON/START positions — `RUN`/`SLEEP` because `ON`/`OFF` are YAML booleans, and `RUN` reads unambiguously where a bare `IGN` invites "which IGN level?") plus the **`ALL`** meta-token ("applicable/readable in every state"; documentary, no predicate — the state analogue of the `ALL` bus code). EV states (`PLUGGED`/`READY`/`CHARGING` — `READY` is the EV name for the driveable state) and finer vendor-specific ignition rungs (Hyundai's numbered `IGN0-3`/split `IGN1`/`IGN2`, an `ACC2` sub-level) are **not** baked into the tool base — a profile declares them in its `vehicle_states.yaml` (the bundled Ioniq does), and `allowed_states()` returns base ∪ `ALL` ∪ the profile's own. The `--prereq`/`--vehicle-states`/`--states` flags validate against that profile-aware vocabulary (no static choice list). Input is normalized to uppercase everywhere, so any casing on `--state`/`--prereq`/`--states` is accepted. Edit subcommands (surgical, comment-preserving, re-validated, auto-reverted via `canlib/states_edit.py` — never hand-edit `vehicle_states.yaml`): `add NAME [--description --when EXPR]`, `rm NAME`, `rename OLD NEW` (renames the vocabulary entry only — existing `ecus/`/`captures/` references keep the old token, so re-run `scripts/migrate_states_uppercase.py`-style fixups or edit them), `set-description NAME [VALUE]` (omit to clear), `set-predicate NAME [EXPR]` (omit to clear; `when:` syntax-checked, and its `ECU.PARAM` references cross-checked against the registry as a non-blocking warning — `canair validate states` is the hard gate). `vehicle_states:` fields are written as **inline flow lists** (`[SLEEP, PLUGGED]`) for readability in the long per-ECU files.
- **`canair groups`** — List and edit the active profile's **capture/monitor selector groups** (`groups.yaml`) — named, reusable *saved queries* (a list of ECU / `ECU:PID` selectors), recalled on the command line with the **`@` sigil** (`canair monitor @charging`, `canair read @driving CLU:220B`). A group reference is expanded **textually before the query parser** (`canlib/ecu_groups.py::expand_group_refs`, wired into `read`/`monitor` via `_live.expand_step_groups`), so it composes with other groups and with ad-hoc selectors; expansion is per-step (identical selectors de-duped within a step). Members are plain selectors (never other groups, never full pipeline steps) and carry no PID suffix (`@charging`, not `@charging:2101`). A bare `canair groups` lists the vocabulary (member selectors + description, `--json`); edit subcommands `add`/`rm`/`rename`/`set-description`/`set-members` modify `groups.yaml` surgically (comment-preserving, re-validated, auto-reverted via `canlib/groups_edit.py`) — never hand-edit it. Group names are lower-case tokens (letters/digits + internal `-`/`_`). `canair validate groups` checks structure, member-selector syntax, and that each member's ECU exists. `@group` works in `canair read`/`canair monitor` today (analysis commands don't expand groups yet).
- **`canair import`** — Bring external CAN data into the active profile, split by the `uds`/`can`/`dbc` kind. **`import uds ECU:PID=PAYLOAD …`** is the domain-A device-free UDS capture import (documented above as its own entry). The domain-B (raw-CAN broadcast, `plans/2026-07-24-raw-can-analysis.md`) kinds: **`import can <FILE>`** reads a raw broadcast-CAN frame log (`.asc`/`.blf`/python-can `.csv`/candump `.log`/`.trc`/**SavvyCAN GVRET `.csv`**; `--format auto` by extension, `.csv` header-sniffed to tell GVRET from python-can CSV) via python-can's readers (GVRET via a built-in adapter), stores it **verbatim** in `captures/can/`, and appends a metadata entry (`frame_count`, `id_set`, `bitrate`, `date`, `label`, …) to `captures/can/index.yaml` — flags `--label`/`--state`/`--notes`/`--source`/`--bitrate`/`--date`/`--force`/`--json`. High-volume logs stay native (not exploded into `captures/*.yaml`). **`import dbc <FILE> [--bus --tx-ecu --ids --dry-run --json]`** imports a DBC's broadcast signal definitions into the profile's `signals/<bus>.yaml` (cantools, `strict=False` to tolerate real-world overlapping-signal DBCs; `--dry-run` previews). List imported logs with **`canair captures can`**. Module is `commands/import_.py` (`import` is a keyword); `NAME="import"`; the `uds` kind lives in `commands/import_uds.py`. Fetch the reference corpus with `scripts/fetch_can_corpus.py` (into gitignored `references/can/`). **`import uds ECU:PID=PAYLOAD …`** is the domain-A device-free UDS capture import (documented above as its own entry). The domain-B (raw-CAN broadcast, `plans/2026-07-24-raw-can-analysis.md`) kinds: **`import can <FILE>`** reads a raw broadcast-CAN frame log (`.asc`/`.blf`/python-can `.csv`/candump `.log`/`.trc`/**SavvyCAN GVRET `.csv`**; `--format auto` by extension, `.csv` header-sniffed to tell GVRET from python-can CSV) via python-can's readers (GVRET via a built-in adapter), stores it **verbatim** in `captures/can/`, and appends a metadata entry (`frame_count`, `id_set`, `bitrate`, `date`, `label`, …) to `captures/can/index.yaml` — flags `--label`/`--state`/`--notes`/`--source`/`--bitrate`/`--date`/`--force`/`--json`. High-volume logs stay native (not exploded into `captures/*.yaml`). **`import dbc <FILE> [--bus --tx-ecu --ids --dry-run --json]`** imports a DBC's broadcast signal definitions into the profile's `signals/<bus>.yaml` (cantools, `strict=False` to tolerate real-world overlapping-signal DBCs; `--dry-run` previews). List imported logs with **`canair captures can`**. Module is `commands/import_.py` (`import` is a keyword); `NAME="import"`; the `uds` kind lives in `commands/import_uds.py`. Fetch the reference corpus with `scripts/fetch_can_corpus.py` (into gitignored `references/can/`).
- **`canair export`** — Export canair data to interchange formats. **`export dbc [--bus --verified-only -o FILE]`** writes the profile's `signals/` broadcast definitions to a DBC (cantools) for SavvyCAN/cabana/Wireshark; round-trips with `import dbc`. (Domain-A decoded-value CSV/JSON export is future work.)

### Profiles

Vehicle data lives in a **profile** bundle — a directory with `ecus/` (one file per ECU — the source of truth), `profile.yaml` (profile-wide settings), `captures/`, `references/`, `vehicle_states.yaml`, and generated `out/`. The repo bundles one or more profiles under `profiles/` (the mature `profiles/ioniq-2017/` is the reference example; `profiles/ioniq-5-2022/` is an early seed). Since more than one profile ships, none is auto-selected — set `default_profile` in config (the bundled `config.example.yaml` sets it to `ioniq-2017`) or pass `--profile`. Selection precedence: `--profile NAME|PATH` (global flag, before the subcommand) > `CANAIR_PROFILE` env var > `default_profile` in config > single discovered profile (auto). Profiles are discovered from `--profiles-dir`, `$CANAIR_PROFILES_DIR`, `profiles_dir` in config, `~/.config/canair/profiles/` (user, uncommitted), and the repo's bundled `profiles/`; user profiles shadow bundled ones by name. Inspect with `canair profile` (alias **`prof`**) `list` / `show [NAME]` (lists every bundle component — `profile.yaml`, `ecus/`, `vehicle_states.yaml`, `can_buses.yaml`, `groups.yaml`, `signals/`, `captures/` + `captures/can/`, `references/`, `dtc_log.yaml`, `out/`; the component list is not hand-written — it is driven by the **`BUNDLE_MEMBERS` registry** in `canlib/profile.py`, the single declaration of what a profile is made of, which also decides what `canair contribute` ships and what the blind-test strip withholds, so a new bundle member is one edit there) / `path [NAME]`; set the config default with `canair profile use NAME` (an alias for `canair config set default_profile NAME`, validated against discovered profiles). A **bare `canair profile` opens an interactive arrow-key picker on a TTY** (↑/↓ move, Enter sets it as `default_profile`, q/Esc cancels; built on `canlib.tui.select_from_list`); piped/non-interactive it prints the plain list (and hints `profile use` when no default is set). Scaffold a new vehicle with `canair profile create <name> --car-model "…"` (creates `profile.yaml`, empty `ecus/`, `captures/`, `out/` under `~/.config/canair/profiles/<name>` or `--path DIR`; `--set-default` to adopt it).

> **Pass `--profile NAME` explicitly on every *mutative/authoring* command** — anything that writes into a profile: `pids upsert-param`/`rename-*`/`rm-*`/`add-research`/`set-*`, `signals upsert`/`rm`, `import uds`/`import can`/`import dbc`, `discover --register`, `ecu add`, `wican autopid write`, and `--save` reads. Without `--profile` these write to the **active profile**, which is whatever `default_profile` (or `CANAIR_PROFILE`) resolves to — **not necessarily the car you mean**. This is exactly how Ioniq-28-derived `WHL_SPD11` signals once landed in `profiles/ioniq-5-2022/` instead of `ioniq-2017/` (a `signals upsert`/`import dbc` run with `default_profile: ioniq-5-2022` and no `--profile`; fixed in the git history). `canair signals`/`import` echo the target profile + full path on write — read it back to confirm. Read-only commands (`decode`/`correlate`/`hunt`/`captures`/`validate`/`ecu`…) are lower-stakes but still resolve the same way, so prefer explicit `--profile` there too when a specific car is intended.

## Key Files

- **`profiles/ioniq-2017/ecus/`** — SOURCE OF TRUTH, one file per ECU. Each `ecus/<name>.yaml` fully describes one ECU: `identity:` (name is the file's top key), `tx_id:` (request arbitration ID — 11-bit `0x000-0x7FF`, or a full 29-bit id like `0x18DA10F1` when the profile/ECU addressing mode is 29-bit), optional `rx_id:` (CAN response address override — defaults to `tx_id` + the profile's `addressing.rx_offset`, itself defaulting to `+0x08`, or the byte-swapped id for `normal_fixed_29bit`; set only for an ECU whose response address doesn't follow the profile rule), optional `addressing:` (per-ECU override of the profile addressing mode — `mode:` plus the make-specific knobs `target_address`/`source_address` (extended-11-bit BMW/PSA) and `fc_id` (functional-TX flow-control override); edit via `canair pids set-addressing`), `can_bus:` (physical CAN bus segment(s) — a flow list of codes like `[B-CAN, P-CAN]` drawn from `can_buses.yaml`; Hyundai/Kia use `B-CAN`/`P-CAN`/`C-CAN`/`MM-CAN`/`H-CAN`/`D-CAN`/`ALL`; edit via `canair pids set-can-bus`), optional `wake:` (a per-ECU **wake ritual** for a fast-sleeping ECU — `method` + `prime_pid`/`attempts`/`interval_ms`/`sleep_timer_ms`/`session_mode`; edit via `canair pids set-wake`; resolver `canlib/wake.py`), `scan_log:` (probe history), `dtcs:` (DTC meanings), `pids:`, `iocontrol:`, `iocontrol_scan_ranges:` (optional `"START-END"` hex DID ranges the `canair scan iocontrol` sweep covers — edit via `canair pids set-iocontrol-ranges`), `routines:`, `research:`. Identity-only modules (AMP/SRS) have no `pids:`. Validate with `canair validate pids` (alias `ecus`); `--stats` for counts
- **`canair validate`** (alias **`val`**) — Schema validation with a positional target: `canair validate pids|captures|ecus|states|can-buses|signals|groups|can|all` (default `all`). Add `--stats` for a count summary (ECUs/PIDs/params/verified/research items). Schemas are tool-owned in `canlib/schema/` (`pids_schema.yaml` — covers the per-ECU files incl. identity/scan_log/dtcs, `captures_schema.json`, `states_schema.yaml`, `can_buses_schema.yaml` — per-profile CAN bus vocabulary, `signals_schema.yaml` — broadcast signal maps, `groups_schema.yaml` — selector-group vocabulary, `can_index_schema.json` — raw-CAN log index). `validate can-buses` (per-profile `can_buses.yaml`), `validate signals` (broadcast `signals/<bus>.yaml` domain-B maps), `validate groups` (per-profile `groups.yaml` — structure + member-selector syntax + member-ECU existence) and `validate can` (`captures/can/index.yaml` raw-CAN log index) gracefully skip when absent (all optional). `validate ecus` is an alias for `validate pids`. **`validate states` cross-references every `when:` predicate's `ECU.PARAM` references against the `ecus/` registry and ERRORS on one that cannot resolve** — this is the *only* place a renamed/typo'd signal name in a predicate is caught, because Kleene evaluation makes it silent (a missing signal is `UNKNOWN` exactly like a not-polled one, so the state simply never gets suggested; that is how a `GEAR_PARK` rename disabled `PARKED` with `validate all` green). Resolution mirrors how the decoded value map is keyed at evaluation time, and each way of missing is reported distinctly: unknown ECU, an ECU **alias** instead of the canonical short name, a lower-case ECU (the map is keyed UPPERCASE), a case-mismatched signal name (matched case-sensitively — the real name is suggested), a signal defined on a *different* ECU, a signal under a `status: ignored` PID (never polled), and a signal that doesn't decode to a number (`ascii`/`date`/`struct` render as text; only numerics reach a predicate). The `__no_response__`/`__responded__` sentinels are not signals and are never resolved. The check skips **out loud** (a printed reason, never silently) when `ecus/` can't be loaded or has no ECUs yet. Resolver `canlib/state_refs.py` (`check_references`/`states_referencing`/`profile_predicates`), reference extraction `canlib/states.py::predicate_references`, the "does this signal decode to a number" invariant `canlib/decoding.py::decodes_to_number`. The same check runs as a **non-blocking warning** at the moments a reference can break — `canair states add --when`/`set-predicate` (authoring a predicate before its signal exists stays allowed), `canair pids rename-param`/`rm-param` (names the states that read the signal you just renamed/removed), and `canair states` marks a dead predicate `✗` instead of `●` with the reason under it (`--json`: a per-state `broken` array). **`validate pids` also errors on a duplicate *shipped* parameter name across PIDs** (a device signal-name collision — each `active`+`enabled` param becomes a distinct device signal, so names must be unique; caught here rather than only at `wican autopid write`). **An `identity:` field name outside the schema's `identity_fields` is an ERROR** (not a warning) — so a typo'd `pids set-identity` is reverted by the editor's validation gate instead of silently persisting; and `validate pids` **warns when two *synonymous* identity fields hold the same value** (the `firmware`/`fw_version`/`sw_version`/`sw_id`, `hw_version`/`hw_sw`, `alias`/`description`, `part_number`/`serial`/`ecu_id` groups in `_IDENTITY_SYNONYM_GROUPS`) — the near-synonymous version fields make it easy to mirror one DID reading into a second field, leaving dead data; the check is per-group on purpose, so a genuine cross-axis coincidence (`hw_version: "100"` + `sw_version: "100"`) does not warn. `validate captures` also emits **soft warnings** for (a) session `vehicle_states` outside the profile's `vehicle_states.yaml` vocabulary (free text still accepted), (b) **echo mismatches** — a stored capture whose payload's SID/PID/DID echo doesn't match its recorded `pid` (a stale/misfiled frame, e.g. a `6101…` payload filed under a `2102` request; the expected Hyundai/Kia `-1` identity-DID offset is tolerated only when the profile declares the `hk_f1xx_minus_one` quirk), (c) **non-hex payloads** — a capture payload that isn't a valid UDS byte string (an ELM327 status string like `NO DATA`, free text, or a mixed hex+ASCII transcription), and (d) **untimed payload captures** — a `payload` (time-series) capture with no usable `time`, which is excluded from time-aligned cross-signal analysis (`scan_results` captures are exempt; existing untimed rows are grandfathered), and (e) **degraded-transport sessions** — a session whose recorded `quality` shows dropped/stale ISO-TP frames (`drop`/`stale` > 0), flagging that its multi-frame payloads may be unreliable (non-answer categories no_data/bus/decode don't warn — nothing was stored). Pass `--strict` to promote the untimed-payload warning to an error (CI / new-data gate).
- **`profiles/ioniq-2017/captures/`** — Raw UDS response payloads, split by date (e.g. `2026-04-19.json`). Stored as **JSON** (`captures/YYYY-MM-DD.json`) — parses ~60x faster than YAML, the dominant cost of every history-consuming command). The read/write seam is `canlib/capture_io.py`; there is **no YAML fallback** — a profile created before the cutover fails fast with an actionable error and is converted once via **`canair captures migrate`** (`--dry-run` to preview). These files are **append-only session logs**, so same-day recordings from two machines merge via canair's git merge driver (`canair captures merge-driver`, `.gitattributes` rule `profiles/*/captures/*.json merge=canair-captures`) — run **`canair captures merge-driver --install`** once per clone to register it (until then git just falls back to conflict markers). Schema in `canlib/schema/captures_schema.json` (tool-owned, format-agnostic — validates the parsed structure; the human companion is `docs/concepts/captures-and-states.md`), with matching Python `TypedDict`s in `canlib/capture_types.py` (`CaptureFile`/`CaptureSession`/`CaptureRecord`/`ScanResults`/`RespondingEntry`/`Quality`) that the builders/IO are typed against (enforced by `ty`). Each capture's `rx` field is the ECU CAN **response** address (RX = request TX + 8, e.g. `0x7EC`; `broadcast` for multi-ECU scans) — it was renamed from `ecu` → `rx`; read it via `capture_io.capture_rx` (tolerates the legacy key) and rename old files with `canair captures migrate-rx`. A capture may also carry an optional **`elapsed_ms`** (wall-clock UDS round-trip in ms — a *relative* speed signal, transport + ECU, not pure ECU time), recorded **only for single per-DID reads** on the live `read` path (batched multi-DID reads, `monitor --save`, scans, and imports omit it); comparable only within the same session `transport`. Measured in `modes/multi_exec.py::_read_single_pid`, threaded via `ResultEntry.elapsed_ms` → `journal.append(elapsed_ms=…)` → `build_query_session`. Validate with `canair validate captures`. **NEVER hand-write or edit these files.** Record device reads via `canair read … --save` with `--label`/`--state`/`--notes` (non-interactive), e.g. `canair read "query MCU" "query VCU:2101" --wican vpn --save --label "…" --state "ready, parked" --notes "…"`. `--save` works with `canair monitor`/`scan`/`raw`/`discover`, positional query/raw steps. **When there's no device on hand** (e.g. a reading pasted from a forum/issue), onboard it with `canair import uds ECU:PID=PAYLOAD --label … --state …` — same machinery, no live bus. Saves are **journaled** to `captures/.journal/` (JSONL) as they stream and reconciled into the per-day JSON on exit; recover a killed session's leftovers with `canair captures uds --recover`. For edits/removals use `canair captures uds --delete <query>` (`--dry-run`/`--yes`) or the `canlib.captures` helpers (`set_capture_note`, `delete_capture`). **Truncated multi-frame reads are rejected at capture time** — `parse_uds_response` compares the reassembled length to the ISO-TP First-Frame declared length (exposed by the ELM327 terminal as a bare `NNN` line) and drops a short read (`truncated ISO-TP: got N, declared M`) so a misaligned payload is never saved; the check is generic (no per-PID length table). **After adding captures, run `canair captures uds --summary` to check for new patterns.**
- **`profiles/ioniq-2017/vehicle_states.yaml`** — Canonical, ordered vehicle operating states (**UPPERCASE** controlled vocabulary — `SLEEP/PLUGGED/ACC/ACC2/READY/CHARGING` + composites + the `ALL` meta-token), each with an optional `when:` predicate over decoded `ECU.PARAM` values used to **auto-suggest** a capture's `vehicle_states` (evaluated with three-valued/Kleene logic — a predicate on an unpolled param abstains rather than reading false; every matching predicate contributes, so a session is composite, and predicate order is display-only, not priority; offline back-fill via `canair captures uds --backfill-states`) (see `canlib/states.py`). Inspect/edit with **`canair states`** (never hand-edit; surgical editor in `canlib/states_edit.py`). References to states in `ecus/` are written as **inline flow lists** (`vehicle_states: [SLEEP, PLUGGED]`). Schema `canlib/schema/states_schema.yaml`; validate with `canair validate states` — which also **resolves each predicate's `ECU.PARAM` references against the `ecus/` registry** and errors on one that cannot resolve (Kleene evaluation makes a renamed/typo'd signal name silent, so this static check is the only thing that catches it; resolver `canlib/state_refs.py`). `canair validate captures`/`validate pids` compare tokens **case-insensitively** and soft-warn / error on values outside the vocabulary. New profiles are scaffolded with a starter `vehicle_states.yaml`. Migrate a legacy lowercase/block-style profile with `scripts/migrate_states_uppercase.py`.
- **`profiles/ioniq-2017/can_buses.yaml`** — Per-profile physical CAN bus segment vocabulary: each bare code (`B-CAN`/`P-CAN`/`C-CAN`/`MM-CAN`/`H-CAN`/`D-CAN`/`ALL` for Hyundai/Kia) maps to a human `name` + `description` + an optional `bitrate` (segment bus speed in bit/s, e.g. `500000`), shown by `canair bus`/`canair ecu`. Bus naming is **vendor-specific** (Ford `HS`/`MS`; BMW `PT-CAN`/`K-CAN`), so it lives per profile, not in a global enum. ECU `can_bus:` lists are written in the readable flow form (`can_bus: [B-CAN, P-CAN]`) by `set-can-bus`. Schema `canlib/schema/can_buses_schema.yaml`; validate with `canair validate can-buses` (errors on a non-positive-integer `bitrate`); loader `canlib/can_buses.py` (`load_can_buses`/`allowed_can_buses`/`bus_names`; `BusDef.bitrate`). `canair pids set-can-bus` accepts only declared codes and `validate pids` errors on an out-of-vocabulary value. New profiles are scaffolded with a starter `can_buses.yaml` (`All` + commented placeholders). (A legacy bare-list form is still accepted.)
- **`profiles/ioniq-2017/groups.yaml`** — Per-profile **capture/monitor selector groups**: a `groups:` mapping of lower-cased group name → `{description, members}`, where `members` is a list of ECU / `ECU:PID` selectors (a bare-list shorthand `name: [SEL, …]` is also accepted). Recalled on the command line as `@name` in `canair read`/`canair monitor` (expanded by `canlib/ecu_groups.py::expand_group_refs` before the query parser). Inspect/edit with **`canair groups`** (never hand-edit; surgical editor in `canlib/groups_edit.py`). Schema `canlib/schema/groups_schema.yaml`; validate with `canair validate groups` (member ECUs must exist). Loader `canlib/ecu_groups.py` (`load_groups`/`allowed_groups`/`group_members`). New profiles are scaffolded with an empty `groups.yaml`; the bundled Ioniq ships `@charging`/`@driving`/`@powertrain`/`@climate`/`@body`.
- **`profiles/<name>/signals/` and `profiles/<name>/captures/can/`** — the raw-CAN broadcast domain (in progress, `plans/2026-07-24-raw-can-analysis.md`), both optional/absent today. `signals/<bus>.yaml` holds DBC-compatible **linear** broadcast signal maps keyed by arbitration ID (schema `canlib/schema/signals_schema.yaml`; `canair validate signals`); `captures/can/` holds imported raw frame logs natively (`.blf`/`.asc`/`.csv`) indexed by `captures/can/index.yaml` (schema `canlib/schema/can_index_schema.json`; `canair validate can`). Distinct from domain-A diagnostic `captures/*.json` + freeform-WiCAN-`expression` PID params. Profile path accessors: `Profile.signals_dir` / `.can_dir` / `.can_index_file`. **Storage/licensing policy** (`.gitattributes` + docs/concepts/broadcast-frames.md → "Storing raw-CAN logs"): a profile's **own** `captures/can/` logs are committed **fully** — via **Git LFS** when large (`.gitattributes` tracks `*.blf`/`*.asc`/`*.trc` + `profiles/*/captures/can/**`; `tests/fixtures/**` is explicitly excluded so the tiny excerpts stay plain, diffable git). **Third-party** logs are committed only when their license permits redistribution (recorded alongside); **unlicensed** corpora (the uhi22 Ioniq-28 data) stay **fetch-on-demand** in gitignored `references/can/` (`scripts/fetch_can_corpus.py`) + a minimal fair-use excerpt in `tests/fixtures/can/`. LFS is storage only — it grants no redistribution right, so it never changes the license question. Contributors need `git lfs install`.
- **`profiles/ioniq-2017/references/`** — External reference material (other-vehicle logs, spreadsheets, SavvyCAN exports, charge-curve data) used to cross-reference RE work. Distinct from the per-ECU `research:` backlog sections inside `ecus/` (surfaced by `canair research`).
- **`profiles/ioniq-2017/profile.yaml`** — Profile-wide settings: `car_model`, `init` (ELM327 AT string, `wican-ws` transport only), `response_timeout_ms`, `multi_did_batching`, `multi_did_max` (cap on DIDs combined per multi-DID request, default 3; per-ECU `multi_did_max` overrides), optional `can_bitrate` (vehicle bus speed in bit/s; precedence config `transport.bitrate` > profile `can_bitrate` > device config > 500000), optional `addressing:` block (CAN diagnostic addressing rule — `mode:` selects `normal_11bit` (default) / `normal_29bit` / `normal_fixed_29bit` (the ISO `0x18DA{target}{tester}` convention, Ford/VAG/etc.; RX derived by byte-swap, no offset) / `normal_extended_11bit` (ISO-TP extended/mixed 11-bit — an 11-bit header plus a per-ECU `target_address` byte in the payload, BMW `0x6F1` / PSA) / `extended_29bit`; `rx_offset:` sets 11-bit response = `tx_id + rx_offset`, default `0x08`, e.g. `0x80` for XPeng `0x704`→`0x784` (may be negative — PSA/Stellantis `-0x20`); the extended-mode ISO-TP extension bytes `target_address`/`source_address` (tester, default `0xF1`); a per-ECU flow-control arbitration override `addressing.fc_id` (functional-TX / physical-RX ECUs, e.g. Renault/Mitsubishi — FC goes to the physical id, not the functional TX); a single ECU overrides with its own `rx_id` and/or a per-ECU `addressing.mode`; resolver in `canlib/addressing.py` — `resolve_mode`/`resolve_rx`/`resolve_ecu_address`/`build_isotp_address` (the `EcuAddress` bundle), with the FC-address override in `canlib/transport/isotp_stack.py`), optional `isotp:` block (client-side ISO-TP tuning for `slcan-tcp` — `tx_padding`/`blocksize`/`stmin`/`rx_flowcontrol_timeout`/`rx_consecutive_frame_timeout`/`can_fd`/`tx_data_length`, defaults in `canlib/transport/isotp_params.py`; the padding byte drives multi-DID split/strip via `resolve_tx_padding`), optional `quirks:` list (make-specific behavior toggles the profile opts into — known: `hk_f1xx_minus_one`, the Hyundai/Kia identity-DID `-1` offset `22F188`→`62F187`; resolver `canlib/unit_guess.py::resolve_unit_candidates`), and DTC `failure_types:`. Only `car_model`+`init` are required; `canair validate` type-checks the rest.
- **`templates/`** (repo root) — Scaffold templates used by `canair profile create`: `profile.yaml.tmpl`, `vehicle_states.yaml.tmpl`, `can_buses.yaml.tmpl`. Placeholders use `string.Template` (`$car_model`, `$init`) so literal braces in YAML/comments never need escaping. Edit the scaffold output by editing these files, not Python strings.

- (There is no longer a top-level `ecus.yaml` or `dtc.yaml` — both were folded into the per-ECU `ecus/` files.)
- **`canair bix`** — Byte index converter: WiCAN ↔ ISO-TP ↔ Torque ↔ bix. A bare `canair bix` (no args) prints a **guided overview** — a plain-language legend for each notation and the `PCI`/`FF`/`CF`/`SID`/`PID`/`DID` Role labels, plus a compact 2-frame table (B00–B15) and next-step hints. Use `canair bix w9` or `canair bix E` for quick lookups, `--table` for the full table (**grouped by CAN frame** — `── Frame N ──` dividers between 8-byte blocks + a `Role` column marking the `FF PCI`/`CF PCI` framing and `SID`/`PID`/`DID` header bytes, so the raw CAN frame boundaries are visible; the legend is printed above it too; frame dividers/PCI rows are color-highlighted on a TTY, plain when piped). **By default `--table` and `--annotate` show only WiCAN + ISO-TP + Role** (the notations expressions use); the **Torque letter (`--torque`)** and **OBDb bix (`--obdb`)** columns are now **separate opt-in flags** (no longer aliases — they're different notations) for cross-referencing third-party PID sheets. Torque notation is used by the Torque app, **Car Scanner**, and similar OBD apps. **A single-index lookup (`canair bix w9`/`b32`/`E`) also reports the CAN frame the byte lands in** (e.g. `CAN frame: 1 (B08–B15)`). **`--annotate HEX` (`-a`)** maps a raw UDS response payload to a table with WiCAN Bnn, ISO-TP index, Torque letter, bix, and role per byte (multi-frame payloads get the same `── Frame N ──` boundary markers). It is **length-aware** — single-frame (≤7-byte) responses have one PCI byte at B00 (SID at B01), multi-frame responses two FF PCI bytes at B00/B01, and the ISO-TP/Torque/bix columns follow the *actual* frame layout (they no longer assume multi-frame, which was off-by-one for single-frame payloads). The **Torque column is Torque 1 (`-1`, 21xx PIDs) or Torque 2 (`-2`, 22xxxx DIDs)** — with `--torque`, annotate names the active variant so it's clear the Torque/OBDb mapping isn't fixed (it counts from the first UDS data byte, after SID + subfunction). The hex may be a no-space blob (`62B004…`), a quoted space-separated string (`"62 B0 04 …"`), or **unquoted space-separated bytes** (`-a 62 B0 04 …`) — all equivalent. Put the mode flag `-1` (21xx, default) / `-2` (22xxxx) **before** the bytes. **`--annotate` expects the reassembled UDS payload (SID-first, ISO-TP PCI stripped — what the transport/captures return); pass `--raw`/`--frame` to annotate an already-framed CAN payload (PCI present, e.g. straight off the bus) as-is.** It reliably warns when the input's first byte contradicts the mode — UDS response SIDs (`0x40`–`0x7F`) and PCI first-bytes (`0x00`–`0x3F`) are disjoint — so a raw frame fed without `--raw` (or a PCI-stripped payload with `--raw`) is caught, not silently mislabelled; a Flow-Control/invalid frame under `--raw` errors. Add **`--ecu ECU --pid PID`** to overlay which defined parameter (and bit `[NAME:k]`) maps each byte and flag `unmapped` data bytes — the fastest way to spot a wrong byte offset in an expression (how the BC05 `B09`→`B10` bug was caught). **`--pid` also derives the subfunction width** when it names its service (`22xxxx` DID → 2 bytes, `21xx` → 1 — the value comes from the same `canlib/notation.py::subfunction_bytes_for_pid` derivation every other command uses), so `bix -a HEX --ecu IGPM --pid 22BC03` needs no `-2`; a **short-form DID** (`B004` for `22B004`) states no service, so it is deliberately *not* treated as conclusive (no caption, and no false "contradicts" warning against a correct `-2`). **The strongest evidence is the payload itself: `--annotate` resolves the header from the response SID** via **`canlib/uds_layout.py`** (a `response_SID → [(role, width)]` table built on the `canlib/uds_services.py` registry), so every header byte is labelled for what it *is* — `DID` (UDS `0x22`/`0x2E`/`0x2F`), `LID` (KWP2000 `0x21`/`0x30`/`0x33`), `PID` (OBD-II mode `0x01`/`0x02`), `RID` + `SF` (`0x31` RoutineControl, whose sub-function comes **before** the routine id), `CTRL` (the IOControl parameter, **after** the DID), `REC`/`INFO`/`FRAME`, and for a negative response `REJ SID` + `NRC` (named from `uds_parse.NRC_CODES`, e.g. `NRC 0x31 requestOutOfRange`). This fixed real mislabelling: `7F 22 31` used to show the NRC as a data byte and `71 03 12 A1` split the RID across the header/data boundary. Resolution order is **explicit `-1`/`-2` > the payload's service > a conclusive `--pid` > 1**; an override that contradicts the payload's service (or the PID) is **warned about**, and a contradicting override falls back to the generic `SID` + `PID`/`DID` labelling since the layout implies its own width. A **definition list of just the roles the payload used** is printed under the table (`--no-legend` to suppress); the `LID` entry cross-references that canair writes these as `21xx` "PIDs" elsewhere. `canlib/uds_layout.py` also owns **`SUBFUNCTION_NAMES`** — the named sub-function/control values per request SID (session types incl. the KWP2000 `0x8x` range, reset types, DTC report types, CommunicationControl controlTypes, IOControl parameters, routine control types) — the single home for enums that were previously re-declared per consumer; `canlib/formatting.py::decode_uds_response` and `canlib/modes/sessions_scan.py::SESSION_NAMES` both read from it, and `tests/test_uds_response_decode.py` cross-checks the two layout models against each other (a response SID that `decode_uds_response` handles but `uds_layout` can't lay out fails the suite). An **unrecognised service** resolves to no layout and keeps the previous width-based behaviour rather than asserting a guess (OBD-II modes `0x05`/`0x06`/`0x08` are deliberately unregistered — their identifier is an O2-monitor id/MID/TID, not a PID). `--table` has no payload, so it keeps the abstract `sub_bytes` model.

## WiCAN Access

Devices are configured in `~/.config/canair/config.yaml` (a legacy repo-root `config.yaml` is still read for back-compat; both gitignored). Copy from `config.example.yaml`:

```yaml
devices:
  home:
    host: "10.0.2.86"       # Device on local LAN
  vpn:
    host: "192.168.3.2"     # Device via VPN
    transport: wican-ws     # optional per-device transport (slcan-tcp | wican-ws)
default_wican: home
```

Each device carries a `host` and optional per-device `transport`/`port`/`bitrate` (precedence: `--transport`/`--wican` CLI > device entry > global `transport:` block > default). The legacy flat `wican_addresses: {alias: host}` form still works when no `devices:` block is present and is **auto-migrated into `devices:` on first run** (comment-preserving, best-effort, one-line notice; module `canlib/devices_migrate.py`, hooked at CLI startup). Once `devices:` exists, `wican_addresses` is ignored (setting it via `canair config set` warns). Resolvers: `canlib/config.py::wican_devices` (authoritative device map + `DeviceEntry`), `fallback_settings`; `wican_settings` is a back-compat `{alias: host}` shim.

**Auto-fallback** — when the selected device is unreachable at connect time, canair tries the other configured devices (config `transport.fallback`, default true; `--no-fallback` per command). A short, configurable `transport.connect_timeout` (default 2.0s) is the per-device liveness probe; `transport.fallback_order` (optional, comma-separated via `config set`) sequences the fallbacks (the explicitly selected device is always tried first). Candidate resolution: `canlib/transport/config.py::resolve_transport_candidates` (`resolve_transport` = candidate[0]); connect-time selection: `canlib/transport/fallback.py::select_reachable_transport` (called at the top of `async_main` before the raw/elm branch, so a fallback can cross transports). A `wican-ws` device is skipped as a fallback on a `classic` WiCAN.

**`--wait` (all live commands)** — block on the initial connect, retrying **indefinitely** (Ctrl-C to stop) until a candidate comes online, then start — so `canair monitor @driving --save --wait` waits for the WiCAN and records the moment it appears. Backed by `canlib/transport/fallback.py::wait_for_reachable` (a bounded/forever loop around the same liveness probe), wired into `async_main` before transport selection.

**Mid-session reconnect / auto-failover (`canair monitor`)** — a monitor session that drops mid-run is **re-homed** rather than given up: it re-probes the reachable **same-transport** devices (raw↔raw / ws↔ws — the initial connect still crosses transports), rebuilds the client, re-opens sessions (`controller.setup`), and resumes; a `--save` recording continues on the same journal (the gap shows in the timestamps). Bounded to `transport.reconnect_max_wait` (default 6.0s) by default; `--wait` retries forever. Infra: `canlib/modes/monitor_reconnect.py` (`ReconnectPolicy`/`MonitorReconnector`/`reconnect_policy`), the per-transport connect closures `build_elm_reconnector` (`canlib/commands/_live/connect.py`, reusing `connect_elm_terminal`) and `build_raw_reconnector` (`canlib/modes/raw_monitor.py`, reusing `build_raw_client`), and `MonitorController.rebind`/`close_client`; the poll loops (`_monitor_noninteractive` + the Textual `_monitor_tui` loop, which shows a `⟳ reconnecting…` banner) call the reconnector on `disconnected`. See `plans/2026-08-03-monitor-reconnect-and-wait.md`.

All CLI tools use `--wican home|vpn|<ip>` to select the target. Without config, falls back to `192.168.80.1` (WiCAN AP mode).

- WebSocket terminal: `ws://<ip>/ws` (send `{"ws_mode": "terminal", "terminal_type": "elm327"}`)

## Transports

canair reaches the bus through one explicitly-selected transport (never auto-detected). Selection precedence: `--transport`/`--wican` CLI > per-device `transport:` > global `transport:` block > default `slcan-tcp`. Registry-driven: each is a `TransportSpec` in `canlib/transport/config.py::TRANSPORTS` (adding a backend = registering a spec).

- **`slcan-tcp`** (default, `raw=True`) — raw SLCAN over TCP; canair runs client-side ISO-TP/UDS (pipelined). Any WiCAN (Pro/classic) or gateway; also powers `canair sniff`. Backend: `RawTerminal` (`canlib/transport/raw_terminal.py`) over `SlcanTcpBus`.
- **`wican-ws`** (Pro-only, `raw=False`) — ELM327 terminal over the WiCAN's `ws://host/ws` WebSocket; the dongle does ISO-TP. Backend: `WiCANTerminal` (`canlib/terminal.py`).
- **`elm327-tcp`** (`raw=False`, `wican_http=False`) — a **generic ELM327 adapter over a plain TCP socket**: WiFi clones (Kiwi, vLinker, OBDLink) and the ELM327-Emulator's `-n` mode. No WiCAN, no HTTP config API. Backend: `Elm327TcpTerminal` (`canlib/transport/elm327_terminal.py`) over a `TcpChannel`; default port 35000 (`DEFAULT_ELM327_TCP_PORT`).

**Shared ELM327 engine.** The ELM327 protocol logic lives once in `Elm327Terminal` (`canlib/transport/elm327_terminal.py`), driven by a swappable async byte `Channel` (`canlib/transport/channel.py`: `WebSocketChannel` for the WiCAN, `TcpChannel` for a clone). `WiCANTerminal`/`Elm327TcpTerminal` are thin subclasses wiring their channel — so a new ELM327 wire (e.g. serial) is a new `Channel`, not a duplicated engine. The engine exposes `drain()` + `recv_frame(timeout)` (passive decoded receive) so modes that collect late frames (the SKM relay-wake) go through the transport-agnostic surface, not the raw socket; `WiCANTerminal` keeps a settable `ws`/`url` proxy only for WiCAN test fakes. `host` is derived from the channel (single source of truth). All three backends satisfy the `Terminal` protocol (`transport/protocol.py`) and run through the shared `dispatch_mode`. ELM-only features (the interactive `repl`, `skm-wake`) gate on `isinstance(terminal, Elm327Terminal)` — so they work on `wican-ws` **and** `elm327-tcp`, but are refused on raw `slcan-tcp` (`RawTerminal`, which parses no ELM `ATSH` text).

**`is_wican_http`** (`TransportConfig`) is spec-driven (`TransportSpec.wican_http` + a host), NOT `host is not None`: true only for the WiCAN transports (queryable `/load_config` / `/check_status`), false for `elm327-tcp`. Gates the WiCAN-only paths in `async_main` (`_live/runtime.py`; sleep banner, `reboot_wican`, `require_ws_reachable`) and `canair status`. The ELM connect factory `connect_elm_terminal(transport, …)` (`_live/connect.py`) builds the right terminal by `transport.type`; a direct-ELM reachability pre-check is `require_elm327_tcp_reachable` (`wican_mode.py`, probes the ELM socket port). Fallback liveness (`transport/fallback.py::_probe_port`) probes port 80 for WiCAN-HTTP, else the ELM/data port.

**Offline testing** — point `elm327-tcp` at [ELM327-Emulator](https://github.com/ircama/ELM327-emulator) (`elm -n 35000`) for a device-free ELM327 wire. It is **not** a canair dependency (its legacy build breaks `uv sync`; install manually with `uv pip install "setuptools<80"` then `uv pip install --no-build-isolation ELM327-emulator`). Opt-in integration test `tests/test_elm327_emulator.py` auto-skips when absent (core suite stays device-free). A bundled test profile `tests/fixtures/profiles/elm327-emulator/` (ENGINE ECU at 0x7E0 + standard OBD-II Mode-01 PIDs) makes `canair read` decode against the emulator; its decode expressions are guarded device-free in `tests/test_elm327_tcp.py`. Docs: `docs/development/offline-testing.md`. Plan: `plans/2026-08-03-elm327-direct-transport.md`.
